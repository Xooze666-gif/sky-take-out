# 苍穹外卖 —— 面试 20 问（附标准答案）

> 针对本项目的高频面试追问。每题先给「一句话答案」，再给「可展开的细节」。面试时先答一句话答案，被追问再展开。

## 一、鉴权与上下文（Q1-Q4）

### Q1. 你项目的 JWT 是怎么实现的？为什么不用现成的库？

**一句话答案**：手写 HS256，不引第三方库，核心就是「HMAC-SHA256 算签名 + 验签」。

**展开**：
- token 分三段：header（算法）、payload（载荷）、signature（签名）。
- 签发：`sign(secretKey, header.payload)` 算出签名拼第三段。
- 验签：重新算一次签名，和 token 里的签名对比，一致才信任。
- 手写的好处：零依赖、体积小、面试能讲清底层原理；坏处：功能少（无 refresh、无吊销），生产一般用 jjwt 或 spring-security。

### Q2. 为什么 token 里只放 empId，不放姓名/手机号/密码？

**一句话答案**：token 前两段只是 Base64 编码不是加密，谁都能解开，敏感信息不能放；需要什么拿 id 查库即可（瘦 token）。

**展开**：
- Base64 可逆，任何拿到 token 的人都能解出 payload，放密码等于泄露。
- 只放 id，后续要姓名查 employee 表、要权限查权限表，信息变更不用重发 token。

### Q3. 有人把 token 的 empId 从 1 改成 999，后端怎么发现？

**一句话答案**：改 payload 会破坏签名，验签时重新算的签名对不上，直接拒绝。

**展开**：
- 签名 = 用只有后端知道的密钥对「前两段」盖章。
- 攻击者改 empId 就得重新算签名，但他没有密钥，算不出，改完签名必对不上。

### Q4. 为什么签名比较用 `MessageDigest.isEqual` 而不是 `Arrays.equals`？

**一句话答案**：防时序攻击——`isEqual` 不提前返回，整段比完，耗时常量。

**展开**：
- 普通 equals 遇第一个不同字节就 return，攻击者靠「返回快慢」一个字节一个字节撞签名。
- `isEqual` 无论错在第几位都完整比较，用时一样，杜绝时间侧信道。

### Q5. 你的管理端和用户端鉴权是怎么隔离的？

**一句话答案**：两套独立 JWT——不同密钥、不同请求头、不同载荷。

**展开**：
- 管理端：请求头 `token`，载荷 `empId`，密钥 A。
- 用户端：请求头 `authentication`，载荷 `userId`，密钥 B。
- 两套拦截器分别拦 `/admin/**` 和 `/user/**`，天然隔离，用户 token 无法访问管理接口。

### Q6. 为什么要用 ThreadLocal 存登录用户 id？

**一句话答案**：让同一请求的 Controller → Service → Mapper 全程都能读到"当前是谁"，免逐层传参。

**展开**：
- 靠参数传 id 的话，每个方法签名都要加一个参数，侵入严重。
- ThreadLocal 是"线程的私有储物柜"，同线程内任意位置可读。

### Q7. 100 个请求同时进来，ThreadLocal 里的 id 会串吗？为什么？

**一句话答案**：不会。因为每个请求占一个线程，ThreadLocal 按线程隔离。

**展开**：
- 分配线程的是 Tomcat 线程池，不是 ThreadLocal。
- ThreadLocal 给每个线程一个独立存储格，不同线程（对应不同请求）互不干扰。

### Q8. 既然按线程隔离不会串，为什么还要在 afterCompletion 里 remove？

**一句话答案**：因为线程池复用线程，不 remove 会把上一个用户的 id 留给下一个请求（串号 + 内存泄漏）。

**展开**：
- 请求1 处理完，线程回到池子，口袋里还留着 id=1。
- 请求2 复用这个线程，若它没有登录态，可能误读到 id=1。

## 二、ORM 与事务（Q9-Q12）

### Q9. 公共字段（createTime/createUser 等）是怎么自动填的？

**一句话答案**：实体字段标 `@TableField(fill=...)` 声明，`MetaObjectHandler` 的 `insertFill`/`updateFill` 真正赋值。

**展开**：
- 两层配合缺一不可：只标注解没人赋值，只写 handler 不知道填哪些字段。
- `strictInsertFill` 会校验字段是否标了 fill 注解，没标的跳过，所以一个 handler 能服务所有表（比如 shopping_cart 没有 create_user 字段也不会误填）。

### Q10. 为什么用 MyBatis-Plus 的 MetaObjectHandler，而不用 AOP + 反射（课程原版）？

**一句话答案**：AOP 在业务层外围猜，MetaObjectHandler 是框架在 SQL 层的原生回调，更精确、无反射开销、零额外依赖。

**展开**：
- AOP 方案要自定义注解 + 切面 + 反射遍历字段，还要靠方法名猜是增还是改。
- MetaObjectHandler 是 MP 在 SQL 组装前精确回调，天生知道 insert 还是 update，且 MP 已缓存表元数据，无需反射遍历。

### Q11. 自动填充什么情况下会失效？

**一句话答案**：在 XML 里手写 insert/update 语句时，MetaObjectHandler 不会被触发。

**展开**：
- 它只对 `BaseMapper.insert/update` 生效。
- 另外 `strictInsertFill` 默认只在字段为 null 时才填，手动 set 过的不覆盖。

### Q12. 菜品和口味（一对多）、套餐和菜品（多对多）是怎么存的？为什么加 @Transactional？

**一句话答案**：一对多用主表 + 外键子表，多对多用中间表；增删改涉及多张表，加事务保证要么全成要么全滚。

**展开**：
- 菜品-口味：dish 表 + dish_flavor 表（dish_id 外键）。
- 套餐-菜品：setmeal 表 + setmeal_dish 中间表（setmeal_id + dish_id）。
- 更新用「先删后插」全量替换，插入前把 id 置 null 防前端带 id 篡改。
- `@Transactional` 默认只回滚 RuntimeException 和 Error，遇检查异常需 `rollbackFor`。

## 三、业务与安全（Q13-Q16）

### Q13. 下单时的价格是从前端拿的还是后端查的？为什么？

**一句话答案**：后端查 dish 表补 name/price，不信任前端传价。

**展开**：
- 防前端篡改价格。
- 订单存价格快照，后续改菜品价不影响历史订单（历史可追溯）。

### Q14. 支付是怎么实现幂等的？重复支付回调会怎样？

**一句话答案**：订单状态机 + 订单号唯一索引，重复回调直接返回 duplicate，不重复入账。

**展开**：
- 回调先查订单，若 payStatus 已支付直接返回 duplicate。
- 首次才更新支付状态 + 订单状态（待付款→待接单）。
- 唯一索引兜底，防止并发下重复插入。

### Q15. 为什么不用 Redis 做幂等和缓存？

**一句话答案**：本机没装 Redis，用数据库状态机 + 唯一索引替代，功能等价。

**展开**：
- 主动补充：生产高并发场景会引入 Redis 缓存热菜/店铺状态、分布式锁，这是后续增强方向（引导面试官聊 Redis，体现有储备）。

### Q16. WebSocket 来单提醒是怎么实现的？怎么管理并发连接？

**一句话答案**：`@ServerEndpoint` 建立长连接，用 `ConcurrentHashMap` 按 type 分组的会话池管理连接。

**展开**：
- 支付成功/催单时，向对应 type 组的会话推送消息。
- 分组的好处：来单提醒推给商家端（type=1），催单推给特定端（type=2），互不干扰。

## 四、SQL 与工程（Q17-Q20）

### Q17. 为什么有些 SQL 写在 XML 里，有些用 BaseMapper？

**一句话答案**：单表简单 CRUD 用 BaseMapper，复杂 SQL（join 分类名、聚合统计）走 XML。

**展开**：
- 菜品分页要 join category 取 categoryName，BaseMapper 表达不了，写 XML。
- 统计报表是聚合查询，同样走 XML，符合"复杂 SQL 显式管理"的工程习惯。

### Q18. 营业额统计的口径是什么？为什么？

**一句话答案**：只统计 status=5（已完成）订单的金额，按订单时间分组。

**展开**：
- 待接单/派送中的订单金额不算营业额，否则数据虚高。
- 用 order_time 做日期维度，与订单数、用户数同一时间轴对齐。

### Q19. 你的项目是多模块 Maven，为什么要拆模块？怎么管理依赖版本？

**一句话答案**：common/pojo 是稳定底座，server 是天天改的业务，拆开便于复用、解耦、统一管理版本。

**展开**：
- 未来加用户端独立服务或定时任务，直接依赖 common+pojo 复用。
- 父 pom 用 `<dependencyManagement>` 统一管理版本，子模块不用写版本号。

### Q20. 订单的状态机是怎么设计的？为什么要有状态守卫？

**一句话答案**：订单状态 1待付款→2待接单→3已接单→4派送中→5已完成（+6取消），每个流转接口校验前置状态，非法流转直接拒绝。

**展开**：
- 比如接单要求当前是"待接单"，派送要求"已接单"，完成要求"派送中"。
- 状态守卫防止越权操作和状态错乱，保证数据一致性。

## 附：三个高频"挖坑"追问，提前备好

1. **"如果用户量大了，你的方案哪里扛不住？"**
   → 答：ThreadLocal 无问题；主要是支付幂等和热数据查询，会加 Redis 缓存 + 分布式锁，接口加限流。

2. **"JWT 有 refresh token 吗？token 被盗怎么办？"**
   → 答：本项目 ttl 较短（管理端 2h），没有 refresh；生产会加 refresh token + 黑名单，关键操作二次校验。

3. **"你的 @Transactional 在自调用（同类方法互调）时生效吗？"**
   → 答：不生效，因为 Spring 事务靠代理对象，自调用绕过代理；解法是用 AopContext 或拆到不同类。
