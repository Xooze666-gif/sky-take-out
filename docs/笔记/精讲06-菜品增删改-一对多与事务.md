# 精讲 06 · 菜品增删改：一对多 + 事务 + 主键回填

> 源码位置：`DishServiceImpl`（`saveWithFlavor` / `updateWithFlavor` / `deleteBatch`）
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版

---

## ① 场景

三个动作，三个接口：

| 动作 | 请求 | 涉及表 |
|---|---|---|
| 新增菜品 | `POST /admin/dish` | `dish` + `dish_flavor` |
| 修改菜品 | `PUT /admin/dish` | `dish` + `dish_flavor` |
| 删除菜品 | `DELETE /admin/dish?ids=14` | `dish` + `dish_flavor` |

前端提交的 JSON（新增）是这样的：

```json
{
  "name": "测试麻婆豆腐",
  "categoryId": 3,
  "price": 28.00,
  "image": "https://example.com/mapo.jpg",
  "description": "精讲用测试菜品",
  "status": 1,
  "flavors": [
    {"name": "辣度", "value": "[\"不辣\",\"微辣\",\"中辣\"]"},
    {"name": "忌口", "value": "[\"不要葱\",\"不要蒜\"]"}
  ]
}
```

注意 `flavors` 是**嵌在菜品里的数组**——这就是一对多在 HTTP 接口上的表现：前端一次提交，后端拆成两张表存。

---

## ② 数据：执行前 → 执行后

**执行前**：`dish` 表最大 id = 13，`dish_flavor` 表最大 id = 8。

**执行后**：

`dish` 表新增一行：

| id | name | category_id | price | status | create_user | update_user |
|---|---|---|---|---|---|---|
| **14** | 测试麻婆豆腐 | 3 | 28.00 | 1 | 1 | 1 |

`dish_flavor` 表新增两行：

| id | dish_id | name | value |
|---|---|---|---|
| **9** | 14 | 辣度 | `["不辣","微辣","中辣"]` |
| **10** | 14 | 忌口 | `["不要葱","不要蒜"]` |

**关键点：`dish_flavor.dish_id` 都是 14。** 而 14 这个数字，是 `INSERT dish` 之后 MySQL 自增出来的——前端根本没传。这个"拿到新主键"的过程就是**主键回填**。

## ③ 逐行拆

### 新增：`saveWithFlavor`

```java
@Transactional
public void saveWithFlavor(DishDTO dishDTO) {
    Dish dish = new Dish();
    BeanUtils.copyProperties(dishDTO, dish);      // ① DTO → Entity
    dish.setStatus(StatusConstant.ENABLE);        // ② 强制起售
    dishMapper.insert(dish);                      // ③ 插主表，主键回填到 dish.id

    insertFlavors(dish.getId(), dishDTO.getFlavors());   // ④ 用回填的 id 插子表
}
```

**第 ① 行为什么不直接用 `DishDTO` 当实体插库？** 因为 `DishDTO` 里有 `flavors` 字段，而 `dish` 表没有这一列。虽然 `Dish` 实体上标了 `@TableField(exist = false)` 排除它，但 DTO 和 Entity 的职责本来就该分开：**DTO 面向接口（前端要什么字段），Entity 面向数据库（表有什么列）**。混用会导致"改接口就得改表映射"。

**第 ② 行为什么要强制 `status = ENABLE`？** 因为新增的菜品默认应该是"起售"状态（`DishServiceImpl.saveWithFlavor` 里写死了 `StatusConstant.ENABLE`），不信任前端传的 `status`。虽然这个 JSON 里前端也传了 `status:1`，但后端不依赖它。

**第 ③ 行是全场最关键的一行。**

`dishMapper.insert(dish)` 执行完后，`dish.getId()` 从 `null` 变成了 `14`。这不是魔法，是 MyBatis-Plus 干的：

```java
@TableId(value = "id", type = IdType.AUTO)   // Dish 实体上这一行
private Long id;
```

`IdType.AUTO` 告诉 MyBatis-Plus"主键由数据库自增生成"，于是它会在 `INSERT` 之后执行：

```java
// 简化后的 JDBC 逻辑
PreparedStatement ps = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS);
ps.executeUpdate();
ResultSet rs = ps.getGeneratedKeys();     // 拿回自增主键
if (rs.next()) entity.setId(rs.getLong(1));   // 塞回实体
```

**如果没有这一行 `type = IdType.AUTO`，`dish.getId()` 会一直是 `null`**，子表的 `dish_id` 就是 `NULL` —— 数据库如果要求 `NOT NULL` 就直接报错，如果允许 `NULL` 就会产生一批"不知道属于谁的"孤儿口味。

### 新增：`insertFlavors`

```java
private void insertFlavors(Long dishId, List<DishFlavor> flavors) {
    if (CollectionUtils.isEmpty(flavors)) {
        return;                          // ① 没口味就直接返回，不是异常
    }
    for (DishFlavor flavor : flavors) {
        flavor.setId(null);              // ② 强制走自增
        flavor.setDishId(dishId);        // ③ 绑定父 id
        dishFlavorMapper.insert(flavor);
    }
}
```

**第 ① 行**：有些菜品确实没有口味（比如"米饭"）。`CollectionUtils.isEmpty` 同时挡 `null` 和空集合，所以 `flavors: []` 和 `flavors: null` 都不会报错。如果没这行，`for` 循环遍历 `null` 会 NPE。

**第 ② 行 `setId(null)` 是防篡改。** 假设前端（或恶意用户）在 `flavors` 数组里塞了 `{"id": 5, ...}`，如果不置 null，MyBatis-Plus 会认为这是"指定主键插入"，直接往 `dish_flavor` 表里写 `id=5`——**把别人菜品的口味覆盖掉**。置 null 之后强制走自增，攻击无效。

这是"不信任前端"的经典落地，面试常问"你怎么防参数篡改"，这行就是答案之一。

**第 ③ 行**：`setDishId(dishId)` 而不是信任 `flavor.getDishId()`。同理，前端传的 `dishId` 也不可信。

**这一行是循环单条 INSERT，不是批量。** 2 个口味 = 2 条 SQL。如果口味有 20 个，就是 20 次数据库往返 —— 这是性能缺口，后面第 ⑦ 层说。

### 修改：`updateWithFlavor` —— 为什么"先删后插"

```java
@Transactional
public void updateWithFlavor(DishDTO dishDTO) {
    Dish dish = new Dish();
    BeanUtils.copyProperties(dishDTO, dish);
    dishMapper.updateById(dish);          // ① 改主表

    // 口味采取「先删后插」全量替换
    dishFlavorMapper.delete(Wrappers.<DishFlavor>lambdaQuery()
            .eq(DishFlavor::getDishId, dishDTO.getId()));   // ② 删掉旧口味
    insertFlavors(dishDTO.getId(), dishDTO.getFlavors());   // ③ 插新口味
}
```

假设原来菜品 14 有【辣度】【忌口】两个口味，现在前端改成只有【辣度】。

**三种可能的实现方式：**

| 方案 | 逻辑 | 问题 |
|---|---|---|
| A. 逐条比对 | 查出旧列表，跟新列表做 diff：哪些删、哪些改、哪些新增 | 代码复杂度爆炸（要按 name 匹配？还是按 id？id 变了怎么办？），极易漏分支 |
| B. 局部更新 | 只 `UPDATE` 前端传来的那几条 | 前端"删掉一个口味"这个动作无法表达（没有对应记录可更新） |
| **C. 先删后插（当前）** | 全删，全插 | 口味 id 会变（见下） |

**方案 C 的代价，我用 SQL 抓出来了：**

修改前口味 id 是 `9`（辣度）、`10`（忌口）；修改后只剩一条，**id 是 `11`**。

也就是说：**原来那条"辣度"记录被删掉了，新插了一条 id=11 的"辣度"**。语义上它俩是同一条，物理上是两条不同记录。

**这有问题吗？** 在这个项目里没问题，因为 `dish_flavor.id` **没有被任何其他表引用**（没人存 `flavorId`）。如果将来做了"用户收藏某个口味"或"口味销量统计"，这条 id 就会断链。

**这就是方案 C 的适用条件：子表的主键没有被外部引用。** 面试被问"先删后插有什么风险"，这就是标准答案。

### 删除：`deleteBatch` —— 顺序和校验

```java
@Transactional
public void deleteBatch(List<Long> ids) {
    if (CollectionUtils.isEmpty(ids)) {
        return;
    }
    // ① 起售中的菜品不能删
    Long onSale = dishMapper.selectCount(Wrappers.<Dish>lambdaQuery()
            .in(Dish::getId, ids)
            .eq(Dish::getStatus, StatusConstant.ENABLE));
    if (onSale != null && onSale > 0) {
        throw new BaseException(MessageConstant.DISH_ON_SALE);
    }

    // ② 先删口味，再删菜品
    dishFlavorMapper.delete(Wrappers.<DishFlavor>lambdaQuery().in(DishFlavor::getDishId, ids));
    dishMapper.deleteBatchIds(ids);
}
```

**第 ① 步的业务理由**：菜品如果在售，用户可能正在下单。删了之后订单里的 `dish_id` 指向一个不存在的菜品，历史订单详情页会显示空白。

**注意 `> 0` 而不是 `> 1`**：只要有一个在售就不让删。这是"全或无"的语义——批量删除要么全成功，要么全失败，不会出现"删了一半"。

**第 ② 步的顺序**：先子后主。如果反过来（先删 dish，再删 flavor），中间那一刻 `dish_flavor` 里有一批 `dish_id` 指向不存在的菜品 —— 孤儿数据。如果将来加了外键约束，先删主表会直接报 `Cannot delete or update a parent row`。

## ④ SQL 实况（真实抓取）

### 场景 A：新增菜品（带 2 个口味）

```sql
SET autocommit=0
SELECT @@session.transaction_read_only

INSERT INTO dish ( name, category_id, price, image, description, status,
                   create_time, update_time, create_user, update_user )
VALUES ( '测试麻婆豆腐', 3, 28.00, 'https://example.com/mapo.jpg', '精讲用测试菜品', 1,
         '2026-10-27 22:40:55.133745', '2026-10-27 22:40:55.133745', 1, 1 )

SELECT @@session.transaction_read_only
INSERT INTO dish_flavor ( dish_id, name, value ) VALUES ( 14, '辣度', '["不辣","微辣","中辣"]' )

SELECT @@session.transaction_read_only
INSERT INTO dish_flavor ( dish_id, name, value ) VALUES ( 14, '忌口', '["不要葱","不要蒜"]' )

commit
SET autocommit=1
```

**逐条解读：**

| SQL | 含义 |
|---|---|
| `SET autocommit=0` | **事务开始**。Spring 的 `DataSourceTransactionManager` 把连接改成手动提交 |
| `SELECT @@session.transaction_read_only` | 不是业务 SQL。MySQL 驱动在事务内每条语句前做的连接状态检查，用来决定是否要发 `SET SESSION TRANSACTION READ ONLY` |
| `INSERT INTO dish ...` | 主表插入，**注意有 `create_time`/`update_time`/`create_user`/`update_user`** |
| `INSERT INTO dish_flavor ... (14, ...)` | 子表插入，**14 就是上一条 INSERT 回填的主键** |
| `commit` | 事务提交 |
| `SET autocommit=1` | 连接归还池子前恢复自动提交 |

**这段输出最值钱的两个点：**

1. **`dish_id = 14` 是主键回填的铁证**。`INSERT dish` 的 SQL 里**没有 id 列**（走自增），但下一条 SQL 里就出现了 14。
2. **`create_time`/`create_user` 出现在 `INSERT dish` 里，但不出现在 `INSERT dish_flavor` 里**。因为 `Dish` 实体标了 `@TableField(fill=...)`，而 `DishFlavor` 实体**没标**（`dish_flavor` 表也确实没有这四列）。这就是 `strictInsertFill` 的价值 —— 详见精讲 12。

### 场景 B：修改菜品（口味从 2 条变 1 条）

```sql
SET autocommit=0

UPDATE dish SET name='测试麻婆豆腐改', category_id=3, price=32.00, image='...', description='改价改口味',
                update_time='2026-10-27 22:41:03.607031', update_user=1
WHERE id=14

DELETE FROM dish_flavor WHERE (dish_id = 14)

INSERT INTO dish_flavor ( dish_id, name, value ) VALUES ( 14, '辣度', '["微辣"]' )

commit
```

**注意这里的 `UPDATE` 只带上了 `update_time` 和 `update_user`，没有 `create_time`/`create_user`。** 因为实体上标的是：

```java
@TableField(fill = FieldFill.INSERT)          // createTime：只在插入时填
@TableField(fill = FieldFill.INSERT_UPDATE)   // updateTime：插入和更新都填
```

`updateFill` 方法里也确实只填了 `updateTime` 和 `updateUser`。**这个区分是必要的——创建时间一旦确定就不该被改。**

### 场景 C：删除起售中的菜品 → 被拦（看 `rollback`）

```sql
SET autocommit=0
SELECT COUNT( * ) AS total FROM dish WHERE (id IN (14) AND status = 1)
rollback
SET autocommit=1
```

响应：`{"code":0,"msg":"起售中的菜品不能删除"}`

**这条 `rollback` 是本次抓 SQL 最有价值的发现之一。**

它证明了：

```
@Transactional 方法内抛异常
  → Spring 事务拦截器 catch 到 RuntimeException
  → 调 connection.rollback()
```

也就是说 `@Transactional` 的默认行为是「**遇到 RuntimeException 回滚**」。`BaseException` 继承了 `RuntimeException`（如果不是，这里就不会回滚），所以能生效。

**如果 `BaseException` 继承的是 `Exception`（受检异常）呢？** 那 `@Transactional` 默认**不回滚**，需要写 `@Transactional(rollbackFor = Exception.class)`。

**这是 @Transactional 最高频的面试坑。** 而且它很隐蔽：报错提示正常显示了，你以为逻辑对，实际上前面已经写进去的数据没回滚。

### 场景 D：删除停售的菜品 → 成功

```sql
SET autocommit=0
SELECT COUNT( * ) AS total FROM dish WHERE (id IN (14) AND status = 1)    -- 结果 0，放行
DELETE FROM dish_flavor WHERE (dish_id IN (14))                            -- 先删子
DELETE FROM dish WHERE id IN ( 14 )                                        -- 再删主
commit
```

验证结果：

```sql
SELECT (SELECT count(*) FROM dish WHERE id=14) AS dish_left,
       (SELECT count(*) FROM dish_flavor WHERE dish_id=14) AS flavor_left;
-- dish_left = 0, flavor_left = 0
```

**「先子后主」在 SQL 层面看得清清楚楚。**

## ⑤ 权衡

### 为什么不用 JSON 字段存口味？

MySQL 5.7+ 支持 `JSON` 类型，完全可以把口味存成 `dish.flavors` 一个 JSON 列，省掉一张表。

**为什么没这么做：**

| | 两张表（当前） | 一个 JSON 列 |
|---|---|---|
| 按口味查询（"所有含'微辣'的菜"） | `WHERE name='辣度' AND value LIKE '%微辣%'`（表结构清晰） | `JSON_CONTAINS(flavors, ...)`，可读性差、索引麻烦 |
| 单条口味独立更新 | 直接 `UPDATE dish_flavor SET value=? WHERE id=?` | 要读整个 JSON、改、写回（读-改-写有并发问题） |
| 外键/约束 | 能做 | JSON 内部无法约束 |
| 写入性能 | 多几条 INSERT | 一次写入 |
| 表结构可读性 | 打开表就知道有哪些字段 | 打开表只看到一坨 JSON |

**结论：口味是"有结构、要被查询、会被单独修改"的数据，应该建表。** JSON 列适合存"结构不固定、只整体读写"的数据（比如前端埋点的扩展属性）。

### 为什么删除要"起售中不能删"，而不是"删的时候自动停售"？

因为**删除是危险操作，应该让操作者明确知道自己在做什么**。

自动停售再删除，用户点一下"删除"，系统悄悄把商品下架了——如果这是误操作，商品直接消失，用户来不及反应。而"起售中不能删"是一个**刹车**：先停售（一个明确的、可回滚的动作），再删除。两步之间有确认的机会。

**这是"危险操作要增加摩擦"的设计原则。** 类似：GitHub 删仓库要你手打仓库名。

### 为什么 `deleteBatch` 加了 `@Transactional`，而 `startOrStop` 没加？

看 `startOrStop`：

```java
public void startOrStop(Integer status, Long id) {
    Dish dish = new Dish();
    dish.setId(id);
    dish.setStatus(status);
    dishMapper.updateById(dish);      // 只有一条 SQL
}
```

**只有一条 SQL 的操作不需要事务**——单条 SQL 本身就是原子的（InnoDB）。加事务只是多两次 `SET autocommit` 往返，纯开销。

而 `deleteBatch` 有**三条** SQL（1 次 COUNT + 2 次 DELETE），必须包起来。

**判断标准：一次业务操作是否产生 ≥2 条写 SQL。** 是 → 加事务；否 → 不加。

（注意：`deleteBatch` 里的 `SELECT COUNT` 也算在事务内，因为它必须和 DELETE 看到同一个数据快照。否则并发下可能出现"COUNT 时还在售、DELETE 时已停售"的窗口。）

## ⑥ 踩坑实录

### 坑 1：第一次写的时候先插口味，`dish_id` 是 null

最早的顺序是"先插口味，再插菜品"（直觉上"先有明细再有总单"）。结果：

```sql
INSERT INTO dish_flavor (dish_id, name, value) VALUES (NULL, '辣度', '...')
```

因为这时 `dish` 还没入库，`dish.getId()` 是 `null`。

**修法**：顺序反过来，先插主表拿到自增 id，再插子表。

**这个坑的本质是：一对多的父子关系里，子表的外键必须来自父表的主键，所以父表必须先落库。** 不管用什么 ORM，这个物理顺序改不了。

### 坑 2：`@Transactional` 在同一个类里自调用会失效

假设我这么写：

```java
public void saveWithFlavor(DishDTO dto) {
    // ... 插入 dish
    this.insertFlavors(dish.getId(), dto.getFlavors());   // 自调用
}

@Transactional
public void insertFlavors(Long dishId, List<DishFlavor> flavors) { ... }
```

**`insertFlavors` 上的 `@Transactional` 完全无效。**

原因：Spring 的事务是靠**动态代理**实现的。外部调用 `dishService.saveWithFlavor()` 走的是代理对象，代理在方法前后加事务逻辑。但 `this.insertFlavors()` 里的 `this` 是**原始对象**（不是代理），绕过了代理，事务注解形同虚设。

**修法**：把事务加在**最外层的入口方法**上（项目里就是这么做的，`@Transactional` 标在 `saveWithFlavor` 上，`insertFlavors` 是 private 不加注解）。

这也解释了另一个现象：项目里 `insertFlavors` 是 `private` 的。`private` 方法 Spring 代理根本拦不到，加了 `@Transactional` 也不生效——干脆不加，靠外层事务覆盖。

### 坑 3：我以为 `commit`/`rollback` 是代码里写出来的

第一次抓 `general_log` 看到 `SET autocommit=0 ... commit`，以为是某个地方手写了这些语句。翻遍代码找不到。

真相：**全是 Spring 的 `DataSourceTransactionManager` 干的**，代码里一行都没有。你在 Java 侧只写了 `@Transactional` 这一个注解。

```
@Transactional
  → 方法进入：getConnection() + setAutoCommit(false)      [对应 SET autocommit=0]
  → 方法正常返回：connection.commit()                      [对应 commit]
  → 方法抛 RuntimeException：connection.rollback()         [对应 rollback]
  → finally：setAutoCommit(true) + close()                [对应 SET autocommit=1]
```

**理解了这一层，"事务什么时候生效/失效"就不再是玄学。**

## ⑦ 缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **口味循环单条 INSERT** | 中 | 10 个口味 = 10 次数据库往返 | MyBatis-Plus 的 `saveBatch`，或 XML 里写 `<foreach>` 批量 INSERT |
| **删除是物理删除** | 中 | `DELETE FROM dish` 真删了，订单里的 `dish_id` 会指向不存在的记录 | 加 `deleted` 逻辑删除字段（MP 的 `@TableLogic`） |
| **没校验 `categoryId` 是否存在** | 低 | 传个不存在的分类 id 也能插进去，产生"孤儿菜品" | 插入前 `categoryMapper.selectById` 判空 |
| **`value` 存的是 JSON 字符串** | 低 | `["不辣","微辣"]` 以字符串形式存在 `varchar` 里，查询/校验都麻烦 | 要么建 `dish_flavor_value` 子表，要么在 Service 层统一序列化/反序列化 |
| **修改时没有乐观锁** | 低 | 两个人同时改同一菜品，后提交的覆盖先提交的 | 加 `version` 字段 + `@Version` |
| **删除没有记录操作人** | 低 | 谁删的菜品查不到（`dish` 表删了就没了） | 改逻辑删除，保留 `update_user` |

### 「物理删除会破坏历史订单」值得展开

用户 10-17 下的订单里有"麻婆豆腐"（`order_detail.dish_id = 5`）。如果管理员把菜品 5 删了：

- 订单列表页：能正常显示（因为 `order_detail` 里存了 `name` 快照）
- 点进订单详情想"再来一单"：后端 `repetition` 会把 `dishId=5` 加回购物车 → 购物车列表显示不出来（查不到菜品）→ 用户看到一条空白记录

**这正是"价格快照"的延伸价值**：快照让历史订单**显示**不受影响，但**关联操作**（再来一单、评价菜品）依然会断链。生产系统里这类数据一律逻辑删除。

## ⑧ 面试 30 秒版

> 菜品和口味是一对多，两张表。新增时有个关键顺序：**必须先插主表**，因为 MyBatis-Plus 的 `IdType.AUTO` 会在 `INSERT` 后把自增主键回填到实体上，子表才能拿到 `dish_id`；我第一次写反了，插口味时 `dish_id` 是 NULL。
>
> 修改用「先删后插」全量替换，不比对差异——比对逻辑复杂易错，而在事务保护下删除+插入简单可靠。代价是子表主键会变（我抓 SQL 验证过：原 id 9、10 变成 11），所以这个方案只在子表主键没被外部引用时成立。
>
> 删除注意两条：起售中的菜品不让删，避免用户正在下单时商品消失；先删子表再删主表，否则产生孤儿数据。整个删除包在 `@Transactional` 里，我抓 `general_log` 能看到异常时确实有 `rollback`——因为 `BaseException` 继承了 `RuntimeException`，如果是受检异常默认不回滚，得写 `rollbackFor = Exception.class`。
