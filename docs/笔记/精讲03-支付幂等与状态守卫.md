# 精讲 03 · 支付幂等：`OrderServiceImpl.payment`

> 源码位置：`OrderServiceImpl.payment`
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版
> 本篇所有 SQL 来自真实 `general_log` 抓取；状态机守卫的完整分析见精讲 08。

---

## ① 场景

订单 `20261027223548518739` 处于「待付款」（`status=1`，`pay_status=0`）。

**"支付成功"这个事件，在真实系统里可能到达 N 次：**

1. 用户点「支付」→ 前端调 `/user/order/payment`
2. 微信服务端异步回调 `/notify/wechatPay`
3. **上面两种都"看起来失败"了（网络超时、响应丢失），微信重试推送** —— 可能推 3 次、5 次、甚至隔几分钟再推

第 3 种就是幂等要解决的核心场景：**同一件事，可能被通知很多遍。**

如果不做幂等：用户付了 38 元，系统记了两笔账、发了两份货、推了两次来单提醒。

---

## ② 数据：执行前 → 执行后

| 字段 | 支付前 | 支付后 |
|---|---|---|
| `pay_status` | 0（未支付） | **1（已支付）** |
| `status` | 1（待付款） | **2（待接单）** |
| `checkout_time` | NULL | **2026-10-27 22:36:03** |

**第二次调用时：三个字段一个都不变，而且数据库里一条写操作都没有。**

这一点比"字段没变"更强 —— 因为"没变"可能是"改了又改回来"，而"没有 UPDATE"是彻底的零副作用。

## ③ 逐行拆

### 第 1 步：用订单号查，不用 id

```java
Orders order = orderMapper.selectOne(Wrappers.<Orders>lambdaQuery()
        .eq(Orders::getNumber, ordersPaymentDTO.getOrderNumber()));
```

**为什么用 `number` 不用 `id`？** 因为支付回调来自第三方（微信），第三方只知道**商户系统传给它的订单号**，不知道你的自增 id。

**接口设计上，凡是"对外"的标识，都不该用内部主键。** 内部主键会暴露业务量、可被遍历（精讲 02 讲过）。

### 第 2 步：订单不存在

```java
if (order == null) {
    throw new BaseException(MessageConstant.ORDER_NOT_FOUND);
}
```

**这一步不能省。** 如果直接 `order.getPayStatus()`，`order` 是 null 就 NPE，被兜底 handler 变成"未知错误"，排查方向直接跑偏。

### 第 3 步：幂等的核心（三行）

```java
if (PayStatusConstant.PAID.equals(order.getPayStatus())) {
    return "duplicate";
}
```

**就这三行，挡住了所有重复回调。**

**为什么有效？** 因为状态存在**数据库**里，所有请求、所有线程、所有服务器实例看到的都是同一份：

```
第 1 次回调：读到 pay_status=0 → 往下走 → 改成 1 → commit
第 2 次回调：读到 pay_status=1 → 直接 return "duplicate"
```

**为什么不用内存标记（比如 `Set<String> processedOrders`）？** 三个致命问题：

1. **服务重启就丢了。** 重启后的第一个重复回调会重新处理一遍。
2. **多实例各自一份内存。** 部署 3 台服务器，回调打到 A 机处理了，重试打到 B 机，B 机不知道，又处理一遍。
3. **内存只增不减会 OOM。** 想清理就得设过期，又回到"过期窗口内重复怎么办"的老问题。

**只有数据库（或 Redis）这种共享存储，才能跨请求、跨实例、跨重启地记住"这件事处理过了"。**

**注意 `PayStatusConstant.PAID.equals(...)` 的顺序** —— 常量在前，`order.getPayStatus()` 是 `Integer` 可能为 null，`null.equals()` 会 NPE。

### 第 4 步：改状态

```java
order.setPayStatus(PayStatusConstant.PAID);
order.setStatus(OrderStatusConstant.TO_BE_CONFIRMED);
order.setCheckoutTime(LocalDateTime.now());
orderMapper.updateById(order);
```

**三件事一起做：钱到位了（`pay_status`）、流程推进了（`status`）、记账时间（`checkout_time`）。**

**为什么这三件事必须一起？** 如果只改 `pay_status` 不改 `status`，订单会卡在"待付款"但钱已收；如果只改 `status` 不改 `pay_status`，商家接单了但系统认为没付钱。**两个字段的语义必须同步推进。**

**但注意这里有个隐患**：`updateById(order)` 里 `order` 是**查出来的完整对象**，所以是 18 个字段全量 UPDATE（第 ④ 层有 SQL 证据）。

### 第 5 步：推送来单提醒

```java
webSocketServer.sendToType("1",
        "{\"type\":1,\"orderId\":" + order.getId() + ",\"content\":\"订单号 " + order.getNumber() + "\"}");
```

**注意位置：在 `updateById` 之后、`return` 之前。**

**如果放在幂等判断之前会怎样？** 每次重复回调都会推一次，商家页面反复弹窗＋响铃。用户付一次钱，商家听到三次"有新订单"。

**所以幂等不只保护数据库，也保护了所有"副作用"**：

- 推送通知
- 发短信
- 扣库存
- 调用第三方（打单机、配送系统）

**这是幂等设计的第一原则：幂等判断必须放在最前面，把后面所有副作用一起挡住。**

**顺带一个细节**：这里用字符串拼 JSON，`order.getId()` 是 `Long`、`getNumber()` 是纯数字字符串，不会产生转义问题。但如果将来 `content` 里要放用户名（可能含引号），拼接就会产生非法 JSON。**规范做法是 `ObjectMapper.writeValueAsString(dto)`。**

## ④ SQL 实况（真实抓取）

### 第 1 次支付（返回 `"success"`）

```sql
SELECT id,number,status,user_id,address_book_id,order_time,checkout_time,pay_method,
       pay_status,amount,remark,phone,address,consignee,cancel_reason,rejection_reason,
       cancel_time,estimated_delivery_time,delivery_status,delivery_time,pack_amount,
       tableware_number,tableware_status
FROM orders WHERE (number = '20261027223548518739')

UPDATE orders SET number='20261027223548518739', status=2, user_id=4, address_book_id=3,
       order_time='2026-10-27 22:35:49', checkout_time='2026-10-27 22:36:03.484332',
       pay_method=1, pay_status=1, amount=12.00, remark='要筷子', phone='13800138000',
       address='北京市北京市东城区XX路1号', consignee='张三',
       estimated_delivery_time='2026-10-27 23:30:00', delivery_status=1,
       pack_amount=0, tableware_number=1, tableware_status=1
WHERE id=5
```

**数一下 SET 里有多少个字段：18 个。** 除了 `id`，整行的所有字段都写了一遍。

### 第 2 次支付（返回 `"duplicate"`）

```sql
SELECT id,number,status,... FROM orders WHERE (number = '20261027223548518739')
```

**就这一条，然后结束。没有 UPDATE，没有 WebSocket 推送。**

### 对比就是答案

| | SQL |
|---|---|
| 第 1 次 | `SELECT` + **`UPDATE`（18 字段）** |
| 第 2 次 | `SELECT` ← **到此为止** |

**这不是"我觉得它幂等"，而是数据库层面对比下来，第二次调用零写入。**

**这也是我自己验证任何"幂等"的方法论：**

1. 开 `general_log`
2. 同一个请求连打两次
3. 对比两次 SQL —— 第二次**必须没有写操作**
4. 再看返回值：`success` → `duplicate`

**光看代码说"这里 return 了所以幂等"，不算证据。** 因为 return 之前有没有别的写操作，只有日志能告诉你。

### 顺便理解一件事：为什么支付全字段 UPDATE，接单只 SET 一个字段

```java
// 支付：order 是查出来的完整对象，18 个字段全非 null
Orders order = orderMapper.selectOne(...);
order.setPayStatus(PAID);
orderMapper.updateById(order);          // → SET 18 个字段

// 接单：new 出来的空对象，只有 id 和 status 有值
Orders update = new Orders();
update.setId(id);
update.setStatus(CONFIRMED);
orderMapper.updateById(update);         // → SET status=3 一个字段
```

**同一个 `updateById`，两种行为，差别就在"传进去的对象是查出来的还是 new 出来的"。**

因为 MyBatis-Plus 的 `updateById` 默认策略是 `FieldStrategy.NOT_NULL`：**只把非 null 的字段拼进 `SET`**。

| 传什么对象 | 字段状态 | 生成的 SQL |
|---|---|---|
| 查出来的完整实体 | 所有字段非 null | 全字段 UPDATE |
| `new` 的空实体 + 局部 set | 只有 set 过的非 null | 只 UPDATE 那几个字段 |

**面试被问"updateById 是全量更新还是增量更新"，标准答案：默认只更新非 null 字段，所以传完整对象等价于全量更新，传空对象局部赋值等价于增量更新。想显式全量更新可以用 `updateById` + `FieldStrategy.ALWAYS`，或者 `UpdateWrapper`。**

## ⑤ 权衡

| 决策 | 选了 | 另一种做法 | 为什么选这个 |
|---|---|---|---|
| 幂等载体 | 数据库 `pay_status` | 内存 `Set` | 内存重启即失效、多实例不共享 |
| 查询条件 | 订单号 `number` | 自增 `id` | 第三方只知道订单号 |
| 判断方式 | 先查后改 | 条件更新 | 简单直接，覆盖 99% 场景（并发缺口见 ⑦） |
| 并发兜底 | `number` 唯一索引 | 无 | 兜住"重复下单"，但兜不住"重复支付"（见 ⑦） |
| 副作用位置 | 幂等判断**之后** | 判断之前 | 防重复弹窗、重复发货 |
| 更新方式 | 全字段 UPDATE | 只 SET 三个字段 | 代码最简，但有丢失更新风险 |

### 为什么不用分布式锁 / Redis？

官方苍穹外卖用的是 **Redis 存购物车 + 店铺状态 + 加锁**。这个项目本机没装 Redis，所以走了"状态机 + 唯一索引"的纯数据库路线。

**这不是妥协，是另一种正确的实现。** 对比：

| | 数据库状态机（当前） | Redis 分布式锁 |
|---|---|---|
| 依赖 | 无（已有 MySQL） | 需要 Redis |
| 一致性 | 强（同一事务） | 最终一致（锁超时、主从延迟） |
| 并发能力 | 单行锁，TPS 几千 | 更高，但锁管理复杂 |
| 实现复杂度 | 低 | 中（要处理锁超时、误删锁、续期） |

**对于外卖这种"单笔订单只关心自己"的场景，数据库行锁完全够用。** 分布式锁适合"跨资源"的互斥（比如全局库存扣减）。

**面试如果被问"为什么不用 Redis 做幂等"，答"幂等标记必须和业务数据在同一个事务里才可靠；Redis 和 MySQL 是两个系统，写 Redis 成功、写库失败就会状态不一致。我用的方案里 `pay_status` 和订单数据在同一行、同一事务，天然一致。"**

**这个回答很硬，因为它指出了"跨系统一致性"这个真问题。**

### 为什么 `return "duplicate"` 而不是抛异常？

因为**重复支付不是错误**。

对于第三方回调来说，"我已经处理过了"是一个**正常的成功响应**。如果你返回错误，微信会认为回调失败，继续重试 —— 变成无限重试风暴。

**幂等接口的正确语义：**

- 第一次处理 → 返回成功
- 重复请求 → **也返回成功**（只是内部不做任何事）

**"成功"的含义是"这个事件已经被正确处理了"，不是"这次调用产生了效果"。**

**这个区别在对接第三方时极其重要。** 很多支付对接事故就是"重复回调返回失败 → 第三方无限重试 → 系统被打挂"。

## ⑥ 踩坑实录

### 坑 1：怎么"证明"幂等真的生效

一开始我只看了代码：

```java
if (PAID.equals(order.getPayStatus())) {
    return "duplicate";
}
```

逻辑很清楚，但**"看代码觉得对"和"实际是对的"是两件事**。

于是我把支付接口连打两次，抓 `general_log`：

- 第 1 次：`SELECT` + `UPDATE`
- 第 2 次：**只有 `SELECT`**

**这才叫验证。** 因为如果 `return` 写在了 `updateById` 之后（位置错），代码看起来还是"有幂等判断"，但实际每次都会全字段 UPDATE 一遍。

**教训：验证幂等要看"有没有写操作"，不是看"有没有 return"。**

### 坑 2：`confirm` 接口调不通，报 `body is missing`

```bash
# 我一开始这么调（错）
curl -X PUT ".../admin/order/confirm?id=5"
```

报：

```
HttpMessageNotReadableException: Required request body is missing:
... OrderController.confirm(com.sky.entity.Orders)
```

因为 Controller 是 `confirm(@RequestBody Orders orders)`，要的是 JSON body：

```bash
curl -X PUT ".../admin/order/confirm" -H "Content-Type: application/json" -d '{"id":5}'
```

**这个坑本身很小，但它暴露了一个设计问题**：接单只需要一个 `id`，却要求前端传整个 `Orders` 对象（23 个字段）。

虽然 Service 里"先查库再校验状态"、不采信前端传的 `status`，但**接口签名暴露了不该暴露的东西**。将来如果有人改动这段代码、不小心用上了前端传的 `status`，就是一个越权改状态的漏洞。

**正确做法**：`@PathVariable Long id`，或者定义一个只有 `id` 的 DTO。

**"接口只暴露必要参数"不是洁癖，是缩小攻击面。**

### 坑 3：`datetime` 精度导致时间"跳秒"

`checkout_time` 存的是 `2026-10-27 22:36:03.484332`，从库里读出来是 `2026-10-27 22:36:03`。

因为 `orders.checkout_time` 列是 `datetime`（不带小数秒），MySQL 对 `.484332` 做了**四舍五入**（截断/进位到秒）。

**影响**：如果你用 `checkout_time` 判断"两笔支付谁先谁后"，同一秒内的分不出来。

**修法**：建表用 `datetime(3)`（毫秒）或 `datetime(6)`（微秒）。这个项目全部用 `datetime`，是个建表时的疏漏。

### 坑 4：重复支付时返回 `"duplicate"`，前端不知道怎么处理

接口返回 `Result<String>`，`data` 是 `"success"` 或 `"duplicate"`。但前端只判 `code === 1`，两种情况都当成功处理。

**这个设计其实是对的**（幂等语义下两者都是成功），但**前端如果不区分，就没法做"支付成功但订单已处理过"的差异化提示**。

**更好的返回**：`{"code":1, "data":{"status":"DUPLICATE","orderId":5}}`，让前端能判断。

**这是"接口返回值信息量不足"的典型** —— 后端知道更多，但没告诉前端。

## ⑦ 缺口

### 缺口 1（最重要）：先查再改不是原子的

```java
if (order.getPayStatus() == PAID) return "duplicate";   // ① 查
order.setPayStatus(PAID);
orderMapper.updateById(order);                          // ② 改
```

**两个请求同时执行到 ①，都读到"未支付"，都往下走，都执行 ②。**

**这时 `number` 唯一索引救不了** —— 因为它挡的是"插入重复行"，而这里是"两次 UPDATE"，都不违反唯一约束。

```
时刻 T1: 回调 A 读到 pay_status=0
时刻 T2: 回调 B 读到 pay_status=0
时刻 T3: 回调 A UPDATE pay_status=1，推 WebSocket（第 1 次）
时刻 T4: 回调 B UPDATE pay_status=1，推 WebSocket（第 2 次）
结果：商家收到两条"新订单"提醒，如果后面还有发短信/扣库存，就重复执行了
```

**真正安全的写法（条件更新 / 乐观锁）：**

```java
int rows = orderMapper.update(null, Wrappers.<Orders>lambdaUpdate()
        .eq(Orders::getId, order.getId())
        .eq(Orders::getPayStatus, PayStatusConstant.UN_PAID)    // 状态作为 WHERE 条件
        .set(Orders::getPayStatus, PayStatusConstant.PAID)
        .set(Orders::getStatus, OrderStatusConstant.TO_BE_CONFIRMED)
        .set(Orders::getCheckoutTime, LocalDateTime.now()));

if (rows == 0) {
    return "duplicate";    // 没更新到 = 被别人抢先处理了
}
```

生成的 SQL：

```sql
UPDATE orders SET pay_status=1, status=2, checkout_time=?
WHERE id=5 AND pay_status=0
```

**为什么原子？** InnoDB 的 `UPDATE` 会对匹配行加排他锁，`WHERE` 的判断和 `SET` 在同一把锁内完成。两个并发请求只有一个能匹配到行。

**而且这一条 SQL 同时解决了缺口 2**（不再全字段覆盖）。

**这是本段代码最值得改的地方，面试必说。**

### 缺口 2：全字段 UPDATE 带来「丢失更新」

第 ④ 层的 SQL 显示：支付的 UPDATE 写了 18 个字段。

**为什么是问题？** 假设商家在支付回调的同一瞬间改了 `remark`（备注）：

```
时刻 T1: 支付回调 selectById → 拿到 remark='要筷子'
时刻 T2: 商家调接口改备注 → UPDATE orders SET remark='不要筷子' WHERE id=5
时刻 T3: 支付回调 UPDATE orders SET ..., remark='要筷子', ... WHERE id=5
        → 商家的修改被覆盖回旧值，凭空消失
```

**这叫"丢失更新"（Lost Update），是并发写全字段的必然代价。**

**修法同缺口 1**：只 `SET` 需要变的字段。

### 其他缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **先查后改非原子** | **高** | 并发下两次回调都成功，副作用重复 | 改条件更新 + 判 rows |
| **全字段 UPDATE** | 中 | 丢失更新风险 | 只 SET 三个字段 |
| **没有校验支付金额** | **高（钱相关）** | 传 `orderNumber` 就直接标记已支付，不校验"实付金额 = 订单金额" | 接真实支付时校验回调签名 + 金额 |
| **没有校验当前状态是否为"待付款"** | 中 | 已取消的订单也能被"支付"（`pay_status` 从 0 变 1，状态从 6 变 2） | 加 `status == PENDING_PAYMENT` 校验 |
| **没有回调签名验证** | **高（钱相关）** | `/notify` 接口谁都能调（不在拦截器范围），伪造一个请求就能把订单标记为已支付 | 验微信签名（`WechatPay-Signature`） |
| **WebSocket 推送在事务外** | 低 | 如果 `updateById` 之后、`sendToType` 之前抛异常，会回滚数据库但已经推送了 | 用 `TransactionSynchronization.afterCommit` 把推送挪到提交后 |

### 「没有校验当前状态」值得单独说

现在的逻辑只判 `pay_status`：

```java
if (order.getPayStatus() == PAID) return "duplicate";
// 直接往下改
```

**如果订单已经被取消（`status=6`，`pay_status=0` 因为取消时没退款），此时来一个支付回调会怎样？**

```
pay_status: 0 → 1
status:     6 → 2（待接单）
```

**一个已取消的订单"复活"了。** 用户取消订单后钱又被扣了一次，商家看到一张新订单。

**修法**：加前置状态校验

```java
if (!OrderStatusConstant.PENDING_PAYMENT.equals(order.getStatus())) {
    throw new BaseException("订单状态不允许支付");
}
```

**这类 bug 的根源是"用单一字段判断复合状态"**。判断"能不能支付"，要同时看 `status` 和 `pay_status`，不能只看一个。

### 「`/notify` 没有鉴权」是最严重的

`WebMvcConfiguration` 里拦截器只拦 `/admin/**` 和 `/user/**`，`PayNotifyController` 的路径是 `/notify/**`，**不在拦截范围**。

这意味着：

```bash
# 任何人不带任何 token
curl -X POST http://你的域名/notify/wechatPay -H "Content-Type: application/json" -d '{"orderNumber":"20261027223548518739"}'
```

**就能把一笔订单标记为"已支付"，白吃一顿。**

这个项目是模拟支付（没有真钱），所以问题不大。**但一旦接真实微信支付，这是致命漏洞。**

**真实微信支付的防护有三层：**

1. **验签**：请求头带 `WechatPay-Signature`，用平台证书公钥验签，确认真的是微信发的
2. **解密**：`resource` 字段是 AES-256-GCM 加密的，要解密才能拿到订单信息
3. **金额比对**：回调里的 `amount.total` 必须等于订单的 `amount`，不一致要报警

**面试如果聊到支付，"回调必须验签 + 验金额"是必备知识点。** 只说"我用状态机做了幂等"是半截答案。

---

## ⑧ 面试 30 秒版

> 支付幂等靠"状态机 + 唯一索引"两道防线。回调进来先用**订单号**查订单（不能用自增 id，第三方只知道订单号），如果 `pay_status` 已经是"已支付"，直接返回 `"duplicate"` —— 注意这会挡住后面所有副作用，包括改状态和推 WebSocket。我实测连打两次，第二次的 SQL 只有一条 `SELECT`，没有任何写操作，这是幂等的硬证据。
>
> 幂等标记必须存在数据库里，不能用内存 `Set` —— 内存重启就丢、多实例不共享。也不用 Redis，因为幂等标记必须和业务数据在同一个事务里才可靠，跨系统写会出现"Redis 成功了但库没写"的不一致。
>
> 重复请求返回 `"duplicate"` 而不是报错，因为对第三方回调来说"已处理过"也是成功；返回错误会导致无限重试。
>
> 这版有个并发缺口：**先查再改不是原子的**，两个回调同时读到未支付会都往下走。而且 `updateById` 传的是查出来的完整对象，会生成 18 个字段的全量 UPDATE，有丢失更新风险。正确解法是把状态塞进 WHERE：`UPDATE ... WHERE id=? AND pay_status=0`，一条 SQL 原子完成判断+更新，判影响行数就知道有没有被抢先。这一改同时解决了两个问题。
>
> 还有一个更重要的：`/notify` 接口在拦截器范围外，没有鉴权也没有验签，任何人伪造请求就能把订单标记为已支付。生产必须验微信签名 + 比对金额。
