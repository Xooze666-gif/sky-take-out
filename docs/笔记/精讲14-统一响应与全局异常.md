# 精讲 14 · 统一响应与全局异常：为什么你的接口全是 200

> 源码位置：`sky-common/result/Result.java`、`PageResult.java`、`sky-common/exception/*`、
> `sky-server/handler/GlobalExceptionHandler.java`、`sky-common/constant/MessageConstant.java`
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL/实测 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版
>
> **这一篇是全项目的"出口层"**。前面 13 篇讲的是"数据怎么进数据库"，这一篇讲"结果怎么出到浏览器"。
> 面试官问「你的接口返回格式怎么设计的」「全局异常怎么做的」「业务异常为什么不返回 500」，
> 答案全在这里。而且这一篇会实锤暴露一个**真 bug**：连 404 都被兜成了 200。

---

## ① 场景

任何一个请求打到后端，只有两条路出去：

```
                    ┌─ 正常：Controller return Result.success(data)
请求 ──► 拦截器 ──► ┤
                    └─ 异常：throw ──► GlobalExceptionHandler ──► Result.error(msg)
```

**共同点：不管走哪条，最终都是一个 JSON，HTTP 状态码都是 `200`。**

这不是偷懒，这是一个**明确的架构选择**，叫「HTTP 状态码守恒 + 业务状态码下移」。

### 项目里真正用到的 4 个返回形态

| 形态 | 长什么样 | 用在哪 |
|---|---|---|
| 成功无数据 | `{"code":1,"msg":null,"data":null}` | 新增、修改、删除 |
| 成功有数据 | `{"code":1,"msg":null,"data":{...}}` | 登录、查询、上传 |
| 成功分页 | `{"code":1,"msg":null,"data":{"total":5,"records":[...]}}` | 所有 `page` 接口 |
| 失败 | `{"code":0,"msg":"密码错误","data":null}` | 所有异常 |

**注意 `msg:null` 也会被序列化出来**（因为没有 `@JsonInclude(NON_NULL)`），所以成功响应里永远能看见 `"msg":null` 这个冗余字段。

## ② 数据：一次失败请求，四个层面分别发生了什么

以「用错误密码登录」为例：

| 层 | 值 | 谁决定的 |
|---|---|---|
| 数据库 | 查到 1 行 admin，**什么都没改** | `SELECT` 不写 |
| Java 抛出的异常 | `new PasswordErrorException("密码错误")` | `EmployeeServiceImpl.login` |
| Spring MVC 处理后 | 被 `@ExceptionHandler(BaseException.class)` 捕获 | `GlobalExceptionHandler` |
| HTTP 状态行 | **`HTTP/1.1 200`** | Spring 默认（handler 没返回 `ResponseEntity`） |
| HTTP 响应体 | `{"code":0,"msg":"密码错误","data":null}` | `Result.error()` |

**四个层面四个值，互相独立。** 面试时能把这四层分开说，就说明你真的理解了，不是背的。

## ③ 逐行拆

### 3.1 `Result<T>`：泛型 + 三个静态工厂

```java
public class Result<T> implements Serializable {
    private Integer code;   // 1 成功 / 0 失败
    private String  msg;    // 提示信息
    private T       data;   // 业务数据，泛型，类型由调用方决定
```

**为什么 `implements Serializable`？**

因为要能塞进 Redis（分布式 session）、能过 RPC（Dubbo/Feign）—— 那时候对象必须可序列化。
现在没用上，但这是「预留」而不是「多余」。

**`code` 为什么用 `Integer` 而不是 `int`？**

细节：用 `Integer`，`Result.success()` 里 code 不赋值就是 `null`，能暴露"忘记设 code"的错误；
用 `int` 默认是 `0`，看起来像失败，反而更容易掩盖问题。这里选了 `Integer` + 每个工厂都显式赋值。

```java
public static <T> Result<T> success() {
    Result<T> result = new Result<>();
    result.code = 1;
    return result;
}

public static <T> Result<T> success(T object) {   // 重载！
    Result<T> result = new Result<>();
    result.data = object;
    result.code = 1;
    return result;
}

public static <T> Result<T> error(String msg) {
    Result<T> result = new Result<>();
    result.msg = msg;
    result.code = 0;
    return result;
}
```

**为什么方法签名上的 `<T>` 必须在 `static` 后面？**

```java
public static <T> Result<T> success(T object)
//           ↑ 这个 <T> 是"方法级泛型参数"
```

静态方法**不能**用类上的 `<T>`（类泛型 `Result<T>` 是实例级别的，静态方法加载时还没确定 T）。
所以必须自己声明一个。这是 Java 泛型的硬规则，写错就编译不过：

```
error: non-static type variable T cannot be referenced from a static context
```

**为什么 `success()` 和 `success(T)` 能共存？**

方法重载看的是**参数列表**，不看返回值也不看泛型。
但有个坑：`Result.success(null)` 会走哪个？答案是走 `success(T)`（因为 `null` 能匹配 `T`，编译器优先选更具体的重载）。
所以项目里从不写 `Result.success(null)`，要空就写 `Result.success()`。

**`error` 为什么不提供 `error(Integer code, String msg)`？**

因为业务码只有 0/1 两种，加个 code 参数反而会让调用方纠结"我该传 1 还是 2"。**克制也是设计。**

### 3.2 `PageResult`：为什么不直接用 `Result<Page<T>>`

```java
public class PageResult implements Serializable {
    private long total;      // 总记录数（不是总页数！）
    private List<?> records; // 当前页数据
```

看 MyBatis-Plus 的 `Page<T>` 里有什么：

```java
Page<T> { records, total, size, current, pages, orders, optimizeCountSql, searchCount, ... }
```

它有 **9 个字段**，但前端只用到 2 个（`total` 算总页数，`records` 渲染表格）。
如果直接 `Result<Page<Employee>>`，JSON 会多出 `size/current/pages/orders/optimizeCountSql/searchCount` 六个无意义字段。

**所以手写一个 2 字段的 `PageResult` 做"裁剪"。** 这是"不要把自己的内部类型当 API 契约"的典型做法 —— 框架换了你不用改前端。

`records` 为什么是 `List<?>` 而不是 `List<T>`？

因为 `PageResult` 没有泛型参数。如果写成 `PageResult<T>`，那 `Result<PageResult<Employee>>` 的嵌套泛型会让每个 Controller 都在写泛型，收益极低。用通配符 `?` 换简洁，代价是取元素时要强转 —— 但 `PageResult` 只负责传输，不负责取值，所以代价为零。

### 3.3 异常体系：为什么全部继承 `RuntimeException`

```
RuntimeException
  └── BaseException                    ← 基类，只有一个 String msg
        ├── AccountNotFoundException   "账号不存在"
        ├── PasswordErrorException     "密码错误"
        ├── AccountLockedException     "账号被锁定"
        └── JwtException               "token 非法"
```

```java
public class BaseException extends RuntimeException {
    public BaseException() { }
    public BaseException(String msg) { super(msg); }
}
```

**为什么是 `RuntimeException` 而不是 `Exception`？** 三个理由，缺一不可：

| 理由 | 说明 |
|---|---|
| **事务能回滚** | Spring `@Transactional` 默认只对 `RuntimeException` 和 `Error` 回滚。如果继承 `Exception`，业务异常抛出来事务**不回滚**，脏数据留在库里 |
| **不污染签名** | `throws` 不用写，Service 层方法签名干净。`login()` 不需要 `throws PasswordErrorException` |
| **不强迫调用方 catch** | 业务异常是"流程分支"，不是"需要就地处理的技术故障"。让它在顶层被统一捕获才合理 |

**为什么还要单独定义 4 个子类，而不是全用 `new BaseException("账号不存在")`？**

因为**类型可以区分，字符串不能**。将来要加国际化（i18n）、要按异常类型做不同埋点、要在 `@ExceptionHandler` 里对不同类型做不同处理（比如 `JwtException` 返回 401），只有类型能扛住。字符串拼错了编译器不会告诉你。

### 3.4 `GlobalExceptionHandler`：三个 handler 的顺序是命门

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BaseException.class)          // ① 最具体
    public Result<String> handleBusinessException(BaseException ex) {
        log.warn("业务异常: {}", ex.getMessage());
        return Result.error(ex.getMessage());
    }

    @ExceptionHandler(DuplicateKeyException.class)  // ② 中间
    public Result<String> handleDuplicateKey(DuplicateKeyException ex) {
        // ... 从 "Duplicate entry 'wangwu' for key 'employee.idx_username'" 里截出 wangwu
        return Result.error(value + " 已存在");
    }

    @ExceptionHandler(Exception.class)              // ③ 最宽 → 兜底
    public Result<String> handleException(Exception ex) {
        log.error("系统异常", ex);
        return Result.error(MessageConstant.UNKNOWN_ERROR);
    }
}
```

**`@RestControllerAdvice` 是什么？**

`@ControllerAdvice` + `@ResponseBody` 的合体。`@ControllerAdvice` 让这个类的 `@ExceptionHandler`
对**所有** `@RestController` 生效（不用每个 Controller 都写 catch）；`@ResponseBody` 让返回值走
Jackson 序列化成 JSON，而不是当成视图名去找模板。

**Spring 到底怎么选中哪个 handler？**

`ExceptionHandlerExceptionResolver` 拿到异常后，遍历所有 handler 方法，按**异常类型在继承树上的距离**排序：
类型越接近（越具体）优先级越高。`PasswordErrorException` 同时是 `BaseException` 和 `Exception` 的子类，
但 `BaseException` 更近，所以走 ①。

**如果把 `Exception.class` 的 handler 写在最前面会怎样？**

**不影响**。Spring 不看方法声明顺序，看类型距离。这一点常被误解成"顺序很重要"，
实际是"**类型继承层级**决定优先级"，写在前面的 `Exception.class` 不会抢走 `BaseException`。
（真正常见的坑是**同一个异常类型被两个 `@ControllerAdvice` 都处理**，那时才比 `@Order`。）

### 3.5 唯一键冲突的消息提取（这段是整个 handler 里最巧的）

```java
if (message != null && message.contains("Duplicate entry")) {
    // 形如：Duplicate entry 'wangwu' for key 'employee.idx_username'
    int start = message.indexOf("Duplicate entry '");
    if (start >= 0) {
        int valueStart = start + "Duplicate entry '".length();
        int valueEnd = message.indexOf("'", valueStart);   // 找下一个单引号
        if (valueEnd > valueStart) {
            String value = message.substring(valueStart, valueEnd);
            return Result.error(value + " 已存在");        // → "wangwu 已存在"
        }
    }
}
return Result.error(MessageConstant.UNKNOWN_ERROR);
```

**为什么不直接 `return Result.error("用户名已存在")`？**

因为**同一个 handler 要服务所有表的唯一键**。`employee.username`、`orders.number`、
`address_book` 将来加唯一索引…… 每一处的提示语都不同。
从异常消息里把冲突的**值**抠出来，拼成 "xxx 已存在"，一份代码覆盖全部场景。

**这算不算好设计？** 算"够用"，不算"优雅"。更工程化的做法是：

```java
// 更稳的方案：解析索引名，映射到字段中文名
// Duplicate entry 'wangwu' for key 'employee.idx_username'
//                                    └─ 拿到 idx_username → 查映射表 → "用户名"
```

但那样要维护一张索引名→中文名的映射表，而且索引改名就崩。
**用值做提示**的好处是：不管哪张表，用户看到的是"他自己输入的那个东西重复了"，很直观。代价是**泄露了"这个值已被占用"**（撞库探测：攻击者能批量试用户名是否存在）。这是第 ⑦ 层要说的缺口。

**三层 `if` 嵌套为什么不用正则？**

```java
// 正则版（更短，但启动时要编译 Pattern，且遇到奇怪字符可能匹配失败）
Pattern.compile("Duplicate entry '(.+?)' for key").matcher(msg)
```

手写 `indexOf` + `substring` **零额外依赖、零编译成本、行为完全可预测**。
在这种"只解析固定格式"的场景，手写反而更可控。这是个可以拿去面试讲的权衡点。

## ④ SQL / 实测：这一篇的实验全部可复现

**环境**：`general_log` 已开，应用跑在 8080，MySQL 8.0。

### 4.1 四种登录结果，HTTP 状态码全是 200

```bash
B=http://localhost:8080
curl -s -w "\n[HTTP %{http_code}]\n" -X POST $B/admin/employee/login \
  -H "Content-Type: application/json" -d '{"username":"admin","password":"123456"}'
```

| 场景 | 响应体 | HTTP |
|---|---|---|
| 正确密码 | `{"code":1,"msg":null,"data":{"id":1,"userName":"admin","name":"管理员","token":"eyJhbGciOiJIUzI1NiIs..."}}` | **200** |
| 错误密码 | `{"code":0,"msg":"密码错误","data":null}` | **200** |
| 账号不存在 | `{"code":0,"msg":"账号不存在","data":null}` | **200** |
| 账号被锁定 | `{"code":0,"msg":"账号被锁定","data":null}` | **200** |

**四次请求在 `general_log` 里长这样（一模一样的 SQL，一模一样失败在 Java 侧）：**

```
2026-10-27 23:00:09.986  SELECT id,name,username,password,phone,sex,id_number,status,create_time,update_time,create_user,update_user
                          FROM employee WHERE (username = 'admin')
2026-10-27 23:00:10.308  SELECT ... FROM employee WHERE (username = 'admin')        ← 密码错，多查一次
2026-10-27 23:00:10.566  SELECT ... FROM employee WHERE (username = 'nobody_here')  ← 查不到 → 抛异常
2026-10-27 23:00:10.827  SELECT ... FROM employee WHERE (username = 'test_precision') ← status=0 → 抛异常
```

**关键观察：数据库完全不区分这四种情况，它只执行了一条按 username 查的 SELECT。**
四种结果的分歧全部发生在 Java 内存里。这就是精讲 04 说的"密码不在 SQL 里比"的直接物证 —— 顺便也证明了**响应层的差异不来自数据库，只来自异常处理层**。

### 4.2 唯一键冲突：原始报错长什么样

先看索引（这是唯一键能生效的前提）：

```sql
mysql> SHOW INDEX FROM sky_take_out.employee;
Key_name        Column_name   Non_unique   Index_type
PRIMARY         id            0            BTREE
idx_username    username      0            BTREE          ← Non_unique=0 就是唯一索引
```

直接复现原始报错：

```sql
mysql> INSERT INTO employee(name,username,password,phone,sex,id_number,status)
       VALUES('test','wangwu','x','1','1','1',1);
ERROR 1062 (23000): Duplicate entry 'wangwu' for key 'employee.idx_username'
       └─ SQLSTATE 23000 = 完整性约束违反
                     └─ 注意 key 是 'employee.idx_username'，带表名前缀
```

走接口的结果：

```bash
curl -s -X POST $B/admin/employee -H "Content-Type: application/json" -H "token: $TOKEN" \
  -d '{"username":"wangwu","name":"王五","phone":"13800138000","sex":"1","idNumber":"110101199001011234"}'
# → {"code":0,"msg":"wangwu 已存在","data":null}   [HTTP 200]
```

`wangwu` 这个字符串**就是从上面那条 MySQL 报错里 `substring` 出来的**。

**同时看这条 INSERT（它执行了，但没写入）：**

```
2026-10-27 23:00:16.786  INSERT INTO employee ( name, username, password, phone, sex, id_number, status, create_time, update_time, create_user, update_user )
                         VALUES ( '王五', 'wangwu', 'e10adc3949ba59abbe56e057f20f883e', '13800138000', '1', '110101199001011234', 1,
                                  '2026-10-27 23:00:16.778853', '2026-10-27 23:00:16.778853', 1, 1 )
```

**这条 SQL 出现在日志里，说明它真的发给了数据库；但表里没有多出一行，说明数据库在执行阶段拒绝了它。**
这正是"**先让数据库兜底，再让 Java 解释错误**"的顺序 —— 而不是"先 SELECT 一次看看重不重名，再 INSERT"（那样有 TOCTOU 竞态，见精讲 07）。

### 4.3 兜底 handler 把四种标准异常全吃了（实测，这是本篇最重要的证据）

```bash
# ① 缺请求体：PUT /admin/order/confirm 需要 @RequestBody Orders，但不传
curl -X PUT "$B/admin/order/confirm?id=4" -H "token: $TOKEN"
# → {"code":0,"msg":"未知错误","data":null}  [HTTP 200]

# ② 路径不存在
curl "$B/admin/not-exist-xxx" -H "token: $TOKEN"
# → {"code":0,"msg":"未知错误","data":null}  [HTTP 200]

# ③ 方法不支持
curl -X DELETE "$B/admin/employee/login" -H "token: $TOKEN"
# → {"code":0,"msg":"未知错误","data":null}  [HTTP 200]

# ④ 参数类型错：pageSize=abc 但声明是 int
curl "$B/admin/employee/page?page=1&pageSize=abc" -H "token: $TOKEN"
# → {"code":0,"msg":"未知错误","data":null}  [HTTP 200]
```

应用日志里对应打印的**真实异常类名**：

```
org.springframework.web.servlet.resource.NoResourceFoundException: No static resource admin/not-exist-xxx.
org.springframework.web.HttpRequestMethodNotSupportedException: Request method 'DELETE' is not supported
```

（另外两个是 `HttpMessageNotReadableException` 和 `MethodArgumentTypeMismatchException`，
因为 `log.error("系统异常", ex)` 打了堆栈，日志里能看到完整 cause chain。）

**四个都掉进了 `@ExceptionHandler(Exception.class)`。** 因为它们都是 `Exception` 的子类，
而项目里没有为它们写专门的 handler。

### 4.4 最离谱的一个：`/images/` 找不到图片也返回 200 + JSON

```bash
curl -s "$B/images/not-exist.png"
# → {"code":0,"msg":"未知错误","data":null}   [HTTP 200] [Content-Type: application/json]
```

对比正常的：

```bash
curl -s -D - -o /dev/null "$B/images/9fadc5538bde41af8f53c80e2a6732b4.png"
# HTTP/1.1 200
# Content-Type: image/png
```

**一个 `<img src="/images/xxx.png">` 加载失败时，浏览器收到的不是 404，而是一段 JSON。**
图片裂了，控制台还看不到 404 —— 排查时会非常困惑。这是第 ⑦ 层的缺口 1。

## ⑤ 权衡：为什么"全是 200"是个合理选择

### 5.1 两种流派的对比

| | **本项目：全 200 + body.code** | **REST 正统：用 HTTP 状态码** |
|---|---|---|
| 成功 | 200/`code:1` | 200 |
| 参数错 | 200/`code:0` | 400 |
| 未登录 | 200/`code:0` | 401 |
| 无权限 | 200/`code:0` | 403 |
| 不存在 | 200/`code:0` | 404 |
| 冲突 | 200/`code:0` | 409 |
| 服务错 | 200/`code:0` | 500 |
| 前端判断 | `if (res.code === 1)` | `if (res.status >= 200 && res.status < 300)` + 拦截器处理 401 |
| 网关/CDN 缓存 | 一个 URL 只有一种状态，**缓存友好** | 要区分缓存策略 |
| 监控告警 | **坏了也不报警**（全是 200） | 5xx 直接触发告警 |
| 浏览器行为 | 不会弹"页面找不到" | 404/500 可能被浏览器/代理美化页劫持 |

**为什么国内这套（全 200）流行？**

三个现实原因：

1. **前端统一拦截器只写一次**。axios 的 `response` 拦截器里 `if (code !== 1) ElMessage.error(msg)`，
   `error` 拦截器只处理真正的网络故障。不用为每个状态码写分支。
2. **不怕运营商/代理劫持 404/500 页面**。早年 4xx/5xx 会被插入广告页，全 200 就绕开了。
3. **历史惯性**。早期 JSP/Struts 时代就这样，团队习惯延续下来了。

**为什么 REST 正统更好？** 因为 HTTP 状态码是**给基础设施看的**（网关、负载均衡、监控、缓存、重试策略），
body 里的 code 是**给业务代码看的**。混在一起，基础设施就瞎了 —— 这正是缺口 2。

### 5.2 那为什么还留 `msg:null`？

因为没加 `@JsonInclude(JsonInclude.Include.NON_NULL)`。
加上它，成功响应会从 `{"code":1,"msg":null,"data":{...}}` 变成 `{"code":1,"data":{...}}`，省 12 字节/请求。

**为什么没加？** 因为前端写的是 `if (res.msg) alert(res.msg)`，`msg` 字段必须**存在**（哪怕是 null），
否则 `res.msg` 是 `undefined`，某些老代码 `res.msg.length` 会直接抛错。
这是"为了前端省事，牺牲一点带宽"的取舍。

### 5.3 `MessageConstant` 为什么要抽常量类

```java
public static final String PASSWORD_ERROR = "密码错误";
public static final String UNKNOWN_ERROR  = "未知错误";
```

不用常量类的话，`"密码错误"` 会在 Service 层、handler 层、测试里各写一遍，改一个字要全局搜。
抽出来之后只有一处定义。

**但这仍然是硬编码。** 真正的国际化方案是 `MessageSource` + `messages_zh_CN.properties`：

```properties
error.password=密码错误
```

```java
throw new PasswordErrorException(messageSource.getMessage("error.password", null, locale));
```

**为什么本项目没做？** 因为苍穹外卖是单语言项目，引入 `MessageSource` 只会增加复杂度。
但面试被问"你的错误提示怎么支持多语言"，你要能答出上面这条路 —— **"知道更好的做法，但因为场景不需要而选了简单的"**，
这个回答比"我用了常量类所以很好"高一个层次。

## ⑥ 踩坑

### 坑 1：`@ExceptionHandler(SQLIntegrityConstraintViolationException.class)` 完全不生效

**当时的写法：**

```java
import java.sql.SQLIntegrityConstraintViolationException;

@ExceptionHandler(SQLIntegrityConstraintViolationException.class)
public Result<String> handleDuplicateKey(SQLIntegrityConstraintViolationException ex) { ... }
```

**结果**：新增重名员工时，前端收到的是 `{"code":0,"msg":"未知错误"}`，而不是期望的提示。
断点根本没进这个方法。

**排查过程：**

1. 先确认异常确实抛了 —— 在 `handleException` 里打断点，进来了，`ex.getClass()` 是
   `org.springframework.dao.DuplicateKeyException`。
2. 才明白：**Spring 在 JDBC 层之上做了一次异常翻译**。

**翻译链路是这样的：**

```
MySQL 服务端  →  ERROR 1062 (SQLSTATE 23000)
    ↓  JDBC 驱动
java.sql.SQLIntegrityConstraintViolationException
    ↓  MyBatis 的 SpringManagedTransaction / SqlSessionTemplate
    ↓  MyBatisExceptionTranslator
    ↓  SQLErrorCodeSQLExceptionTranslator.doTranslate()
       （查 sql-error-codes.xml：1062 → DuplicateKeyException）
org.springframework.dao.DuplicateKeyException     ← 最终到你这儿的类型
```

**所以 `@ExceptionHandler` 要写 Spring 的 DAO 异常体系，不是 JDBC 的。**

`DuplicateKeyException` 的继承链：

```
RuntimeException
  └─ DataAccessException
       └─ NonTransientDataAccessException
            └─ DataIntegrityViolationException
                 └─ DuplicateKeyException
```

**这条坑的通用教训**：`@ExceptionHandler` 要匹配的类型，是**异常穿过所有框架层之后到达 Controller 时的类型**，
不是它最原始的类型。凡是经过 Spring 封装的（JDBC、`RestTemplate`、`@Valid` 校验），都要先想"它会被翻译成什么"。

### 坑 2：`PUT /admin/order/confirm?id=5` 报 `Required request body is missing`，前端只看到"未知错误"

**现象**：用例是"商家接单"，接口声明是

```java
@PutMapping("/confirm")
public Result confirm(@RequestBody Orders orders) { ... }
```

用 `curl -X PUT ".../confirm?id=5"` 打过去，返回"未知错误"。**完全没有提示说"你少传了 body"。**

**为什么？** 因为 `HttpMessageNotReadableException` 没有专门的 handler，掉进了 `Exception` 兜底 →
`Result.error("未知错误")`。真正的根因被吞了。

**怎么定位的**：去应用日志里翻 `log.error("系统异常", ex)` 打的堆栈，才看到
`HttpMessageNotReadableException: Required request body is missing`。

**教训**：**兜底 handler 必须是最后一道网，不能是唯一一道网。**
凡是"参数/格式/路由"这类**客户端错误**，都应该有独立的 handler，返回能指导前端修正的消息。
现在还留着这个缺口（第 ⑦ 层缺口 2）。

### 坑 3：日志里的中文是乱的 —— `ÏµÍ³Òì³£`

`log.error("系统异常", ex)` 在 Windows CMD 里输出成 `ÏµÍ³Òì³£`。

**根因**：JVM 默认用系统编码（GBK，`file.encoding=GBK`）把中文转成字节写进 stdout，
但 CMD 窗口按 UTF-8 解码（或反过来）。**纯粹是终端编码问题，不影响业务。**

**为什么值得记一笔**：因为排查 bug 时你是靠日志的。日志看不懂，整个排查就瘫痪了。
本项目**没改**它（`-Dfile.encoding=UTF-8` 属于启动参数，改不改都能跑），
但这是"报警系统本身坏了"的典型案例 —— **可观测性也是功能**。

## ⑦ 缺口：这一篇实测出了 3 个真问题

### 缺口 1（最严重）：兜底 `Exception` handle 把 404/405/400 全兜成 200 + "未知错误"

**实测证据**（4.3 / 4.4 节）：路径不存在、方法不支持、缺 body、参数类型错、**静态图片不存在**，
五种情况全部返回 `{"code":0,"msg":"未知错误"}` + `HTTP 200`。

**为什么这是真问题？**

| 受害方 | 后果 |
|---|---|
| **前端** | 接口路径拼错了，收到的提示是"未知错误"，会去查后端是不是挂了，浪费半天 |
| **监控** | 所有请求都是 200，5xx 报警规则永不触发。服务真的挂了才知道 |
| **网关/负载均衡** | 无法基于状态码做熔断、重试、灰度 |
| **CDN** | `/images/not-exist.png` 返回 200 + JSON，会被当成功缓存住（缓存"污染"） |
| **浏览器** | 图片裂了但没有 404，`onerror` 事件拿不到有意义的信息 |
| **SEO/爬虫** | 不存在的页面返回 200，被判"大量重复内容"（这个项目没页面，但同类设计会踩） |

**怎么改（三步，按优先级）：**

```java
// 第一步：给客户端错误单独开 handler，返回真实语义
@ExceptionHandler({
        NoResourceFoundException.class,           // 404 静态资源
        NoHandlerFoundException.class,            // 404 接口
        HttpRequestMethodNotSupportedException.class, // 405
        HttpMessageNotReadableException.class,    // 400 请求体不合法
        MethodArgumentTypeMismatchException.class,// 400 参数类型错
        MissingServletRequestParameterException.class // 400 缺参数
})
public ResponseEntity<Result<String>> handleClientError(Exception ex) {
    log.warn("客户端请求错误: {} - {}", ex.getClass().getSimpleName(), ex.getMessage());
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(Result.error("请求参数或路径不正确"));
}
```

**注意要返回 `ResponseEntity` 才能改状态码。** 直接 `return Result.error(...)` 永远是 200 ——
这是"全 200"设计的本质：handler 的返回值只决定 body，不碰状态行。

```java
// 第二步：给业务异常选一个合适的状态码（如果真的想保留全 200，就跳过这步）
@ExceptionHandler(BaseException.class)
public ResponseEntity<Result<String>> handleBusinessException(BaseException ex) {
    // 业务异常是"请求合法但业务规则不允许" → 422 或 200 都可以，看团队约定
    return ResponseEntity.ok(Result.error(ex.getMessage()));
}
```

```java
// 第三步（可选）：兜底也返回 500，让监控能看见
@ExceptionHandler(Exception.class)
public ResponseEntity<Result<String>> handleException(Exception ex) {
    log.error("系统异常", ex);
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(Result.error(MessageConstant.UNKNOWN_ERROR));
}
```

**面试怎么说这个缺口：**

> "我的全局异常处理器只有一个 `Exception` 兜底，结果把 404、405、参数绑定失败全兜成了
> 200 + '未知错误'。这是我自己测出来的 —— 用 `curl` 打一个不存在的路径，返回的是 200 加一段 JSON。
> 后果是监控看不到 5xx，前端也分不清是路径写错还是服务挂了。改法是把客户端错误单独拎出来，
> 用 `ResponseEntity` 返回真实状态码，兜底那个改成 500。"
>
> **这段话的价值在于：它证明你会自己找自己的问题，而不是等面试官指出来。**

### 缺口 2：唯一键冲突的消息把"值已存在"泄露给了攻击者

`{"msg":"wangwu 已存在"}` —— 攻击者可以批量调 `POST /admin/employee`（需要 token，但内部人员/泄露的 token 都能用），
根据返回是"xxx 已存在"还是成功，**枚举出系统里所有的用户名**。

**这是"用户枚举"（User Enumeration）漏洞。** 登录接口同理：返回"账号不存在"和"密码错误"的**区别**，
就已经告诉攻击者"这个账号存在"了。

**正确做法**：登录失败统一返回"用户名或密码错误"；注册/新增重复时返回"信息校验失败，请更换后重试"
（或者干脆走异步校验，不即时反馈）。

**这是教科书级的反面案例 —— 而这个项目恰好两条都踩了**：

| 接口 | 当前提示 | 泄露了什么 |
|---|---|---|
| `POST /admin/employee/login` | "账号不存在" / "密码错误" 分开 | 用户名是否存在 |
| `POST /admin/employee` | "wangwu 已存在" | 用户名是否被占用 |

**面试可以主动说**："我知道这块有用户枚举的问题，登录应该合并成'用户名或密码错误'。
当时是为了方便调试才分开的，生产环境要合上。" —— **主动认领比被问出来强**。

### 缺口 3：`Result` 没有 `traceId`，出问题无法定位

线上用户截图过来说"报错了"，你问"什么错"，他说"未知错误"。你去日志里搜"未知错误"，
一下午几千条，**根本不知道是哪一条**。

**改法**：加一个 `traceId`（`MDC` + `UUID`），在 `Result` 里带出去：

```java
// 拦截器 or Filter 里
MDC.put("traceId", UUID.randomUUID().toString().replace("-", "").substring(0, 16));

// Result 里加字段
private String traceId = MDC.get("traceId");
```

用户把 `traceId` 报给你，`grep traceId` 一条就定位。
**这是生产系统的基本素养**，课程项目不做但你要知道。

## ⑧ 面试 30 秒版

> **问：你的接口返回格式怎么设计的？**
>
> "统一用 `Result<T>`，三个字段：`code`（1 成功 / 0 失败）、`msg`、`data`（泛型）。
> 分页单独用 `PageResult`，只有 `total` 和 `records` 两个字段 —— 因为 MyBatis-Plus 的 `Page`
> 有 9 个字段，直接返回会把内部结构暴露成 API 契约，框架一升级前端就崩。
>
> 所有返回的 HTTP 状态码都是 200，业务成败看 body 里的 `code`。这样前端只需在拦截器里
> 写一次 `if (code !== 1)`，不用为每个状态码写分支。代价是监控看不到 5xx —— **这个我知道是取舍。**"
>
> **问：全局异常怎么做的？**
>
> "`@RestControllerAdvice` + 三个 `@ExceptionHandler`：`BaseException` 处理业务异常、
> `DuplicateKeyException` 处理唯一键冲突、`Exception` 兜底。
> 业务异常继承 `RuntimeException` 而不是 `Exception`，因为 `@Transactional` 默认只对
> `RuntimeException` 回滚，继承 `Exception` 会导致异常抛出但事务不回滚。
>
> 唯一键冲突那块做了个细节：从 MySQL 的 `Duplicate entry 'wangwu' for key 'employee.idx_username'`
> 里把冲突的值 `substring` 出来，拼成 'wangwu 已存在'，这样一份代码能覆盖所有表的唯一键。
>
> **这里我踩过一个坑**：一开始 catch 的是 `SQLIntegrityConstraintViolationException`，
> 死活不生效。后来发现 Spring 在 DAO 层用 `SQLErrorCodeSQLExceptionTranslator` 把 SQLSTATE 23000
> 翻译成了 `DuplicateKeyException`，所以 `@ExceptionHandler` 要写 Spring 的异常类型，不是 JDBC 的。"
>
> **问：你的异常处理有什么问题？**（这题最容易被追问）
>
> "实测发现一个真问题：`Exception` 兜底把 404、405、参数绑定失败全兜成了 200 + '未知错误'。
> 我用 `curl` 打一个不存在的路径，返回的是 200 加 JSON，静态图片找不到也是。
> 后果是监控看不到 5xx、前端分不清是路径写错还是服务挂了。
> 改法是把客户端错误单独拎出来，用 `ResponseEntity` 返回 400/404/405，兜底那个改成 500。
>
> 另外一个隐患是登录返回'账号不存在'和'密码错误'两种提示，相当于告诉攻击者账号是否存在，
> 这是用户枚举漏洞，生产环境要合并成'用户名或密码错误'。"
