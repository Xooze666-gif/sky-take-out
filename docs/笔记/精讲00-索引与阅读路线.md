## 四、怎么验证我说的是真的（自己动手）

**这套笔记里的 SQL 全部来自 `general_log` 实抓，你可以自己复现。**

### 抓 SQL 的标准流程

```bash
MY="E:/env/mysql-8.0/bin/mysql.exe"

# ① 开日志
"$MY" -uroot -p123456 -e "SET GLOBAL log_output='TABLE'; SET GLOBAL general_log=ON; TRUNCATE TABLE mysql.general_log;"

# ② 启动应用
cd "E:/project/sky-take-out/sky-server/target"
unset SERVER__PORT && /e/env/jdk-17/bin/java -jar sky-server-1.0-SNAPSHOT.jar --server.port=8080

# ③ 打请求（以登录为例）
curl -s -X POST http://localhost:8080/admin/employee/login \
  -H "Content-Type: application/json" -d '{"username":"admin","password":"123456"}'

# ④ 看 SQL
"$MY" -uroot -p123456 --default-character-set=utf8mb4 -e \
"SELECT argument FROM mysql.general_log
 WHERE command_type='Query'
   AND argument NOT LIKE '%general_log%'
   AND argument NOT LIKE '%version%'
 ORDER BY event_time"

# ⑤ 关日志（重要，别留着）
"$MY" -uroot -p123456 -e "SET GLOBAL general_log=OFF; TRUNCATE TABLE mysql.general_log;"
```

### 三个必须注意的细节

1. **`--default-character-set=utf8mb4`**：不加的话中文会显示成 `??` 或乱码。
2. **过滤掉 `general_log` 和 `version` 关键字**：否则你会看到"查日志表本身"和"版本探测"的噪音。
3. **`@@session.transaction_read_only` 不是业务 SQL**：它是 MySQL 驱动在事务内做的连接状态检查。**但它有诊断价值** —— 看到它夹在两条 SQL 中间，说明这两条在同一个事务里。

### 怎么判断"事务生效了"

```sql
SET autocommit=0        ← 事务开始
... 业务 SQL ...
commit                  ← 正常结束
SET autocommit=1

或

SET autocommit=0
... 业务 SQL ...
rollback                ← 抛异常回滚
SET autocommit=1
```

**没有 `SET autocommit=0` 就说明这个方法没加 `@Transactional`。** 精讲 07 的"起售校验没有事务"就是这么发现的。

### 怎么验证幂等

```
同一个请求连打两次 → 对比两次的 SQL → 第二次必须没有写操作
```

精讲 03 的"第 2 次支付只有 SELECT"就是这么来的。

### 怎么验证 WebSocket（SQL 抓不到）

```bash
cd E:/project/sky-take-out/docs
node _ws_test.js      # 同时连 type=1 和 type=2
node _ws_pay.js       # 只连 type=1，测来单推送
```

然后在另一个窗口触发催单/支付，看终端输出。

### 关于 Redis（重要，别跳过）

**当前状态：没有写代码，所以没有精讲。**

原因：本机没装 Redis（Windows 装它比较折腾），所以幂等和购物车都用了"数据库 + 状态机"的纯 DB 方案。

**这个决定在面试里怎么讲？**

> 我没用 Redis，不是因为不会，而是因为**在这个场景下数据库方案更可靠**：幂等标记必须和业务数据在同一个事务里，跨系统写 Redis 会出现"Redis 成功但库回滚"的不一致。外卖的单笔订单只关心自己，MySQL 行锁完全够用。如果是"全局库存扣减"这种跨资源互斥，才需要分布式锁。

**这个回答比"我用了 Redis 做幂等"更难被追问倒。**

**如果还是想补这个模块**（能让简历技术栈更完整），设计方案见 `Day19`~`Day21`：缓存热菜列表、店铺营业状态、购物车。但**需要先自己装 Redis**（Windows 解压版或 Docker），AI 不代装软件。

## 六、怎么用这套笔记（具体动作）

### 每天 60 分钟的分配

| 时间 | 做什么 |
|---|---|
| 10 分钟 | 打开 `DayXX` 文件，看今天该读哪篇精讲 |
| 30 分钟 | 读精讲对应章节（**不要一次读完一篇，按 ①→⑧ 顺序读，每层停一下想想**） |
| 15 分钟 | **打开 IDEA 对照源码**，找到讲的每一行（这一步不能省，光看笔记记不住） |
| 5 分钟 | 合上笔记，**用自己的话口述 ⑧ 面试 30 秒版**，卡住的地方标出来 |

### 读每一篇的正确姿势

**不要"读一遍觉得懂了"就过。** 判断标准是这三个问题能答上来：

1. **这个方法被什么动作触发？**（① 场景）
2. **执行完数据库里哪几个字段变了？**（② 数据）
3. **如果删掉某一行会发生什么？**（③ 逐行）

答不上第 3 个，说明只是"看懂了字面"，没理解因果。

### 每篇的"⑦ 缺口"要重点记

**面试的分水岭在这里。** 能说出"这段代码有什么问题"的人，一定是自己写过、调过、想过的人；只会复述"我用了 XX 技术"的人，一问就穿。

**建议做法**：每篇读完，把 ⑦ 里的缺口抄成一句自己的话，攒成一个"**我知道的问题清单**"。面试时主动抛出一两个，效果远好于被问出来。
