# 精讲 15 · 启动流程与三大配置类：那 3.177 秒里发生了什么

> 源码位置：`SkyApplication.java`、`config/MybatisPlusConfiguration.java`、
> `config/WebMvcConfiguration.java`、`config/WebSocketConfiguration.java`、
> `resources/application.yml`、三个模块的 `pom.xml`、`HealthController.java`
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ 实测 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版
>
> **这是唯一一篇"不处理业务"的精讲。** 但它解释了一件事：
> **为什么你写的 `@Autowired EmployeeMapper` 能用、为什么 `/images/xxx.png` 能访问、
> 为什么分页会自动加 `LIMIT`、为什么 WebSocket 能连上。** 这些全是"配置类 + 自动装配"在背后干活。
> 面试问"Spring Boot 自动装配原理"、"你的项目怎么分层"，答案在这里。

## ① 场景：`java -jar` 之后

```bash
cd sky-server/target
java -jar sky-server-1.0-SNAPSHOT.jar --server.port=8080
```

你敲下这行命令后的 **3.177 秒**，JVM 做了这些事（顺序严格，改不了）：

```
① main() 启动
    └─ SpringApplication.run(SkyApplication.class, args)
② 创建 ApplicationContext（这里是 ServletWebServerApplicationContext）
③ 读 application.yml（+ 命令行参数 --server.port=8080 覆盖 yml）
④ 扫包：@SpringBootApplication 里的 @ComponentScan → com.sky 及其子包
    └─ 找到 3 个 @Configuration、11 个 @RestController、9 个 @Service、11 个 Mapper
⑤ 自动装配：从 spring.factories 加载 ~140 个 AutoConfiguration
    └─ 其中 DataSourceAutoConfiguration → 创建 HikariDataSource
    └─ 其中 MybatisPlusAutoConfiguration → 注册 SqlSessionFactory
    └─ 其中 ServletWebServerFactoryAutoConfiguration → 创建 Tomcat 10.1.20
⑥ 启动内嵌 Tomcat，绑定 8080
⑦ 执行 WebMvcConfiguration.addInterceptors() → 注册两个 JWT 拦截器
⑧ 执行 WebMvcConfiguration.addResourceHandlers() → /images/** → 本地目录
⑨ ServerEndpointExporter 扫描 @ServerEndpoint → 注册 /ws/{type}
⑩ 打印 "Started SkyApplication in 3.177 seconds"
```

**这 10 步是本篇的主线。** 下面一层层拆开。

## ③ 逐行拆

### 3.1 启动类：三行代码，四个注解

```java
@SpringBootApplication          // ① 三合一复合注解
@MapperScan("com.sky.mapper")   // ② 扫描 MyBatis 接口
public class SkyApplication {
    public static void main(String[] args) {
        SpringApplication.run(SkyApplication.class, args);   // ③ 一行启动
    }
}
```

#### `@SpringBootApplication` 拆开是三个注解

```java
@SpringBootConfiguration   // = @Configuration，说明这是个配置类
@EnableAutoConfiguration   // 核心！触发自动装配
@ComponentScan             // 扫 com.sky 及子包（默认扫启动类所在包）
public @interface SpringBootApplication { ... }
```

**`@EnableAutoConfiguration` 到底做了什么？**

它 `@Import(AutoConfigurationImportSelector.class)`。这个 selector 会：

```
① 读 classpath 下所有 jar 的
   META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
   （Boot 2.7 之前是 spring.factories，3.x 改成这个新文件）
② 拿到 ~140 个 xxxAutoConfiguration 全限定名
③ 逐个过 @Conditional 系列注解筛（@ConditionalOnClass / @ConditionalOnMissingBean / @ConditionalOnProperty）
④ 通过的才注册成 Bean
```

**这就是"约定优于配置"的物理实现。** 你只写了 `spring-boot-starter-web` 这个依赖，
Boot 就自动给你配好了 Tomcat + DispatcherServlet + Jackson + 静态资源映射，因为你**没有自己定义**它们
（`@ConditionalOnMissingBean` 判断的）。

**为什么这个项目 Boot 版本是 3.2.5 而不是官方的 2.7.x？**

| | Boot 2.7 | Boot 3.2.5（本项目） |
|---|---|---|
| JDK | 8/11 | **17+（强制）** |
| Servlet API | `javax.servlet.*` | **`jakarta.servlet.*`** |
| Tomcat | 9.x | **10.1.20** |
| Spring | 5.3 | **6.1.6** |
| MyBatis-Plus | `mybatis-plus-boot-starter` | **`mybatis-plus-spring-boot3-starter`** |

选 3.2.5 的理由：**JDK17 + Boot3 是 2024 年之后招聘 JD 里的主流写法**，而且本地仓库正好有这个版本。
代价是所有 `javax.*` 的 import 必须改成 `jakarta.*`（第 ⑥ 层踩坑 1 就是这个）。

#### `@MapperScan("com.sky.mapper")` 做了什么

MyBatis 的 Mapper 是**接口**，没有实现类。能 `@Autowired` 进来，靠的是**动态代理**：

```
@MapperScan("com.sky.mapper")
    ↓ 注册 MapperScannerConfigurer
    ↓ ClassPathMapperScanner.doScan("com.sky.mapper")
    ↓ 对包下每个接口生成一个 MapperFactoryBean
    ↓ getObject() 返回 JDK 动态代理（Proxy.newProxyInstance）
    ↓ 代理的 InvocationHandler 是 MapperProxy
    ↓ 你调 employeeMapper.selectOne(wrapper)
    ↓ MapperProxy 根据【接口全名 + 方法名】找到 MappedStatement
    ↓ 执行 SQL，把 ResultSet 映射成 Employee
```

**关键点：Mapper 接口的方法名和 XML 的 `id` 必须能对上。**
`EmployeeMapper extends BaseMapper<Employee>` 没写 XML 也能用，是因为 `BaseMapper` 的
`selectOne/insert/updateById` 等方法由 MP 在启动时**动态注入 MappedStatement**
（`ISqlInjector` 干的活），SQL 是根据实体的 `@TableName`/`@TableId`/字段名拼出来的。

#### 为什么 `main` 里只有一行，却能启动整个应用

```java
SpringApplication.run(SkyApplication.class, args);
```

这行的内部（简化）：

```java
public static ConfigurableApplicationContext run(Class<?> primarySource, String... args) {
    return new SpringApplication(primarySource).run(args);
}
// new SpringApplication():
//   ① 推断应用类型 → SERVLET（因为 classpath 有 spring-webmvc）
//   ② 加载 ApplicationContextInitializer / ApplicationListener（从 spring.factories）
//   ③ 推断 main 类
// run():
//   ① 发布 ApplicationStartingEvent
//   ② 准备 Environment（读 yml / 环境变量 / 命令行参数，优先级从低到高）
//   ③ 创建 ApplicationContext
//   ④ refresh() ← 这就是整个 Spring 启动的核心，13 个步骤
//   ⑤ 发布 ApplicationStartedEvent / ApplicationReadyEvent
```

**`--server.port=8080` 为什么能覆盖 `application.yml` 里的 8080？**

Spring 的 `PropertySource` 有严格优先级（高 → 低）：

```
命令行参数  --server.port=8080          ← 最高
   ↓
Java 系统属性  -Dserver.port=8080
   ↓
OS 环境变量  SERVER_PORT（注意：下划线形式）
   ↓
application-{profile}.yml
   ↓
application.yml                          ← 本项目写在这里
   ↓
@PropertySource
   ↓
默认值（SpringApplication.setDefaultProperties）
```

**这就是精讲里一直强调"启动时必须 `unset SERVER__PORT`"的原因** ——
环境变量 `SERVER__PORT`（双下划线是 Boot 对 `.` 的宽松绑定写法）会**打败** `application.yml`，
导致你以为改了端口其实没改。这个坑在第 ⑥ 层踩坑 4。

### 3.2 `application.yml`：六个配置块，每一块都对应一个自动配置类

```yaml

  servlet:
    context-path: /            # ① 全局路径前缀，Tomcat 的 contextPath

spring:
  application:

  servlet:
    multipart:
      max-file-size: 10MB      # ③ 单个文件上限
      max-request-size: 10MB   # ④ 整个请求上限（多文件时按总和算）
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/sky_take_out?serverTimezone=Asia/Shanghai&...
    username: root
    password: "123456"
    hikari:
      maximum-pool-size: 10    # ⑤ 连接池上限
      minimum-idle: 2          # ⑥ 最小空闲（= 启动后常驻连接数）

    user-ttl: 604800000
    user-token-name: authentication
  file:
    upload-dir: E:/project/sky-take-out/upload
```

**逐条说几个容易忽略的：**

**③④ `max-file-size` vs `max-request-size`**
- `max-file-size` 管**单个** part
- `max-request-size` 管**整个** `multipart/form-data` 请求体
- 两个都设 10MB → 传一个 9MB 的文件 OK；传两个 6MB 的文件（共 12MB）**失败**（超 request 限）

**⑦ `map-underscore-to-camel-case: true`**
数据库是 `id_number`，Java 是 `idNumber`。开了这个，MyBatis 自动把 `id_number` 映射到 `idNumber`。
**不开会怎样**：所有下划线字段全是 `null`，而且不报错 —— 这种坑最难查。
默认值就是 `true`（MyBatis-Plus 的默认），这里显式写出来是**为了让人一眼看见**。

**⑧ `log-impl: StdOutImpl`**
启动日志第 18 行 `Logging initialized using 'class org.apache.ibatis.logging.stdout.StdOutImpl' adapter.`
就是它打印的。作用是把每条 SQL 打到控制台：

```
==>  Preparing: SELECT id,name,... FROM employee WHERE (username = ?)
==> Parameters: admin(String)
<==      Total: 1
```

**这在开发期是刚需，上线必须关掉** —— 它会绕过日志框架（直接 `System.out`），
无法按级别过滤、无法落文件、高并发下 `synchronized` 的 `System.out` 会成为瓶颈。

**⑨ `id-type: auto` 与实体上的 `@TableId(type = IdType.AUTO)` 重复了**

MyBatis-Plus 的主键策略三级：

| 级别 | 写法 | 优先级 |
|---|---|---|
| 字段级 | `@TableId(type = IdType.AUTO)` | 最高（本项目所有实体都写了） |
| 全局 | `mybatis-plus.global-config.db-config.id-type: auto` | 中 |
| 默认 | `ASSIGN_ID`（雪花算法，19 位 Long） | 最低 |

**`AUTO` 意味着什么？**

```sql
INSERT INTO employee (name, username, ...) VALUES (...)   -- 不含 id
-- 依赖 MySQL 的 AUTO_INCREMENT，JDBC 用 Statement.RETURN_GENERATED_KEYS 回填
```

`ASSIGN_ID` 则是 MP 在 Java 侧生成一个 19 位雪花 ID，SQL 里带 `id`。
本项目选 `AUTO` 的理由：**表结构是课程给的，主键就是 `bigint AUTO_INCREMENT`，跟 `AUTO` 对齐；
而且自增 ID 短、可读、便于人工排查**。代价是分库分表时 ID 会冲突（雪花算法正是为解决这个）。

**有意思的细节：启动日志第 19 行**

```
Initialization Sequence datacenterId:2 workerId:0
```

**明明配了 `id-type: auto`，为什么雪花算法还在初始化？**

因为 `MybatisPlusAutoConfiguration` 无条件创建了一个 `IdentifierGenerator` Bean，
而它的构造函数里 `new Sequence()` 会打印这行。**实例化了，但永远不会被调用**（因为 `AUTO` 优先）。
`datacenterId:2 workerId:0` 是 MP 用**本机 IP + PID** 算出来的，所以每台机器不一样。

**这条日志的价值**：面试官如果问"你日志里这个 datacenterId 是什么"，你要能答
"那是 MyBatis-Plus 雪花算法的机器位，我的主键用的是数据库自增，所以它只是被实例化但没参与生成"。
—— 这种细节最能证明你真的看过自己的日志。

**⑮ `sky.*` 是自定义命名空间**

不是 Boot 的配置，是给 `JwtProperties` 和 `WebMvcConfiguration` 用的：

```java
@Component
@ConfigurationProperties(prefix = "sky.jwt")     // 把 sky.jwt.* 绑到字段
public class JwtProperties {
    private String adminSecretKey;   // ← 绑定 sky.jwt.admin-secret-key
    private long   adminTtl;
    private String adminTokenName;
    private String userSecretKey;
    private long   userTtl;
    private String userTokenName;
}
```

**`@ConfigurationProperties` 的宽松绑定（relaxed binding）**：`admin-secret-key`、
`adminSecretKey`、`ADMIN_SECRET_KEY` 三种写法都能绑到同一个字段。这是它比 `@Value` 强的地方
（`@Value("${sky.jwt.admin-secret-key}")` 只能精确匹配）。

### 3.3 `MybatisPlusConfiguration`：10 行代码决定分页是"真分页"还是"假分页"

```java
@Configuration
public class MybatisPlusConfiguration {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.MYSQL);
        pagination.setMaxLimit(500L);       // ← 单页最大 500 条
        interceptor.addInnerInterceptor(pagination);
        return interceptor;
    }
}
```

**如果没有这个 Bean，`selectPage()` 会发生什么？**

`BaseMapper.selectPage(page, wrapper)` 在没有分页插件时：

```
① 执行 SELECT * FROM employee                     ← 查全表
② 把结果全部读进内存 List
③ 在内存里 subList(start, end)                     ← 内存分页
④ total = list.size()
```

10 万条数据、单页 10 条 → **每次翻页都把 10 万条读进内存**。这就是"假分页"，数据量一大就 OOM。

**有了插件之后：**

```
① 先执行 SELECT COUNT(*) AS total FROM employee           ← 自动生成
② 再执行 SELECT ... FROM employee ORDER BY create_time DESC LIMIT 500  ← 自动加 LIMIT
```

两条 SQL，只读 500 行。这就是"真分页"。**下面 ④ 节有 general_log 实抓的两条 SQL。**

**`DbType.MYSQL` 为什么必须传？**

因为不同数据库的 `LIMIT` 语法不一样：
- MySQL：`LIMIT offset, size`
- Oracle：`ROWNUM` 或 `OFFSET ... FETCH`
- SQL Server：`OFFSET ... ROWS FETCH NEXT ... ROWS ONLY`
- PostgreSQL：`LIMIT size OFFSET offset`

`PaginationInnerInterceptor` 按 `DbType` 生成对应的方言。**不传会怎样？**
IPage 的 `dialect` 为空 → 抛 `MybatisPlusException: 请设置分页方言`。
（也可以靠 `mybatis-plus.helper-dialect` 或者 MP 自动从数据源 URL 推断，但显式传最稳。）

**`setMaxLimit(500L)` 是防什么？**

前端传 `pageSize=999999` 时，如果没上限，SQL 就是 `LIMIT 999999` ——
数据库要把 999999 行排序再返回，等于**给攻击者一个一请求打爆数据库的开关**（DoS）。
设了 500，实际 SQL 变成 `LIMIT 500`。**④ 节有实测：传 999999，SQL 里是 `LIMIT 500`。**

**这里有个更深的坑：`LIMIT 500` 但 `total` 还是真值。**

前端拿到 `total=5`（真实总行数）和 `records`（最多 500 条），如果 `total > 500` 就会显示
"共 1000 条，第 1/200 页"，但翻到第 3 页（501-1000）**返回空数组**。
正确做法是**同时把 total 也截到 500**，或者**在参数校验层直接拒绝 `pageSize > 500`**：

```java
if (pageSize > 500) throw new BaseException("单页最多 500 条");
```

本项目没做这个校验，属于第 ⑦ 层的小缺口。

### 3.4 `WebMvcConfiguration`：一个类干两件事

```java
@Configuration
public class WebMvcConfiguration implements WebMvcConfigurer {

    @Autowired private JwtTokenAdminInterceptor jwtTokenAdminInterceptor;
    @Autowired private JwtTokenUserInterceptor  jwtTokenUserInterceptor;

    @Value("${sky.file.upload-dir}")
    private String uploadDir;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(jwtTokenAdminInterceptor)
                .addPathPatterns("/admin/**")
                .excludePathPatterns("/admin/employee/login");     // ① 登录不能拦

        registry.addInterceptor(jwtTokenUserInterceptor)
                .addPathPatterns("/user/**")
                .excludePathPatterns("/user/user/login");          // ② 微信登录不能拦
    }

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/images/**")
                .addResourceLocations("file:" + uploadDir + "/");  // ③ file: 前缀！
    }
}
```

**为什么 `implements WebMvcConfigurer` 而不是 `extends WebMvcConfigurationSupport`？**

这是**必答的面试题**：

| | `implements WebMvcConfigurer` | `extends WebMvcConfigurationSupport` |
|---|---|---|
| 效果 | **追加**配置 | **接管**配置 |
| 自动配置 | Boot 的 `WebMvcAutoConfiguration` 照常生效 | **全部失效**（`@ConditionalOnMissingBean(WebMvcConfigurationSupport.class)`） |
| 静态资源 | 保留（`/static`、`/public`、`/webjars`） | 丢 |
| 消息转换器 | 保留（Jackson 自动配） | 丢，要自己 `configureMessageConverters` |
| 本项目 | ✅ 用这个 | ❌ 用了它 `/images/**` 和欢迎页都会出问题 |

**一句话记法：想要 Boot 的默认配置，就 implements；想彻底自己接管，才 extends。**

**`excludePathPatterns` 为什么不能用通配符偷懒？**

如果写成 `.excludePathPatterns("/admin/employee/*")`，会把 `/admin/employee/page`、
`/admin/employee/status/1` 全放行 —— **整个员工管理裸奔**。
必须精确列出 `"/admin/employee/login"`。

**③ `file:` 前缀是最容易漏的一个字**

```java
.addResourceLocations("file:" + uploadDir + "/")   // ✅ 文件系统绝对路径
// 如果写成
.addResourceLocations(uploadDir + "/")              // ❌ 会被当 classpath 相对路径
```

`addResourceLocations` 支持四种前缀：

| 前缀 | 含义 | 例 |
|---|---|---|
| `classpath:` | 从 jar 里读 | `classpath:/static/` |
| `file:` | 从磁盘读 | `file:E:/project/sky-take-out/upload/` |
| `http:` / `https:` | 远程 | 很少用 |
| 无前缀 | **取决于前面有没有已注册的 handler**，新人最易踩坑 | ❓ |

**末尾的 `/` 也不能少。** 少了它，`file:E:/.../upload` 会变成"upload 这个文件"而不是"upload 目录"。

**为什么需要这个映射？**

`CommonController.upload` 把图片存到 `E:/project/sky-take-out/upload/xxx.png`（磁盘上），
前端拿到返回的 `/images/xxx.png` 要去显示。但 Tomcat 默认只服务**classpath 下的 static**，
磁盘目录它不认识。所以必须手动把 URL 路径映射到磁盘路径。

**这也是第 ⑦ 层缺口（存储型 XSS）的放大器**：映射完，任何上传的文件（包括 `.html`）都能被浏览器直接执行。
实测：`/images/xxx.html` 返回 `Content-Type: text/html`，也就是说上传一个带 `<script>` 的 HTML
就能在同源下执行 JS、偷 token。见精讲 13 缺口 3。

**顺带说一个隐藏行为：`static/index.html` 是怎么被服务的？**

本项目没写任何 `@GetMapping("/")`，但 `GET /` 返回了 44845 字节的 `index.html`。
靠的是 Boot 的 `WelcomePageHandlerMapping`，启动日志第 20 行：

```
Adding welcome page: class path resource [static/index.html]
```

**机制**：`WebMvcAutoConfiguration.EnableWebMvcConfiguration` 里注册了
`WelcomePageHandlerMapping`，它把 `/` 映射到 classpath 下任意一个 `index.html`。
**所以前端 SPA 只要扔进 `resources/static/` 就自动可访问，一行代码都不用写。**
（`/images/**` 的映射和它不冲突：`/` 走 welcome page，`/images/**` 走自定义 handler，
`/admin/**`、`/user/**` 走 Controller，三套 handler 按 `order` 匹配。）

### 3.5 `WebSocketConfiguration`：为什么只要一行

```java
@Configuration
public class WebSocketConfiguration {
    @Bean
    public ServerEndpointExporter serverEndpointExporter() {
        return new ServerEndpointExporter();
    }
}
```

**JSR-356 的 `@ServerEndpoint` 是 Servlet 容器规范，不是 Spring 规范。**
所以 Spring 根本不认识 `@ServerEndpoint` —— 它不会自动把 `WebSocketServer` 注册成 Bean，
也不会管它怎么被实例化。

`ServerEndpointExporter` 是 Spring 提供的"桥"：

```
ApplicationContext 启动完成
    ↓ 触发 ServerEndpointExporter 的 SmartInitializingSingleton
    ↓ 遍历所有 Bean，找带 @ServerEndpoint 的类
    ↓ 对每个类调 ServerContainer.addEndpoint(ServerEndpointConfig)
    ↓ Tomcat 的 WsServerContainer 收下，注册到 /ws/{type}
```

**三个必答的细节（都在精讲 09 展开过，这里只列因配置导致的）：**

1. **`WebSocketServer` 上没加 `@Component`** —— 因为加了会变成单例 Bean，
   而 JSR-356 要求**每个连接一个实例**。`ServerEndpointExporter` 是靠**反射 newInstance**
   创建实例的，不是从容器拿。
2. **所以会话池必须是 `static`** —— 每个连接一个对象，`this.sessions` 是不共享的，
   只有 `static` 才能跨实例共享。
3. **用 `@Bean` 方式（而不是 `@ServerEndpointExporter` 注解）** —— 因为 Spring 没有
   `@EnableWebSocket` 这种注解给 JSR-356 用，只能手动注册这个 Bean。

**内嵌 Tomcat 下必须加这个 Bean；打成 war 部署到外部 Tomcat 反而不能加**（会重复注册报错）。
这是从 war 迁移到 jar 时最常见的坑之一。

### 4.2 连接池：`minimum-idle: 2` 的物证

应用跑起来、打过几次接口之后，到 MySQL 里数连接：

```sql
mysql> SELECT id, user, host, db, command, time, state
       FROM information_schema.processlist
       WHERE db='sky_take_out';

id    user   host              db             command   time   state
121   root   localhost:50917   sky_take_out   Sleep     48
122   root   localhost:50918   sky_take_out   Sleep     70
```

**不多不少正好 2 条，和 `minimum-idle: 2` 完全对上。**

- `command=Sleep` → 连接闲着，但 TCP 没断（这就是"池"）
- `maximum-pool-size: 10` 是上限，压力上来才扩容，**闲下来也不会降到 0**
- 如果配成 `minimum-idle: 0`，空闲连接会被回收，代价是下次请求要重新握手（多 20-50ms）

**面试问"你怎么验证连接池配对了"** —— 这就是标准答法：去 `information_schema.processlist` 数连接。
比"我配了 10"这种背诵强一百倍。

### 4.3 分页插件：一条 `general_log` 证明 `LIMIT 500` 是真的

**请求**：`GET /admin/employee/page?page=1&pageSize=999999`（前端故意传超大值）

**`general_log` 实抓到两条 SQL：**

```
2026-10-27 23:00:24.297  SELECT COUNT(*) AS total FROM employee
2026-10-27 23:00:24.306  SELECT id,name,username,password,phone,sex,id_number,status,
                                create_time,update_time,create_user,update_user
                         FROM employee ORDER BY create_time DESC LIMIT 500
                                                                        └────┬────┘
                                                              传的是 999999，被截成 500
```

对比正常请求 `pageSize=3`：

```
2026-10-27 23:00:25.014  SELECT COUNT(*) AS total FROM employee
2026-10-27 23:00:25.016  SELECT ... FROM employee ORDER BY create_time DESC LIMIT 3
```

**三点可以确认：**

1. **`setMaxLimit(500L)` 真的生效了** —— 999999 → 500
2. **分页是两条 SQL**（COUNT + 数据），不是一条。所以 N 次翻页 = 2N 次查询
3. **`ORDER BY create_time DESC` 是 `EmployeePageQueryDTO`/Controller 里写死的**，插件只负责加 `LIMIT`，不负责排序

**顺便：传 `pageSize=abc` 时一条 SQL 都没有。**
因为 `pageSize` 声明是 `int`，Spring 在**参数绑定阶段**就抛 `MethodArgumentTypeMismatchException`，
压根没到 MyBatis。这解释了为什么精讲 14 里那个请求返回的是"未知错误"而不是 SQL 错误。

**还有第七个发现（SQL 层面）：分页把 `password` 查出来了。**

```
SELECT id,name,username,password,phone,... FROM employee
                        └──┬───┘
                   明文 MD5 被查出来
```

但 JSON 响应里**没有** `password` 字段 —— 因为 `Employee.password` 上有 `@JsonIgnore`：

```java
@JsonIgnore
private String password;
```

**这是"双保险只上了一道"**：Jackson 层挡住了，SQL 层没挡。
正确做法是在查询时就裁列（`wrapper.select(Employee.class, i -> !"password".equals(i.getColumn()))`），
**永远不要把不需要的字段从数据库读出来**。这是第 ⑦ 层缺口 2。

### 4.6 multipart 限额：11MB 上传撞墙

## ⑤ 权衡

### 5.1 多模块 Maven：为什么要拆三个

```
sky-take-out (父，pom 打包)
  ├── sky-common   ← 工具/常量/异常/结果/BaseContext   依赖：spring-boot-starter, commons-lang3, jackson-databind
  ├── sky-pojo     ← entity / dto / vo                 依赖：jackson-annotations, mybatis-plus-annotation
  └── sky-server   ← controller/service/mapper/config  依赖：sky-common, sky-pojo, web, websocket, mybatis-plus, mysql, poi
```

**依赖是单向的：`server → pojo → 无`，`server → common → 无`。`pojo` 和 `common` 互不依赖。**

| | 多模块（本项目） | 单模块 |
|---|---|---|
| 编译粒度 | 改 pojo 不用重编 common | 全量重编 |
| 依赖管控 | `pojo` 里**根本引不到** JDBC/Web —— 想违规都违规不了 | 谁都能 `import` 任何东西 |
| 复用 | `sky-pojo` 能单独给小程序/后台/对账系统引用 | 做不到 |
| 团队协作 | 前端同学只要 `sky-pojo` 就能拿到 DTO 定义 | 要整个项目 |
| 复杂度 | 3 个 pom + 父 pom 的 dependencyManagement | 1 个 pom |

**为什么 `sky-pojo` 里只有 `jackson-annotations` 和 `mybatis-plus-annotation`？**

这是**刻意的极致精简**：

- 要 `jackson-annotations` → 因为 `Employee.password` 上有 `@JsonIgnore`
- 要 `mybatis-plus-annotation` → 因为 `@TableName` / `@TableId` / `@TableField` 在 `entity` 上
- **不要** `mybatis-plus-core` → 因为 `BaseMapper`、`UpdateWrapper` 是 server 层的东西，pojo 不该知道"怎么查"
- **不要** `spring-boot-starter-web` → 因为 pojo 不该知道"怎么响应 HTTP"

**"这个模块不该依赖什么"比"该依赖什么"更重要。** 这是分层的本质。

**父 pom 用 `<dependencyManagement>` 而不是 `<dependencies>`：**

```xml
<!-- 父 pom：只声明版本，不真的引入 -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
            <version>${mybatis-plus.version}</version>
        </dependency>
    </dependencies>
</dependencyManagement>

<!-- 子模块：引入时不写版本，继承父的 -->
<dependency>
    <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
</dependency>
```

**区别**：`<dependencies>` 会让**所有子模块**都强制引入这个依赖（哪怕 `sky-pojo` 根本不用）。
`<dependencyManagement>` 只统一版本，谁要谁引。**这是多模块项目的标准姿势。**

### 5.2 三个配置类为什么都这么短？—— 因为 Boot 干了绝大部分

| 需求 | 我要写的代码 | Boot 帮我写的 |
|---|---|---|
| Tomcat | 0 行 | `ServletWebServerFactoryAutoConfiguration` |
| DispatcherServlet | 0 行 | `DispatcherServletAutoConfiguration` |
| Jackson | 0 行 | `JacksonAutoConfiguration` |
| 数据源/Hikari | 7 行 yml | `DataSourceAutoConfiguration` |
| 事务管理器 | 0 行 | `DataSourceTransactionManagerAutoConfiguration` |
| SqlSessionFactory | 0 行 | `MybatisPlusAutoConfiguration` |
| Mapper 代理 | 1 行 `@MapperScan` | `MapperScannerConfigurer` |
| **分页插件** | **10 行** | ❌ 不管（必须手写） |
| **拦截器** | **10 行** | ❌ 不管（业务决定） |
| **静态资源映射到磁盘** | **4 行** | ❌ 不管（路径业务决定） |
| **WebSocket 端点** | **5 行** | ❌ 不管（JSR-356 不属于 Spring） |

**加粗的四行就是"配置类存在的全部理由"。** 框架能猜的它都猜了，猜不到的（业务路径、插件、拦截规则）才要你写。

**这也解释了为什么"配置类越少越好"是错的** —— 该写的还得写，只是写得更少了。

### 5.3 `application.yml` vs `application.properties` vs 多 profile

| | yml | properties |
|---|---|---|
| 层级 | 缩进，天然分层 | 全平铺 `a.b.c=v` |
| 重复前缀 | 只写一次 | 每个 key 都重写 |
| 类型 | 支持 List/Map | 只支持字符串 |
| 坑 | **缩进错一个空格就绑不上，且不报错** | 无 |

**yml 的致命问题：缩进错了不报错，只是配置静默失效。**
比如 `hikari:` 少缩进两格，它就成了 `spring.datasource` 的同级，`maximum-pool-size` 完全不生效。
**排查方法：看启动日志有没有 `HikariPool - configuration:` 打印（开 debug 才有），
或者直接查 `processlist` 数连接（4.2 节）。**

**多 profile 本项目没做**（启动日志第 ② 行 `No active profile set`）。生产项目的标准结构：

```
application.yml            # 公共配置 + spring.profiles.active: dev
application-dev.yml        # 本地：localhost:3306, root/123456, 打 SQL
application-test.yml       # 测试环境
application-prod.yml       # 生产：连接池调大, log-impl 关掉, 密钥从环境变量读
```

**为什么必须有多 profile？** 因为「打印 SQL」「数据库密码」「JWT 密钥」这三样在开发和生产的要求完全相反。
现在全写在一份 yml 里，意味着**这份文件不能给别人看**（含明文密码），也不能直接上线（会打 SQL + 密钥硬编码）。
这是第 ⑦ 层缺口 1。

## ⑥ 踩坑

### 坑 1：`javax.servlet` 全部编译失败 —— Boot 3 的 jakarta 迁移

**现象**（P8 接 WebSocket 时）：

```
[ERROR] .../JwtTokenAdminInterceptor.java:[3,26] 程序包javax.servlet.http不存在
[ERROR] .../WebMvcConfiguration.java:[4,33] 程序包javax.servlet不存在
[ERROR] .../CommonController.java:[5,24] 程序包javax.servlet不存在
```

**根因**：Oracle 把 Java EE 捐给 Eclipse 基金会后，**商标不能用 `javax`**，
所以 Jakarta EE 9 起全部改名为 `jakarta.*`。Boot 3.x 只支持 Jakarta EE 9+，
内嵌的 Tomcat 10 也只会 `import jakarta.servlet.*`。

**修改（三处）：**

```java
// 改前
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
// 改后
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
```

WebSocket 同理：`javax.websocket.*` → `jakarta.websocket.*`（`@ServerEndpoint`、`Session`、`OnOpen` 等）。

**为什么这个坑值得记**：因为它**不是"写错代码"，是"抄了过时的代码"**。
网上 90% 的苍穹外卖教程是 Boot 2.7 + `javax`，直接抄过来必炸。
而且报错信息只告诉你"包不存在"，不会告诉你"因为你是 Boot 3"。

**判断口诀**：看到 `Tomcat/10.x` 或 `Spring Boot 3.x`，脑子里立刻把 `javax.` 换成 `jakarta.`。

### 坑 2：离线构建（`-o`）时 POI 死活解析不到

**现象**：

```
[ERROR] The following artifacts could not be resolved:
        org.apache.poi:poi-ooxml:jar:5.2.5 ... was not found
```

但 `E:\env\maven_repo\org\apache\poi\poi-ooxml\5.2.5\` 里**jar 明明在**。

**根因**：Maven 的本地仓库里每个 jar 旁边有个 `_remote.repositories` 文件，记录"这个 jar 是从哪个仓库下的"：

```
poi-ooxml-5.2.5.jar>central=
                     └─ 从 id 为 central 的仓库下载的
```

而项目的 `maven-settings.xml` 里配的镜像 id 是 `aliyunmaven`：

```xml
<mirror>
    <id>aliyunmaven</id>
    <url>https://maven.aliyun.com/repository/public</url>
    <mirrorOf>central</mirrorOf>
</mirror>
```

**离线模式（`-o`）下，Maven 会校验"当前仓库 id 是否在 `_remote.repositories` 里"。**
`aliyunmaven` 不在里面（里面只有 `central`）→ 判定为"未下载" → 报缺失。
**但文件明明在磁盘上** —— 这就是这个坑最迷惑人的地方。

**三种解法（按推荐度）：**

```bash
# ① 去掉 -o，联网重新解析一次（本项目采用）
mvn -gs maven-settings.xml package -DskipTests
# 联网时 Maven 会把 _remote.repositories 里的标记更新为 aliyunmaven，之后 -o 就能用了

# ② 加参数忽略这个校验
mvn -o -llr ...      # legacy-local-repository，让 Maven 只检查文件是否存在

# ③ 手动删掉所有 _remote.repositories（不推荐，文件太多）
```

**这个坑的普适教训**：`-o` 不是"只要文件在就行"，它有**元数据校验**。
看到"文件在但说找不到"，第一反应就该是 `_remote.repositories`。

### 坑 3：`@MapperScan` 和 `@Mapper` 重复了

```java
@MapperScan("com.sky.mapper")                        // 启动类：扫整个包
public interface EmployeeMapper extends BaseMapper<Employee> { }  // 接口上还有 @Mapper
```

**两种方式都能让 Mapper 生效，二选一即可：**

| 方式 | 机制 | 范围 |
|---|---|---|
| `@MapperScan("com.sky.mapper")` | `MapperScannerConfigurer` 扫**包下所有接口**，不看注解 | 整个包 |
| 接口上 `@Mapper` | `AutoConfiguredMapperScannerRegistrar` 扫**启动类所在包及其子包**里带 `@Mapper` 的接口 | 带注解的 |

**当前状态：两者并存，冗余但无害**（不会重复注册，因为 Bean 名都是 `employeeMapper`，后者被跳过）。

**为什么留着**：`@Mapper` 在单个接口上能**自解释**"我是 MyBatis 接口"（IDE 也会有图标），
`@MapperScan` 在启动类上能**一眼看到全局入口**。两者同时存在是很多项目的习惯写法。

**要不要删一个？** 建议删掉 `@MapperScan` —— 因为 `@Mapper` 更精确（只注册你标记的接口），
不会把 `com.sky.mapper` 下将来某个非 Mapper 接口误注册。但**这个项目已经在跑，不动它**。

**面试可以主动说**："我这里 `@MapperScan` 和 `@Mapper` 重复了，两种方式都行，留一个是更好的做法。
我留着是为了让接口上能自解释。" —— **知道冗余在哪，比假装完美强。**

### 坑 4：`unset SERVER__PORT` —— 环境变量打败了 yml

**现象**：想把端口改成 8081，改 yml 没用，日志还是 `port 8080`。

**根因**：Spring 的宽松绑定会把环境变量 `SERVER_PORT` 绑到 `server.port`。
这台机器上存在某个 `SERVER__PORT`（双下划线），Boot 会把它归一化成 `server.port`，
**优先级高于 `application.yml`**（见 3.1 节的优先级表）。

**解法（每次启动都做）：**

```bash
unset SERVER__PORT && java -jar sky-server-1.0-SNAPSHOT.jar --server.port=8080
```

**`unset` 的作用范围**：只影响当前 shell 及其子进程，**不修改系统环境变量**（符合"不改系统环境"的约束）。

**为什么同时还要显式 `--server.port=8080`**：双保险。命令行参数是最高优先级，
写了它，哪怕环境变量还在，也一定是 8080。

**这个坑的普适教训**：**配置不生效时，先怀疑"有更高优先级的源覆盖了它"**，
而不是怀疑"框架有 bug"。排查顺序：命令行 → 系统属性 → 环境变量 → profile yml → 主 yml。

### 坑 5：`mvn clean` 禁用之后，怎么保证构建干净

**约束**：不许用 `mvn clean`（会删 `target`）。

**那改了代码会不会用到旧 class？**

- `mvn package` 会**重新编译所有源文件**（`maven-compiler-plugin` 的增量编译基于时间戳，
  `src` 里的 `.java` 比 `target` 里的 `.class` 新就重编）
- `spring-boot-maven-plugin` 的 `repackage` 会**重新打 jar**（覆盖旧的）

**所以 `mvn package` 本身够用**，`clean` 只在"target 里有不该有的残留"时才必要
（比如删掉了一个类，旧 `.class` 还在 target 里，会被打进 jar）。

**遇到"改了代码但行为没变"时，正确的排查顺序：**

```bash
# ① 确认 jar 时间戳是刚才
ls -l sky-server/target/sky-server-1.0-SNAPSHOT.jar

# ② 确认没有旧进程占着 8080（旧 jar 还在跑，你测的是老的）
netstat -ano | grep 8080

# ③ 确认 jar 里的 class 是新的
unzip -p sky-server/target/sky-server-1.0-SNAPSHOT.jar \
      BOOT-INF/classes/com/sky/config/WebMvcConfiguration.class | strings | grep images

# ④ 手动删掉单个残留 class（比 clean 精确）
```

**第 ② 步是最常见的坑**：8080 被上一个进程占着，新进程启动失败（`Port 8080 was already in use`），
但你可能没注意日志，还在测老服务。**本项目规矩："改代码前先停实例"，就是为了避免这个。**

## ⑦ 缺口

### 缺口 1：没有多 profile，密钥和密码明文躺在代码里

```yaml
spring:
  datasource:
    password: "123456"                              # ← 明文
sky:
  jwt:
    admin-secret-key: sky-take-out-admin-secret-key-2026   # ← 明文
```

**三个后果：**

1. **代码不能公开** —— 简历放 GitHub，数据库密码和 JWT 密钥一起泄露
2. **密钥改了要重新打包** —— 运维改不了运行时配置
3. **开发和生产的配置混在一起** —— `log-impl: StdOutImpl` 上线还在打 SQL（性能 + 日志体积）

**正确做法（三步）：**

```yaml
# application.yml（进代码库）
spring:
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}
  datasource:
    password: ${DB_PASSWORD:}

# application-dev.yml（进代码库，本地默认值）
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/sky_take_out
    password: 123456
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   # 只有 dev 打 SQL

# application-prod.yml（进代码库，但值是占位符）
spring:
  datasource:
    password: ${DB_PASSWORD}       # 从环境变量注入，没有就启动失败
sky:
  jwt:
    admin-secret-key: ${JWT_ADMIN_SECRET}
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.nologging.NoLoggingImpl   # 生产不打 SQL
```

**启动时注入：**

```bash
java -jar app.jar --spring.profiles.active=prod \
     # 环境变量 DB_PASSWORD / JWT_ADMIN_SECRET 由 K8s Secret / Docker env 提供
```

**面试话术**："我的配置是单文件的，密钥硬编码在 yml 里。生产要拆成 `dev/prod` 两个 profile，
密钥走环境变量或配置中心（Nacos/Apollo），`log-impl` 生产必须关掉。"
—— **主动说自己的不足，比被问出来体面得多。**

### 缺口 2：分页 SQL 把 `password` 查出来了，只靠 `@JsonIgnore` 挡

**实测证据**（4.3 节）：

```sql
SELECT id,name,username,password,phone,... FROM employee ORDER BY create_time DESC LIMIT 500
                        └──┬───┘
                    不需要，但查了
```

**风险链条**：

```
SQL 查出 password
    → 进 MyBatis 的 ResultSet → 塞进 Employee 对象
    → 如果哪天有人写了 @JsonIgnore 之外的序列化（比如 log.info("{}", employee)）
    → 或者转成了 Map 返回（BeanUtil.beanToMap 会带上所有字段）
    → or 走了别的 JSON 视图（@JsonView）
    → 密码 MD5 就漏了
```

**MD5 虽然不可逆，但 `e10adc3949ba59abbe56e057f20f883e` 在彩虹表里 = `123456`，等于明文。**

**改法一：查询时裁列（推荐）**

```java
// 只选需要的列
QueryWrapper<Employee> wrapper = new QueryWrapper<>();
wrapper.select(Employee.class, info -> !"password".equals(info.getColumn()));
wrapper.like(StringUtils.hasText(name), "name", name);
wrapper.orderByDesc("create_time");
Page<Employee> page = employeeMapper.selectPage(new Page<>(pageNum, pageSize), wrapper);
```

**改法二：VO 隔离（更彻底，工作量大）**

给分页单独定义 `EmployeeVO`（不含 password），Mapper 直接返回 VO。
**这是生产项目的标准做法** —— Entity 只在内层流转，出到 Controller 的一律是 VO。

**为什么本项目没做**：因为 `@JsonIgnore` 已经挡住了眼前的风险，改 VO 要动 5 个文件。
**但这是个"知道该做但没做"的技术债，面试要能讲清楚。**

### 缺口 3：`setMaxLimit(500)` 只截了数据，没截 `total`

**问题**：`pageSize=999999` 时，`records` 最多 500 条，但 `COUNT(*)` 返回**真实总数**。

假设表里有 1000 行：

```json
{"total": 1000, "records": [... 只有 500 条 ...]}
```

前端算总页数：`Math.ceil(1000/999999) = 1` 页 → 看起来正常。但如果是
`pageSize=500` 而表里有 1000 行，翻到第 3 页（1001-1500）→ 空数组。
**用户会以为"数据丢了"。**

**改法：在参数校验层直接拒绝**

```java
// EmployeePageQueryDTO 上加 @Max，Controller 上加 @Validated
@Max(value = 500, message = "单页最多 500 条")
private int pageSize;
```

**或者在 Service 入口判断：**

```java
if (pageSize > 500) throw new BaseException("单页最多查询 500 条");
```

**这比"悄悄截断"好一百倍** —— 用户知道发生了什么，而不是"数据莫名少了"。

### 缺口 4：`/images/**` 把整个 upload 目录暴露成静态资源，无鉴权

`registry.addResourceHandler("/images/**").addResourceLocations("file:" + uploadDir + "/")`
意味着 **upload 目录下任何文件都能被匿名访问**。

- 正常场景：菜品图片，本来就该公开（前端要显示）→ **合理**
- 风险场景：有人上传了 `1.html`（含 `<script>fetch('/admin/employee/page',{headers:{token:localStorage.token}})</script>`）
  → **同源 XSS，能偷 admin 的 token**（精讲 13 缺口 3 已实测复现）
- 更糟：如果上传接口允许 `.jsp`/`.jar`，配合某些容器配置可能 RCE（本项目 Tomcat 10 不解析 JSP 于静态目录，风险低但存在）

**改法（三条都要）：**

```java
// ① 上传时校验扩展名白名单 + 真实 MIME（不只看 Content-Type，要读文件头 Magic Number）
// ② 静态资源响应加 X-Content-Type-Options: nosniff，禁止浏览器猜类型
// ③ 上传目录和静态目录物理隔离：上传到 upload/tmp，审核后移到 upload/public
```

**第二条的威力**：加了 `nosniff`，浏览器不会把 `.md` 当 HTML 执行，XSS 链条直接断掉。

> **问：Spring Boot 自动装配原理？**
>
> "`@SpringBootApplication` 里有 `@EnableAutoConfiguration`，它 `@Import` 了
> `AutoConfigurationImportSelector`。这个 selector 读 classpath 下所有 jar 的
> `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
> （Boot 3 的新文件，2.7 之前是 `spring.factories`），拿到 140 多个自动配置类的名字，
> 再按 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 这些条件筛，通过才注册成 Bean。
>
> 所以'约定优于配置'的本质是：**你没定义，我就给你默认的**。
> 比如我项目里数据源只写了 7 行 yml，HikariCP 是 `DataSourceAutoConfiguration` 自动建的 ——
> 我实测过，`minimum-idle: 2` 配了之后 `information_schema.processlist` 里正好 2 条连接。"
>
> **问：你的项目怎么分层的？**
>
> "Maven 多模块，三个：`sky-common` 放工具/常量/异常/统一响应，`sky-pojo` 放 entity/dto/vo，
> `sky-server` 放 controller/service/mapper/config。依赖是单向的，`server → pojo`、`server → common`。
>
> 关键是 `sky-pojo` 的依赖我压到最小 —— 只有 `jackson-annotations`（因为 `@JsonIgnore`）和
> `mybatis-plus-annotation`（因为 `@TableName`/`@TableId`），**没有** `spring-boot-starter-web`。
> 这样 pojo 模块根本 `import` 不到 HTTP 相关的东西，想违反分层都违反不了。"
>
> **问：你的配置类都写了什么？**
>
> "三个，加起来不到 30 行，因为 Boot 能猜的都猜了。
>
> `MybatisPlusConfiguration` 注册分页插件，`setMaxLimit(500)` 防前端传超大 pageSize。

> `WebSocketConfiguration` 就一行 `ServerEndpointExporter`，因为 `@ServerEndpoint` 是 JSR-356 规范、
> 不是 Spring 规范，得靠这个 Bean 做桥接。内嵌 Tomcat 必须加，打 war 部署到外部 Tomcat 反而不能加。"

> **问：你踩过什么框架层面的坑？**

> 三个文件要改 import。网上大部分教程是 Boot 2.7 的，直接抄必炸。

> ② 离线构建 `-o` 时报 'POI 找不到'，但 jar 明明在本地仓库。

## 补充：`HealthController` 为什么用 `JdbcTemplate` 而不是 Mapper

```java
@Autowired
private JdbcTemplate jdbcTemplate;   // ← 不是 EmployeeMapper

@GetMapping
public Map<String, Object> health() {
    Map<String, Object> result = new LinkedHashMap<>();
    result.put("app", "sky-take-out");
    result.put("time", LocalDateTime.now().toString());
    try {
        Integer tables = jdbcTemplate.queryForObject(
            "select count(*) from information_schema.tables where table_schema = 'sky_take_out'",
            Integer.class);
        Integer dishes = jdbcTemplate.queryForObject("select count(*) from dish", Integer.class);
        result.put("db", "UP");
        result.put("tableCount", tables);
        result.put("dishCount", dishes);
    } catch (Exception e) {
        result.put("db", "DOWN");
        result.put("error", e.getMessage());
    }
    return result;
}
```

**四个设计决定：**

1. **返回 `Map` 而不是 `Result`** —— 健康检查不该受业务响应体的约束。运维工具要的是
   `{"db":"UP"}` 这种扁平结构，不是 `{"code":1,"data":{"db":"UP"}}`。
2. **用 `JdbcTemplate` 而不是 MyBatis** —— 健康检查要验证的是**最底层**的连通性。
   走 Mapper 会经过 MyBatis 的一堆拦截器/插件，万一插件挂了，你分不清是数据库挂了还是 MyBatis 挂了。
   `JdbcTemplate` 直连 `DataSource`，最接近真实。
3. **`try-catch` 而不是抛异常** —— 数据库挂了要返回 `{"db":"DOWN"}`（HTTP 200），
   而不是 500。因为健康检查的**语义就是"我给你报告状态"**，不是"我也挂了"。
   （这条和精讲 14 的"全 200"哲学一致，但这里是有意的。）
4. **不用 `/admin/**` 前缀** —— 否则会被 JWT 拦截器拦住，运维没 token 就查不了健康状态。**这是最容易犯的错。**

**实测输出：**

```bash
curl http://localhost:8080/health
# {"app":"sky-take-out","time":"2026-10-27T23:00:04.182144300","db":"UP","tableCount":11,"dishCount":12}
```

**`tableCount: 11`、`dishCount: 12`** —— 一行 `curl` 同时验证了「应用活着 + 数据库通了 + 数据还在」。
这就是健康检查的价值：**出问题时第一个要看的地方**，而且不需要 token。
