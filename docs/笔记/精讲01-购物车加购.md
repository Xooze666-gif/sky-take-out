# 精讲 01 · 购物车加购：`ShoppingCartServiceImpl.add`

> 源码位置：`ShoppingCartServiceImpl.add` + `fillGoodsInfo` + `currentAmount`
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版

---

## ① 场景

用户在小程序里点「+」，加一份水煮鱼（微辣）。前端发出：

```
POST /user/shoppingCart/add
{"dishId": 1, "dishFlavor": "微辣"}
```

**前端只传了三样东西：`dishId`、`dishFlavor`，以及 token 请求头里的身份。**

它**没传**价格、没传菜名、没传 `userId`。这三样全部由后端补齐 —— 这是理解这个方法的主线。

---

## ② 数据：执行前 → 执行后

假设 `shopping_cart` 表此时**没有**这个用户的任何记录。

执行后新增一行：

| id | user_id | dish_id | setmeal_id | dish_flavor | name | image | amount | number | create_time |
|---|---|---|---|---|---|---|---|---|---|
| 7 | 4 | 1 | NULL | 微辣 | 水煮鱼 | xxx.jpg | **38.00** | 1 | 22:31:05 |

**三个必须看准的点：**

1. **`amount = 38.00` 是单价，不是总价。** 总价要靠 `amount × number` 算。这一条后面第 ⑥ 层会用 SQL 证明。
2. **`user_id = 4` 不是前端传的**，是从 token 解出来、经 ThreadLocal 递下来的。
3. **`name` / `image` / `amount` 全是后端查 `dish` 表补的。**

再点一次「+」，表里不会多一行，而是原来那行 `number` 从 1 变 2 —— 这是"同商品合并"的逻辑。

---

## ③ 逐行拆

### 第 1 行：身份只能信 token

```java
Long userId = BaseContext.getCurrentId();
```

从 ThreadLocal 拿（拦截器已经把 token 里的 `userId` 存进去了，见精讲 05）。

**为什么不从请求参数拿？** 因为前端可以传任意 `userId`。如果代码写 `cart.setUserId(dto.getUserId())`，A 用户就能往 B 用户的购物车塞东西 —— 这叫**越权写入（IDOR）**，是 OWASP 前十的漏洞。

**身份相关的字段，永远只从服务端可信源取。**

### 第 2-4 行：copy 和 set 的顺序是刻意的

```java
ShoppingCart cart = new ShoppingCart();
BeanUtils.copyProperties(shoppingCartDTO, cart);   // 先 copy
cart.setUserId(userId);                            // 后 set
```

**如果反过来写会出事**：

```java
cart.setUserId(userId);                    // 先设正确的 4
BeanUtils.copyProperties(dto, cart);       // 后 copy —— 如果 DTO 里有 userId，就被覆盖了
```

`BeanUtils.copyProperties` 是"源有值就覆盖目标"，不看目标原来是什么。只要 `ShoppingCartDTO` 里将来有人加了个 `userId` 字段，前端传个 `999`，就能把已经设好的正确值冲掉。

**所以顺序是"先信任最低地接住所有外来数据，再用可信值覆盖关键字段"。** 这个模式和精讲 07 里套餐快照的覆盖是同一个思路。

### 第 5-7 行：为什么提前校验"二选一"

```java
if (cart.getDishId() == null && cart.getSetmealId() == null)
    throw new BaseException("dishId 和 setmealId 至少传一个");
```

购物车里的"商品"可能是**菜品**（单点），也可能是**套餐**（组合），靠这两个字段谁非空来区分。

**不校验会怎样？** 后面 `fillGoodsInfo` 里是这么写的：

```java
if (cart.getDishId() != null) {
    // 查 dish
} else {
    // 查 setmeal
}
```

两个都 null 时会走 `else`，拿 `null` 去查套餐表，查出来是 null，然后抛"套餐不存在"。

**用户实际问题是"我什么都没传"，收到的提示是"套餐不存在"** —— 排查方向直接被带偏。

**这叫"错要错在第一时间、错得准确"。** 早失败（fail fast）不只是性能优化，更是可维护性。

### 第 8-12 行：查重 + 动态条件

```java
ShoppingCart existing = shoppingCartMapper.selectOne(Wrappers.<ShoppingCart>lambdaQuery()
        .eq(ShoppingCart::getUserId, userId)
        .eq(cart.getDishId() != null, ShoppingCart::getDishId, cart.getDishId())
        .eq(cart.getSetmealId() != null, ShoppingCart::getSetmealId, cart.getSetmealId())
        .eq(cart.getDishFlavor() != null, ShoppingCart::getDishFlavor, cart.getDishFlavor()));
```

**为什么要查重？** 用户连点两次「+」，购物车里应该是「水煮鱼 ×2」，而不是两条「水煮鱼 ×1」。后者会在下单时生成两条订单明细，而且用户看着也别扭。

**重点是 `eq(布尔, 列, 值)` 这个重载**：

```java
eq(boolean condition, R column, Object val)
```

**第一个参数为 `false` 时，这个条件整条不拼进 SQL。** 所以实际行为是：

| 加购的东西 | 生成的 WHERE |
|---|---|
| 菜品 + 有口味 | `user_id = 4 AND dish_id = 1 AND dish_flavor = '微辣'` |
| 菜品 + 无口味 | `user_id = 4 AND dish_id = 1` |
| 套餐 + 无口味 | `user_id = 4 AND setmeal_id = 2` |

**为什么不 `if` 分开写成两个方法？** 因为组合会爆炸：菜品/套餐 × 有口味/无口味 = 4 种，加上未来可能加"规格""加料"，就是 8 种、16 种。**动态条件一行顶 N 行。**

**这个重载在项目里到处都是**（`EmployeeServiceImpl.pageQuery` 的 `like(条件, ...)`、`OrderServiceImpl.conditionSearch` 的一堆 `.eq(条件, ...)`），是 MyBatis-Plus 最实用的 API 之一。

### 第 13-18 行：已存在 → 数量 +1，单价刷新

```java
if (existing != null) {
    existing.setNumber(existing.getNumber() + 1);
    existing.setAmount(currentAmount(existing));      // ← 全场最值得琢磨的一行
    shoppingCartMapper.updateById(existing);
    return;
}
```

`currentAmount(existing)` 会**重新查一次 dish 表**拿最新价。

**这意味着什么？** 用户上次加购时是 38 元，商家这期间把价格改成 58，用户**这次**再点「+」，整个条目的单价（包括上次那份）都变成 58。

**为什么合理？** 因为购物车还没成交，按最新价算才对。商家涨价了，用户看到的应该是新价，不然下单时会"咦怎么贵了"。

**这跟"价格快照"矛盾吗？** 不矛盾，是**两个阶段的不同规则**：

| 阶段 | 规则 | 原因 |
|---|---|---|
| 购物车 | **活价**（每次刷新） | 还没成交，应该反映当前价 |
| 订单 | **死价**（快照 + 冻结） | 已成交，改价不能影响历史 |

**"购物车用活价，订单用死价"** —— 这句话面试说出来，面试官会觉得你想过业务，不是背代码。

### 第 19-23 行：不存在 → 补全信息后新增

```java
fillGoodsInfo(cart);                        // 查 dish / setmeal 补 name、image、amount
cart.setNumber(1);                          // 首次加购就是 1 份
cart.setCreateTime(LocalDateTime.now());    // 手动设创建时间
shoppingCartMapper.insert(cart);
```

`fillGoodsInfo` 根据 `dishId` 查 `dish` 表，把 `name`、`image`、**`price`** 拷进购物车。

**为什么必须查库补？** 前端只传了 `dishId`，它不知道水煮鱼多少钱 —— 就算它知道也不能信。**价格只能从数据库来。**

**注意 `cart.setAmount(dish.getPrice())` —— 存的是单价。** 所以：

```
shopping_cart.amount  = 单价
shopping_cart.number  = 份数
总价 = amount × number（不存储，展示时算）
```

**`setCreateTime` 这里为什么手写？** 因为 `ShoppingCart` 实体标了 `@TableField(fill = FieldFill.INSERT)`，理论上 handler 会填。但这里显式设了也一样（`strictInsertFill` 发现非 null 就跳过）。**属于冗余但无害的写法**（精讲 12 会讲这个机制）。

## ④ SQL 实况（真实抓取，2026-10-27 22:34）

测试数据：用户 4 加购 `dishId=1`（王老吉，6.00 元），口味「微辣」，连点两次。

### 第 1 次加购（不存在 → 走新增）

```sql
-- ① 查重：动态拼了 3 个条件（user_id + dish_id + dish_flavor）
SELECT id,name,image,user_id,dish_id,setmeal_id,dish_flavor,number,amount,create_time
FROM shopping_cart
WHERE (user_id = 4 AND dish_id = 1 AND dish_flavor = '微辣')

-- ② 查菜品补信息
SELECT id,name,category_id,price,image,description,status,create_time,update_time,create_user,update_user
FROM dish WHERE id=1

-- ③ 插入：注意字段列表
INSERT INTO shopping_cart ( name, image, user_id, dish_id, dish_flavor, number, amount, create_time )
VALUES ( '王老吉', '/images/wlj.png', 4, 1, '微辣', 1, 6.00, '2026-10-27 22:34:05.930318' )
```

**看第 ③ 条的字段列表：只有 `create_time`，没有 `create_user` / `update_time` / `update_user`。**

这就是 `strictInsertFill` 生效的直接证据：`ShoppingCart` 实体只标了 `createTime` 一个填充注解，handler 里那四行 `strictInsertFill` 有 **3 行被自动跳过**（详见精讲 12）。

**对比一下：新增菜品时，`INSERT INTO dish` 里四个公共字段全在。** 同一个 handler，不同的表不同的结果 —— 靠的就是"实体上标了什么"。

### 第 2 次加购（已存在 → 走更新）

```sql
-- ① 查重：查到了 id=6 那条
SELECT ... FROM shopping_cart WHERE (user_id = 4 AND dish_id = 1 AND dish_flavor = '微辣')

-- ② 又一次查 dish —— 这就是 currentAmount() 在刷新单价
SELECT ... FROM dish WHERE id=1

-- ③ 更新：所有字段都写了一遍，number 从 1 变 2
UPDATE shopping_cart
SET name='王老吉', image='/images/wlj.png', user_id=4, dish_id=1,
    dish_flavor='微辣', number=2, amount=6.00, create_time='2026-10-27 22:34:06'
WHERE id=6
```

### 从这三条 SQL 里能看出三个事实

**事实 1：第 2 次加购比第 1 次多了一次 `SELECT dish`。**

第 1 次的 `SELECT dish` 是 `fillGoodsInfo`；第 2 次的 `SELECT dish` 是 `currentAmount`。

**这正是"购物车用活价"的证明** —— 每次加购都重新查价，商家改价后用户再点一次「+」，单价就跟着变。

**事实 2：`UPDATE` 把所有字段都写了一遍，连 `create_time` 都被覆盖了。**

因为 `existing` 是**从库里查出来的完整对象**，所有字段都非 null，MyBatis-Plus 的 `NOT_NULL` 策略会把它们**全部拼进 SET**。

**风险：并发下的"丢失更新"。** 如果同时有另一个请求改了这行的 `image`，这次 UPDATE 会用旧值把它覆盖回去。

**这也解释了精讲 03 里支付为什么是全字段 UPDATE、精讲 08 里接单为什么只有一个字段** —— 差别就在"传进去的对象是查出来的还是 new 出来的"。

**事实 3：`create_time` 从 `22:34:05.930318` 变成了 `22:34:06`。**

表字段是 `datetime`（**无小数秒**），MySQL 对 `.930318` 四舍五入进位到下一秒。

**如果你要精确到毫秒，建表得用 `datetime(3)`。** 这个项目所有时间列都是 `datetime`，所以精度只到秒 —— 统计"接口耗时"这种事就别指望它了。

## ⑤ 权衡

| 决策点 | 选了 | 另一种做法 | 为什么选这个 |
|---|---|---|---|
| `userId` 来源 | ThreadLocal | 前端传参 | 防越权写入 |
| copy 与 set 顺序 | 先 copy 后 set | 先 set 后 copy | 防 DTO 字段把可信值冲掉 |
| 查重条件 | 动态 `eq(条件, ...)` | `if/else` 分 4 个方法 | 组合爆炸，动态条件更简洁 |
| 已存在时价格 | 刷新为最新价 | 保留首次加购价 | 购物车未成交，应按现货价 |
| 商品信息 | 后端查库补 | 信任前端传的 name/price | 前端不可信，改价风险 |
| 数量为 1 时 | 仍然插一行（不特殊处理） | 直接返回不插 | 语义一致，且用户要能"看到"购物车有一条 |

### 为什么"已存在就刷新单价"是对的，而不是保留首次价？

有人会担心："用户上次看到的 38 元，这次变 58 了，是不是欺骗？"

**反过来想：如果保留 38 元会怎样？**

- 商家涨到 58，用户购物车里还是 38，下单时按 38 收钱 —— **商家亏**
- 商家降到 30，用户购物车里还是 38，下单时按 38 收钱 —— **用户亏**

两边都可能亏，所以购物车**必须反映现货价**。用户在下单页会看到最终价格，那个才是成交价。

**这也是为什么电商的"购物车价格"和"结算价格"经常不一样** —— 购物车是"参考价"，结算页才是"锁定价"。

### 为什么查重时不查 `setmeal_id` 为 null 的情况？

因为 `eq(cart.getSetmealId() != null, ...)` 已经处理了：加的是菜品时，`setmeal_id` 是 null，这个条件**整条不拼**。SQL 里就只有 `dish_id = ?`。

**如果拼了会怎样？** `AND setmeal_id = NULL` —— 这在 SQL 里**永远不成立**（NULL 跟任何值比较都是 UNKNOWN）。查重永远查不到，每次加购都新增一行，"合并数量"彻底失效。

**这是 SQL 三值逻辑的经典坑：`= NULL` 不等于"匹配空值"，要用 `IS NULL`。** MyBatis-Plus 的动态条件正好绕过了它。

## ⑥ 踩坑实录

### 坑 1：`amount` 到底是单价还是总价？

写这篇笔记之前，我先入为主地以为 `amount` 是"这一行的总价"（6.00 × 2 = 12.00）。

抓了 SQL 才发现：

```sql
INSERT INTO shopping_cart (... number, amount ...) VALUES (... 1, 6.00 ...)   -- 1 份，6.00
UPDATE shopping_cart SET number=2, amount=6.00 ...                            -- 2 份，还是 6.00
```

**数量变了，`amount` 没变** → 说明 `amount` 是**单价**。

顺着这条线再看订单：

```sql
INSERT INTO order_detail (... number, amount ...) VALUES (... 2, 6.00)   -- 明细：2 份，单价 6.00
INSERT INTO orders (... amount ...) VALUES (... 12.00 ...)               -- 主表：总额 12.00
```

**结论：**

```
shopping_cart.amount   = 单价
order_detail.amount    = 单价
orders.amount          = 总额   ← 只有主表是总额
```

**被面试官问"你的金额字段怎么设计的"，答错这个就直接暴露"你没看过自己的表"。**

### 坑 2：`datetime` 没有毫秒，时间会"跳一秒"

上面事实 3 提到的：`22:34:05.930318` 存进 `datetime` 列，读出来是 `22:34:06`。

原因是 MySQL 的 `datetime` 默认精度是**秒**，小数部分会**四舍五入**（不是截断）。

**这个坑的实际影响**：如果你用 `create_time` 做"两条记录谁先谁后"的判断，同一秒内的两条记录分不出先后。

**修法**：建表用 `datetime(3)`（毫秒）或 `datetime(6)`（微秒）。

**这个项目的所有时间列都是 `datetime`**，所以做"接口耗时统计""并发时序分析"时，时间精度不够用 —— 这是建表时的疏漏。

### 坑 3：我以为 `setCreateTime` 是多余的

看到代码里手写 `cart.setCreateTime(LocalDateTime.now())`，第一反应是"实体上不是标了自动填充吗，这不是重复了？"

**确实重复了，但无害**：`strictInsertFill` 发现字段非 null 就跳过，不会覆盖。

**但如果理解错了机制就危险了**：有人可能以为"手动 set 会覆盖自动填充"，于是所有地方都手动 set —— 那自动填充就白写了，又回到"每处四行"的老路上。

**正确的心智模型**：

```
自动填充 = 兜底（你没设，我帮你设）
手动 set = 优先（你设了，我不动）
```

### 坑 4：`updateById` 会把 `create_time` 也写进去

第 2 次加购的 UPDATE 里，`create_time='2026-10-27 22:34:06'` 也被 SET 了。

**这是"查出来再改再存"的必然结果**：对象是完整的，所有字段都非 null，全都进 SET。

**如果这期间 `create_time` 被别的逻辑改过（理论上不该），这次 UPDATE 会把它覆盖回旧值。**

**更规范的做法**：更新时用 `new` 一个空实体只 set 要改的字段（像精讲 08 的接单那样），避免全字段覆盖。

**但购物车这里必须用完整对象** —— 因为 `number` 和 `amount` 是基于旧值算的（`existing.getNumber() + 1`），必须先查出来。

**所以"查出来再改"不是错，是要知道它的代价。**

## ⑦ 缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **`dishFlavor` 为 null 会误匹配** | 中 | 用户加购「微辣」后，前端漏传口味再加一次，会匹配到微辣那条，变成微辣 ×2 | null 统一按空串处理，或菜品有口味时强制校验 |
| **全字段 UPDATE 有丢失更新风险** | 中 | `existing` 是完整对象，会覆盖别人刚改的字段 | 用 `lambdaUpdate()` 只 set 需要改的列 |
| **没有校验购物车上限** | 低 | 用户可以加 9999 份，或加 1000 种商品 | 加数量上限和条目上限 |
| **没有校验菜品是否起售** | 中 | 停售的菜品也能加进购物车（`fillGoodsInfo` 不查 `status`） | 加 `status = ENABLE` 校验 |
| **没有清理失效商品** | 低 | 菜品被删后，购物车里那条还在，`name`/`image` 是快照还能显示，但下单会失败 | 下单前统一校验，或定时清理 |
| **`setmeal` 分支没校验套餐起售** | 中 | 同上 | 同上 |

### 「`dishFlavor` 为 null 会误匹配」是最值得说的一个

这是一个**真实的、能复现的边界 bug**：

```
第 1 次：{"dishId":1, "dishFlavor":"微辣"}    → 插入 (dish_id=1, dish_flavor='微辣', number=1)
第 2 次：{"dishId":1}                        → dishFlavor 是 null
         → WHERE 只拼 user_id=4 AND dish_id=1（口味条件不拼）
         → 匹配到刚才那条「微辣」
         → number 变成 2

用户以为加的是"不辣"，实际加到"微辣"上了。
```

**这个 bug 在当前前端不会触发**（前端总是传口味），但只要有一个入口漏传（比如"再来一单"直接调加购），就会静默出错。

**修法有三层，从轻到重：**

1. **规范 null**：`cart.setDishFlavor(dto.getDishFlavor() == null ? "" : dto.getDishFlavor())`，查重时条件永远拼上
2. **业务校验**：菜品有口味（`dish_flavor` 表有记录）时，强制要求传口味
3. **数据库约束**：`UNIQUE KEY (user_id, dish_id, setmeal_id, dish_flavor)` —— 让数据库兜底

**第 3 种最彻底**：并发下两个请求同时"查不到"然后都插入，只有唯一索引能挡住。

**面试如果被问"这段代码有什么边界问题"，能答出这个 + 说出唯一索引的兜底方案，就是"真懂"而不是"看过"。**

## ⑧ 面试 30 秒版

> 加购接口前端只传 `dishId` 和口味，**价格和菜名都是后端查 dish 表补的**，不信前端。`userId` 从 ThreadLocal 拿而不是从参数拿，否则 A 用户能往 B 用户购物车塞东西。
>
> 查重用 MyBatis-Plus 的动态条件 `eq(布尔, 列, 值)`：菜品拼 `dish_id`、套餐拼 `setmeal_id`、有口味才拼 `dish_flavor`，一个方法覆盖四种组合。已存在就数量 +1 并按**最新价**刷新单价 —— 因为**购物车用活价、订单用死价**，快照只在下单那一刻固化。
>
> 我抓 SQL 验证过两件事：一是 `INSERT INTO shopping_cart` 的字段列表里只有 `create_time`，没有 `create_user`，因为购物车表没这列、实体也没标填充注解，`strictInsertFill` 自动跳过了；二是 `amount` 存的是**单价**不是总价，`orders.amount` 才是总额。
>
> 已知边界问题：口味为 null 时查重条件不拼口味，会误匹配到之前选了口味的那条。修法是 null 规范成空串，或者在 `(user_id, dish_id, dish_flavor)` 上建唯一索引让数据库兜底。
