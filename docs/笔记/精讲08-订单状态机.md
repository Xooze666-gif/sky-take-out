# 精讲 08 · 订单状态机：从接单到完成

> 源码位置：`OrderServiceImpl`（`confirm` / `rejection` / `delivery` / `complete` / `cancel`）
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版

---

## ① 场景

用户付完钱，订单进入商家端。接下来是一串状态推进：

```
1 待付款 → 2 待接单 → 3 已接单 → 4 派送中 → 5 已完成
                ↓
             6 已取消（拒单/用户取消）
```

四个按钮，四个接口：

| 动作 | 接口 | 允许的前置状态 | 目标状态 |
|---|---|---|---|
| 接单 | `PUT /admin/order/confirm` | 2 待接单 | 3 已接单 |
| 拒单 | `PUT /admin/order/rejection` | 2 待接单 | 6 已取消（+退款） |
| 派送 | `PUT /admin/order/delivery/{id}` | 3 已接单 | 4 派送中 |
| 完成 | `PUT /admin/order/complete/{id}` | 4 派送中 | 5 已完成 |

**这张表就是"状态机"的全部内容。** 每个接口只接受一个前置状态，其他一律拒绝。

## ② 数据：执行前 → 执行后

**执行前**，`orders` 表（真实数据）：

| id | number | status | pay_status | amount | delivery_time |
|---|---|---|---|---|---|
| 1 | 2026101700000001 | **5 已完成** | 1 | 88.00 | NULL |
| 4 | 20261018141859582146 | **2 待接单** | 1 | 38.00 | NULL |

**执行后**（对订单 4 走完三步）：

| id | status | delivery_time |
|---|---|---|
| 4 | **5 已完成** | 2026-10-27 22:41:55 |

**注意只有两列变了：`status` 和 `delivery_time`。** 其他 20 列一个都没动。

这跟精讲 03 里「支付」的行为形成鲜明对比——支付是**全字段 UPDATE**（18 个字段），状态流转是**单字段 UPDATE**。原因在下一层。

## ③ 逐行拆

### `confirm`：最短的完整例子

```java
@Override
public void confirm(Orders orders) {
    Orders db = orderMapper.selectById(orders.getId());       // ① 查当前状态
    if (db == null) {
        throw new BaseException(MessageConstant.ORDER_NOT_FOUND);
    }
    if (!OrderStatusConstant.TO_BE_CONFIRMED.equals(db.getStatus())) {   // ② 状态守卫
        throw new BaseException(MessageConstant.ORDER_STATUS_ERROR);
    }

    Orders update = new Orders();       // ③ 新建空实体，只填两个字段
    update.setId(orders.getId());
    update.setStatus(OrderStatusConstant.CONFIRMED);
    orderMapper.updateById(update);     // ④ 生成单字段 UPDATE
}
```

**第 ① 步：为什么要查一次？**

因为 `orders` 参数是前端传来的，里面只有 `id`（可能还有其他字段）。**订单当前是什么状态，前端说了不算，必须查库。**

**这一步是所有状态机的基础：不信任前端传来的状态。**

**第 ② 步：守卫。** `!TO_BE_CONFIRMED.equals(db.getStatus())` —— 只要不是"待接单"，一律拒绝。

**注意 `常量.equals(变量)` 的顺序，不是 `变量.equals(常量)`。** 如果 `db.getStatus()` 是 `null`（数据库里 status 允许 NULL 的话），`null.equals(...)` 直接 NPE；而 `常量.equals(null)` 返回 `false`，安全。

**这个"常量在前"的写法，是 Java 里防 NPE 的肌肉记忆。** 面试有时会问"为什么 `"abc".equals(str)` 比 `str.equals("abc")` 好"，就是这个原因。

**第 ③ 步是理解"为什么只 UPDATE 一个字段"的关键：**

```java
Orders update = new Orders();     // ← new 出来的对象，所有字段都是 null
update.setId(orders.getId());
update.setStatus(OrderStatusConstant.CONFIRMED);
// 其他 20 个字段全是 null
```

MyBatis-Plus 的 `updateById` 默认策略是 `FieldStrategy.NOT_NULL`：**只把非 null 的字段拼进 `SET` 子句**。所以生成的 SQL 是：

```sql
UPDATE orders SET status=3 WHERE id=4
```

**而不是**

```sql
UPDATE orders SET number=..., status=3, amount=..., remark=... WHERE id=4
```

**这是本项目里一个非常实用的技巧：`new` 一个空实体，只 set 要改的字段，就实现了"精准更新"。**

对比精讲 03 的 `payment`：

```java
Orders order = orderMapper.selectOne(...);   // ← 查出来的是完整对象，20 个字段都有值
order.setPayStatus(PAID);
order.setStatus(TO_BE_CONFIRMED);
order.setCheckoutTime(now);
orderMapper.updateById(order);               // ← 20 个字段全进 SET
```

同一个 `updateById`，两种行为，差别只在**传进去的对象是"查出来的"还是"new 出来的"**。

### `rejection`：拒单要连带退款

```java
Orders update = new Orders();
update.setId(orders.getId());
update.setStatus(OrderStatusConstant.CANCELLED);         // 6 已取消
update.setRejectionReason(orders.getRejectionReason());  // 拒单原因（前端传）
update.setCancelTime(LocalDateTime.now());
update.setPayStatus(PayStatusConstant.REFUND);           // 2 退款
orderMapper.updateById(update);
```

**这里有个信任边界**：`rejectionReason` 是前端传的，直接落库。这没问题（它是文案，不是金额），但如果前端传个 5000 字的字符串，会撑爆字段。生产上要加长度校验。

**注意 `setPayStatus(REFUND)` 只是"标记退款"，没有真的调微信退款接口。** 注释里写了"简化：直接标记退款状态"。真实系统这里要：

```
1. 调微信退款 API（要证书、签名、异步回调）
2. 退款回调到达后，才把 pay_status 改成 2
3. 中间状态应该是"退款中"（比如 3），不能直接跳到"已退款"
```

现在这个实现是"标记即退款"，如果退款 API 失败，钱没退但状态显示已退——**这是钱相关的严重缺口**。

### `delivery` / `complete`：结构完全一样

```java
public void delivery(Long id) {
    Orders db = orderMapper.selectById(id);
    if (db == null) throw new BaseException(ORDER_NOT_FOUND);
    if (!CONFIRMED.equals(db.getStatus())) throw new BaseException(ORDER_STATUS_ERROR);   // 必须"已接单"

    Orders update = new Orders();
    update.setId(id);
    update.setStatus(DELIVERY_IN_PROGRESS);
    orderMapper.updateById(update);
}

public void complete(Long id) {
    Orders db = orderMapper.selectById(id);
    if (db == null) throw new BaseException(ORDER_NOT_FOUND);
    if (!DELIVERY_IN_PROGRESS.equals(db.getStatus())) throw new BaseException(ORDER_STATUS_ERROR);  // 必须"派送中"

    Orders update = new Orders();
    update.setId(id);
    update.setStatus(COMPLETED);
    update.setDeliveryTime(LocalDateTime.now());    // ← 只有这里多一个字段
    orderMapper.updateById(update);
}
```

**这三个方法（`confirm`/`delivery`/`complete`）的结构完全一样**：查 → 判状态 → new 空实体 → 改状态 → update。

**这个"重复"其实是好的。** 有人会想把它们抽成一个通用方法：

```java
private void transit(Long id, Integer from, Integer to) { ... }
```

但那样会丢掉"业务语义"：`complete` 要记 `delivery_time`，`rejection` 要记原因和退款，`cancel` 要记取消原因和时间。**每个状态流转都有自己的副作用，"看起来一样"只是暂时的。**

**过早抽象比重复更贵。** 三个方法各 10 行，一眼能看懂；抽成通用方法后，每个调用点都要传 `from`/`to` 两个魔法数字，可读性反而下降。

### `cancel`：用户取消，允许两个前置状态

```java
if (!(PENDING_PAYMENT.equals(order.getStatus())
        || TO_BE_CONFIRMED.equals(order.getStatus()))) {
    throw new BaseException(MessageConstant.ORDER_STATUS_ERROR);
}
```

**这是唯一一个"多前置状态"的流转。**

业务理由：
- `1 待付款`：还没付钱，随时能取消
- `2 待接单`：付了钱但商家还没接，也应该能取消（不然用户被锁死）

一旦到了 `3 已接单`，商家已经开始做了（可能菜已经下锅），就不让取消了——要走"申请退款"流程（这个项目没做）。

## ④ SQL 实况（真实抓取）

### 场景 A：非法跳转（对已完成订单 id=1 点接单）

```sql
SELECT id,number,status,user_id,address_book_id,order_time,checkout_time,pay_method,pay_status,
       amount,remark,phone,address,consignee,cancel_reason,rejection_reason,cancel_time,
       estimated_delivery_time,delivery_status,delivery_time,pack_amount,tableware_number,tableware_status
FROM orders WHERE id=1
```

响应：`{"code":0,"msg":"订单状态错误"}`

**只有 1 条 SELECT，没有任何 UPDATE。**

这是"守卫生效"的铁证：请求读到了订单（`status=5`），发现不是"待接单"，直接抛异常，**根本没走到写库**。

### 场景 B：合法接单（订单 4，2→3）

```sql
SELECT id,number,status,... FROM orders WHERE id=4

UPDATE orders SET status=3 WHERE id=4
```

**注意 `UPDATE` 只有 `status=3` 一个字段。**

### 场景 C：派送（3→4）

```sql
SELECT id,number,status,... FROM orders WHERE id=4
UPDATE orders SET status=4 WHERE id=4
```

### 场景 D：完成（4→5）

```sql
SELECT id,number,status,... FROM orders WHERE id=4
UPDATE orders SET status=5, delivery_time='2026-10-27 22:41:55.399585' WHERE id=4
```

**只有"完成"多带了一个 `delivery_time`。** 三个 UPDATE 放在一起对比，能清楚看到"每个状态流转的副作用不一样"。

### 一个意外发现：`orders` 表没有 `update_time`

我本来想看看"接单时有没有记录操作人"，于是查了：

```sql
UPDATE orders SET status=3 WHERE id=4
```

**没有 `update_time`，没有 `update_user`。**

再看表结构：

```sql
SELECT column_name FROM information_schema.columns
WHERE table_schema='sky_take_out' AND table_name='orders' ORDER BY ordinal_position;
```

结果：

```
id, number, status, user_id, address_book_id, order_time, checkout_time, pay_method,
pay_status, amount, remark, phone, address, consignee, cancel_reason, rejection_reason,
cancel_time, estimated_delivery_time, delivery_status, delivery_time, pack_amount,
tableware_number, tableware_status
```

**23 个字段，没有 `create_time`、`update_time`、`create_user`、`update_user`。**

验证：

```sql
SELECT count(*) FROM information_schema.columns
WHERE table_schema='sky_take_out' AND table_name='orders'
  AND column_name IN ('create_time','update_time','update_user');
-- 结果：0
```

**这意味着两件事：**

1. **自动填充在订单表上完全不生效。** `MyMetaObjectHandler` 里的 `strictInsertFill(metaObject, "updateTime", ...)` 会因为实体上没标 `@TableField(fill=...)` 而跳过。不会报错，静默跳过。
2. **订单没有"时间轴"。** 只有 `order_time`（下单）、`checkout_time`（支付）、`delivery_time`（送达）、`cancel_time`（取消）。**接单时间、派送开始时间都没记。**

**这是一个真实的设计缺口。** 商家想看"平均接单时长"（从支付到接单），现在算不出来——因为没记接单时间。

正确做法应该是加一张 `order_status_log` 表：

```sql
CREATE TABLE order_status_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_id BIGINT NOT NULL,
  from_status INT,
  to_status INT NOT NULL,
  operator_id BIGINT,        -- 谁操作的
  operator_type TINYINT,     -- 1商家 2用户 3系统
  remark VARCHAR(255),
  create_time DATETIME NOT NULL
);
```

每次状态流转插一条。这样既能算时长，又能审计，还能做"订单轨迹"页面（用户端很常见的功能）。

## ⑤ 权衡：`check-then-act` vs 条件更新

这一段是本篇最重要的地方。

**当前写法是 `check-then-act`：**

```java
Orders db = orderMapper.selectById(id);        // ① 检查
if (!TO_BE_CONFIRMED.equals(db.getStatus()))   // ② 判断
    throw ...;
orderMapper.updateById(update);                // ③ 执行
```

**问题：① 和 ③ 之间有一个窗口。**

```
时刻 T1: 请求 A 读到 status=2，通过检查
时刻 T2: 请求 B 读到 status=2，通过检查
时刻 T3: 请求 A 执行 UPDATE SET status=3
时刻 T4: 请求 B 执行 UPDATE SET status=3     ← 重复接单，但结果一样，无害

但如果 B 是「拒单」呢？
时刻 T4: 请求 B 执行 UPDATE SET status=6, pay_status=2(退款)
→ 订单被接单了，又被拒单退款了。商家要做菜，钱退了。
```

**这就是经典的 TOCTOU 竞态。** 网络重试、用户连点、两个店员同时操作，都能触发。

**更稳的写法：条件更新（一条 SQL 解决）**

```java
// 一条 SQL 完成"检查 + 更新"
int rows = orderMapper.update(null, Wrappers.<Orders>lambdaUpdate()
        .eq(Orders::getId, id)
        .eq(Orders::getStatus, OrderStatusConstant.TO_BE_CONFIRMED)   // 状态作为 WHERE 条件
        .set(Orders::getStatus, OrderStatusConstant.CONFIRMED));

if (rows == 0) {
    throw new BaseException(MessageConstant.ORDER_STATUS_ERROR);   // 没更新到 = 状态不对
}
```

生成的 SQL：

```sql
UPDATE orders SET status=3 WHERE id=4 AND status=2
```

**为什么这是原子的？** 因为 InnoDB 的 `UPDATE` 会对匹配的行加排他锁，`WHERE status=2` 的判断和 `SET status=3` 在**同一把锁**内完成。两个并发请求只有一个能匹配到行，另一个 `rows=0`。

**对比：**

| | check-then-act（当前） | 条件更新（更好） |
|---|---|---|
| SQL 数量 | 2 条（SELECT + UPDATE） | **1 条** |
| 是否原子 | ❌ 有窗口 | ✅ 原子 |
| 并发重复操作 | 可能都成功 | 只有一个成功 |
| 能不能区分"订单不存在"和"状态不对" | 能（查不到就是不存在） | 不能（都是 rows=0） |

**最后一个缺点是真实代价。** 条件更新丢失了"订单不存在"和"状态错误"的区别，需要额外查一次才能给出准确提示。

**实际工程中的折中**：先查（给出准确错误提示），再用条件更新（保证原子），检查 rows：

```java
Orders db = orderMapper.selectById(id);
if (db == null) throw new BaseException(ORDER_NOT_FOUND);
if (!TO_BE_CONFIRMED.equals(db.getStatus())) throw new BaseException(ORDER_STATUS_ERROR);

int rows = orderMapper.update(null, Wrappers.<Orders>lambdaUpdate()
        .eq(Orders::getId, id)
        .eq(Orders::getStatus, TO_BE_CONFIRMED)
        .set(Orders::getStatus, CONFIRMED));

if (rows == 0) throw new BaseException("订单状态已变更，请刷新后重试");   // 并发兜底
```

**多一次查询换准确的错误提示，再用条件更新兜住并发 —— 这是可接受的平衡。**

### 顺带说：为什么不用"状态机引擎"？

有 Spring StateMachine 这种框架，也可以自己用枚举 + Map 定义合法流转。

**这个项目不需要**，因为状态少（6 个）、流转固定（线性 + 一个分支）。手写 `if` 判断反而最直观。

**什么时候该上状态机引擎？** 状态超过 10 个、流转是网状（不是线性）、不同角色有不同权限、需要可视化配置。订单状态只有 6 个且基本线性，上引擎是过度设计。

**面试如果被问"你会用状态机模式吗"，答"看复杂度，这个项目的状态流转线性且少，手写守卫更清晰；如果状态和流转组合爆炸，才值得上引擎"。** 这比"我会用 XX 框架"更成熟。

## ⑥ 踩坑实录

### 坑 1：我用 query 参数调 `confirm`，报 `Required request body is missing`

第一次测接单，我按习惯写：

```bash
curl -X PUT "http://localhost:8080/admin/order/confirm?id=5" -H "token: $AT"
```

返回：

```json
{"code":0,"msg":"未知错误"}
```

日志里是：

```
org.springframework.http.converter.HttpMessageNotReadableException:
Required request body is missing: public com.sky.result.Result<java.lang.Void>
com.sky.controller.admin.OrderController.confirm(com.sky.entity.Orders)
```

**原因：** 接口签名是 `confirm(@RequestBody Orders orders)`，`@RequestBody` 要求必须有一个 JSON body。我只传了 query 参数，body 是空的 → Spring 在参数绑定阶段就抛异常，**连 Service 都没进**（所以抓 SQL 时一条都没有）。

正确姿势：

```bash
curl -X PUT "http://localhost:8080/admin/order/confirm" \
  -H "Content-Type: application/json" -H "token: $AT" \
  -d '{"id":5}'
```

**这个坑的价值不在于"改对参数"，而在于它暴露了一个设计问题** —— 见第 ⑦ 层的"接口暴露整个实体"。

### 坑 2：这个异常被兜成了"未知错误"，看不出问题

`Required request body is missing` 是 `HttpMessageNotReadableException`，它不属于 `BaseException`，也不属于 `DuplicateKeyException`，所以落到最后一层：

```java
@ExceptionHandler(Exception.class)
public Result<String> handleException(Exception ex) {
    log.error("系统异常", ex);
    return Result.error(MessageConstant.UNKNOWN_ERROR);   // "未知错误"
}
```

**前端只看到"未知错误"，完全不知道是参数格式错了。**

这是 `GlobalExceptionHandler` 的一个真实缺口：**参数校验类异常（`HttpMessageNotReadableException`、`MethodArgumentNotValidException`、`MissingServletRequestParameterException`）应该单独处理，返回"请求参数错误"而不是"未知错误"。**

生产上这四个 handler 是标配：

```java
@ExceptionHandler(HttpMessageNotReadableException.class)   // JSON 格式错/缺 body
@ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid 校验失败
@ExceptionHandler(MissingServletRequestParameterException.class)  // 缺必填参数
@ExceptionHandler(BaseException.class)                     // 业务异常
```

### 坑 3：`orders` 表没有 `update_time`，我一开始以为自动填充坏了

看到 `UPDATE orders SET status=3` 里没有 `update_time`，第一反应是"`MyMetaObjectHandler` 没生效"。

查了表结构才明白：**`orders` 表根本没这两列**，所以是 `strictUpdateFill` 正确地跳过了（详见精讲 12）。

**但换个角度想：这其实是设计漏了，不是自动填充坏了。** 订单表比任何表都更需要"谁在什么时候接的单"。

## ⑦ 缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **`check-then-act` 竞态** | **高** | 检查状态和更新状态分两条 SQL，并发下双成功 | 改条件更新 `WHERE id=? AND status=?`，判 rows |
| **拒单只标记退款，没真退款** | **高（钱相关）** | `setPayStatus(REFUND)` 直接改状态，退款 API 失败也不回滚 | 引入"退款中"中间态 + 退款回调 |
| **订单没有状态流转日志** | 中 | 没有接单时间、派送时间、操作人，算不出时效也查不了责任 | 加 `order_status_log` 表 |
| **`confirm`/`rejection` 收整个 `Orders` 实体** | 中 | 接口暴露 23 个字段，前端能传 `amount`、`payStatus` 等敏感字段（虽然当前没被使用，但未来改动容易踩雷） | 定义 `OrderConfirmDTO { Long id; String rejectionReason; }` |
| **状态值是 int 魔术数字** | 低 | `status == 5` 出现在 SQL 和 Java 里，可读性差 | 已抽了 `OrderStatusConstant`，但 SQL 里还是硬编码 5（见精讲 10） |
| **没有权限区分** | 中 | 任何管理员都能接单/拒单/取消，真实业务里"接单"是店员权限，"取消"是店长权限 | 加角色权限模型 |
| **取消订单没有退款** | 中 | 用户取消已支付订单，`pay_status` 不变，钱不退 | 同上，补退款流程 |

### 「拒单只标记不退款」值得单独说

这是全项目**唯一涉及钱的缺口**，面试如果聊到订单，一定会被追问。

现在的代码：

```java
update.setStatus(CANCELLED);
update.setPayStatus(PayStatusConstant.REFUND);   // 直接把"已支付"改成"已退款"
orderMapper.updateById(update);
```

**如果真实的微信退款接口调用失败（网络、余额不足、订单超过可退期限），会怎样？** 状态显示"已退款"，但用户没收到钱。用户投诉，客服查系统显示"已退款"，无法处理。

**正确流程：**

```
商家点拒单
  → 订单状态 2 → 6（已取消）
  → 支付状态 1（已支付）→ 3（退款中）      ← 新状态
  → 调微信退款 API
     ├─ 同步成功：等回调
     └─ 同步失败：回滚状态，提示商家重试
  → 微信退款回调到达 → 支付状态 3 → 2（已退款）
```

**核心原则：涉及资金的状态，必须以「外部系统的确认」为准，不能本地直接标记。**

## ⑧ 面试 30 秒版

> 订单是状态机：1 待付款 → 2 待接单 → 3 已接单 → 4 派送中 → 5 已完成，加一个 6 已取消。每个流转接口都做前置状态守卫——接单必须"待接单"，派送必须"已接单"，非法跳转直接拒绝。我抓 SQL 验证过：对已完成订单点接单，只有一条 SELECT，没有任何 UPDATE，说明守卫在写库之前就拦住了。
>
> 更新用 `new Orders()` 只 set id 和 status，靠 MyBatis-Plus 的 `NOT_NULL` 策略生成 `UPDATE orders SET status=3 WHERE id=4`，只改一个字段。对比支付那里查完整对象再更新，会生成 18 个字段的全量 UPDATE——同一个 `updateById`，行为差别在传进去的对象是"new 的"还是"查出来的"。
>
> 已知问题：现在是 check-then-act，先查状态再更新，中间有并发窗口，两个请求可能都通过检查。更稳的写法是把状态作为 UPDATE 的 WHERE 条件：`UPDATE ... WHERE id=? AND status=2`，然后判影响行数，一条 SQL 原子完成。另外拒单那里"标记退款"不等于"真退款"，生产必须走"退款中"中间态 + 回调确认。
