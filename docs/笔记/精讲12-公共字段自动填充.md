# 精讲 12 · 公共字段自动填充：`MyMetaObjectHandler`

> 源码位置：`MyMetaObjectHandler` + 各实体上的 `@TableField(fill = ...)`
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版

---

## ① 场景

几乎每个「新增」「修改」接口，都要顺手填这么四个字段：

```sql
create_time   创建时间
update_time   更新时间
create_user   创建人 id
update_user   修改人 id
```

项目里有 **10+ 处**新增/修改：员工、分类、菜品、套餐、购物车、地址、订单……

**如果每处都手写**：

```java
dish.setCreateTime(LocalDateTime.now());
dish.setUpdateTime(LocalDateTime.now());
dish.setCreateUser(BaseContext.getCurrentId());
dish.setUpdateUser(BaseContext.getCurrentId());
dishMapper.insert(dish);
```

四行 × 十几处 = 几十行重复代码，而且**只要漏写一处，就会出现 `create_time` 为 null 的脏数据**（如果数据库列是 `NOT NULL`，直接报错；如果是 `NULL`，那就静默污染）。

**自动填充要解决的就是这个"横切关注点"。**

---

## ② 数据：谁被填了、谁没被填

先看**实际标注情况**（我 grep 了全部实体）：

| 实体 | 表 | 标了几个字段 | 具体 |
|---|---|---|---|
| `Employee` | employee | **4 个** | createTime, updateTime, createUser, updateUser |
| `Dish` | dish | **4 个** | 同上 |
| `Category` | category | **4 个** | 同上 |
| `Setmeal` | setmeal | **4 个** | 同上 |
| `ShoppingCart` | shopping_cart | **1 个** | 只有 createTime |
| `User` | user | **1 个** | 只有 createTime |
| `Orders` | orders | **0 个** | 一个都没有（只有一行 import，没用上） |
| `DishFlavor` | dish_flavor | 0 个 | 表里没这四列 |
| `SetmealDish` | setmeal_dish | 0 个 | 表里没这四列 |
| `OrderDetail` | order_detail | 0 个 | 表里没这四列 |

**为什么差距这么大？不是漏了，是故意的：**

- `shopping_cart` / `user`：**表里根本没有 `create_user`/`update_user` 列**。购物车是用户自己加的，用户表是 C 端自己注册的，"谁操作"没有意义。
- `orders`：表里也没有这四列（我用 `information_schema` 查过，0 个匹配）。
- `dish_flavor` / `setmeal_dish` / `order_detail`：子表，只有业务字段。

**关键：handler 里的代码是"每张表都填四个"，但实际效果"每张表只填它声明过的"。** 这个差异怎么实现的，就是下一层的重点。

## ③ 逐行拆

### handler 全文（50 行，每一行都有用）

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {
        LocalDateTime now = LocalDateTime.now();      // ① 同一个时间戳
        Long operatorId = currentOperatorId();        // ② 同一个操作人

        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, now);
        this.strictInsertFill(metaObject, "updateTime", LocalDateTime.class, now);
        this.strictInsertFill(metaObject, "createUser", Long.class, operatorId);
        this.strictInsertFill(metaObject, "updateUser", Long.class, operatorId);
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
        this.strictUpdateFill(metaObject, "updateUser", Long.class, currentOperatorId());
    }

    private Long currentOperatorId() {
        Long id = BaseContext.getCurrentId();
        return id == null ? 0L : id;                  // ③ null 兜底
    }
}
```

### 第 ① 行：`now` 只取一次

```java
LocalDateTime now = LocalDateTime.now();
```

**如果写成 `strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now())` 和 `strictInsertFill(metaObject, "updateTime", ..., LocalDateTime.now())`，两次 `now()` 会差几微秒。**

结果：`create_time = 22:42:21.177684`、`update_time = 22:42:21.178012`。

**这会导致一个问题**：任何"`create_time == update_time` 说明这条记录从没被改过"的判断都会失效。虽然业务上很少这么判，但**同一个逻辑时刻应该用同一个时间戳**，这是基本要求。

**抓到的 SQL 印证了这一点**：

```sql
INSERT INTO dish (...) VALUES (..., '2026-10-27 22:40:55.133745', '2026-10-27 22:40:55.133745', 1, 1)
                                            ↑ create_time                   ↑ update_time
```

**两个时间到微秒都完全一致。**

### 第 ② 行：`operatorId` 也只取一次

同理，避免 `create_user` 和 `update_user` 不一致（虽然实际上不会，但语义上应该一致）。

### 第 ③ 行：`id == null ? 0L : id` 的兜底

```java
private Long currentOperatorId() {
    Long id = BaseContext.getCurrentId();
    return id == null ? 0L : id;
}
```

**什么时候 ThreadLocal 是空的？**

1. **数据初始化脚本**：`CommandLineRunner` 里插种子数据，没有 HTTP 请求，自然没有拦截器
2. **定时任务**：`@Scheduled` 跑在独立线程，没有请求上下文
3. **单元测试**：直接调 Service，不走拦截器
4. **`@Async` 异步方法**：ThreadLocal 不会跨线程传递
5. **WebSocket 回调**：跑在容器 IO 线程

**这时候如果直接 `setCreateUser(null)`：**

- 数据库列是 `NOT NULL` → 报错
- 数据库列是 `NULL` 允许 → 存了个 null，将来 `WHERE create_user = ?` 查不到这些记录

**用 `0L` 表示"系统操作"**，是个约定俗成的做法（Unix 的 root 用户也是 uid=0）。

**注意：如果 `create_user` 列有外键指向 `employee.id`，`0` 这个值会违反外键约束**（因为没有 id=0 的员工）。这个项目没建外键，所以没事。

### `strictInsertFill` 的 "strict" 到底严格在哪

这是全篇最重要的概念。

**`MetaObjectHandler` 有两个版本的方法：**

```java
// 非 strict 版本
default MetaObjectHandler fillStrategy(MetaObject metaObject, String fieldName, Object fieldVal)
// strict 版本
default <T, E extends T> MetaObjectHandler strictInsertFill(
        MetaObject metaObject, String fieldName, Class<T> fieldType, E fieldVal)
```

**两者的区别：**

| | 非 strict | **strict** |
|---|---|---|
| 检查字段上有没有 `@TableField(fill=...)` | ❌ 不检查 | **✅ 检查** |
| 字段不存在时 | 报错或静默失败 | **跳过** |
| 能否一个 handler 服务所有表 | 不能（会去填不存在的列） | **能** |

**`strictInsertFill` 的内部逻辑（简化）：**

```java
// MyBatis-Plus 源码逻辑
TableInfo tableInfo = findTableInfo(metaObject);
TableFieldInfo fieldInfo = tableInfo.getFieldList().stream()
        .filter(f -> f.getProperty().equals(fieldName))
        .findFirst().orElse(null);

if (fieldInfo == null) {
    return this;                 // ① 实体里没这个字段 → 跳过
}
FieldFill fill = fieldInfo.getFieldFill();
if (fill != FieldFill.INSERT && fill != FieldFill.INSERT_UPDATE) {
    return this;                 // ② 标的是 UPDATE 或 DEFAULT → 跳过
}
// ③ 只有在当前值为 null 时才填
if (getFieldValByName(fieldName, metaObject) == null) {
    setFieldValByName(fieldName, fieldVal, metaObject);
}
```

**三个"跳过"的条件，每一个都对应一个真实场景：**

**① 实体里没这个字段 → 跳过**

比如 `DishFlavor` 实体只有 `id`、`dishId`、`name`、`value` 四个属性。`strictInsertFill(metaObject, "createUser", ...)` 找不到 `createUser` 属性，直接跳过。

**如果用非 strict 版本，会尝试 `metaObject.setValue("createUser", 0L)` → 抛 `ReflectionException: There is no getter for property named 'createUser'`。**

**② 标的是 `FieldFill.UPDATE` 或没标 → 跳过**

比如 `ShoppingCart` 只标了 `createTime`。

```java
@TableField(fill = FieldFill.INSERT)
private LocalDateTime createTime;
// 没有 updateTime / createUser / updateUser
```

handler 里那 4 行 `strictInsertFill`：
- `createTime` → 标了 `INSERT`，**填**
- `updateTime` / `createUser` / `updateUser` → 实体里没这仨属性，**跳过**

**所以购物车插入时只有 `create_time` 被填。** 这就是"一个 handler 服务所有表"的机制。

**③ 当前值非 null → 跳过**

```java
// 如果你在 Service 里手动设了
dish.setCreateTime(LocalDateTime.of(2020, 1, 1, 0, 0));
dishMapper.insert(dish);
// handler 不会覆盖，存进去的还是 2020-01-01
```

**这个特性有用**：数据迁移时想保留原始创建时间，手动 set 一下就行，不用改 handler。

**但也可能踩坑**：如果你 `new` 一个实体时，某个字段被 `BeanUtils.copyProperties` 从 DTO 拷了个非 null 值（比如前端传了 `updateTime`），handler 就不会填——**存进去的是前端传的时间**。

### `updateFill` 为什么只有两个字段

```java
public void updateFill(MetaObject metaObject) {
    this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    this.strictUpdateFill(metaObject, "updateUser", Long.class, currentOperatorId());
}
```

**没有 `createTime` 和 `createUser`。**

因为"创建时间/创建人"在记录创建后就应该**永不改变**。更新时去改它，就把"这条记录是谁什么时候建的"这个事实抹掉了。

**注意 `strictUpdateFill` 检查的是 `FieldFill.UPDATE` 或 `FieldFill.INSERT_UPDATE`**：

```java
@TableField(fill = FieldFill.INSERT)          // createTime：只有 INSERT 才算
@TableField(fill = FieldFill.INSERT_UPDATE)   // updateTime：UPDATE 也填
```

所以 `updateFill` 里的两行只会命中 `updateTime` 和 `updateUser`（它们标的是 `INSERT_UPDATE`）。

**`createTime` 就算被误写进 `updateFill`，`strictUpdateFill` 也会跳过它**（因为标的是 `INSERT`，不是 `UPDATE` 或 `INSERT_UPDATE`）。

**这是"声明式"的好处：规则写在实体上，handler 只需要"试着填"，填不填由声明决定。**

## ④ SQL 实况（真实抓取，四张表对比）

这是本篇最有价值的部分——**同一个 handler，四张表四种行为**。

### 表 1：`dish`（标了 4 个字段）→ 填 4 个

```sql
INSERT INTO dish ( name, category_id, price, image, description, status,
                   create_time, update_time, create_user, update_user )
VALUES ( '测试麻婆豆腐', 3, 28.00, '...', '...', 1,
         '2026-10-27 22:40:55.133745', '2026-10-27 22:40:55.133745', 1, 1 )
```

**四个字段全有，时间到微秒完全一致。**

### 表 2：`employee`（标了 4 个字段）→ 填 4 个

```sql
INSERT INTO employee ( name, username, password, phone, sex, id_number, status,
                       create_time, update_time, create_user, update_user )
VALUES ( '测试员', 'test_precision', 'e10adc...', '13900000001', '1', '...', 1,
         '2026-10-27 22:42:21.177684', '2026-10-27 22:42:21.177684', 1, 1 )
```

### 表 3：`dish_flavor`（一个都没标）→ 填 0 个

```sql
INSERT INTO dish_flavor ( dish_id, name, value ) VALUES ( 14, '辣度', '["不辣","微辣","中辣"]' )
```

**只有三个业务字段，没有任何时间/操作人。**

因为 `DishFlavor` 实体里**没有这四个属性**，`strictInsertFill` 全部跳过。

**如果用的是非 strict 版本，这里会直接抛异常。** 这就是 strict 的价值。

### 表 4：`shopping_cart`（只标了 createTime）→ 填 1 个

（这是之前抓加购 SQL 时拿到的）

```sql
INSERT INTO shopping_cart ( user_id, dish_id, name, image, amount, number, create_time )
VALUES ( 4, 1, '水煮鱼', '...', 38.00, 1, '2026-10-27 22:31:05.123456' )
```

**只有 `create_time`，没有 `update_time` / `create_user` / `update_user`。**

因为 `ShoppingCart` 实体只标了 `createTime`，且表里确实没这三列。

### 表 5：`orders`（一个都没标）→ 更新时填 0 个

```sql
UPDATE orders SET status=3 WHERE id=4
```

**没有 `update_time`，没有 `update_user`。**

我查了 `orders` 表结构，确认它**根本没有**这四列：

```sql
SELECT count(*) FROM information_schema.columns
WHERE table_schema='sky_take_out' AND table_name='orders'
  AND column_name IN ('create_time','update_time','update_user');
-- 结果：0
```

**而且 `Orders.java` 第 3 行有一句 `import com.baomidou.mybatisplus.annotation.FieldFill;`，但整个类里没有一个 `@TableField(fill=...)`** —— 说明当初想过要标，最后没标，import 忘删了。

### 更新时的对比（最有意思的一组）

| 操作 | 生成的 SQL | 填了几个 |
|---|---|---|
| `UPDATE dish SET name=..., price=..., update_time='...', update_user=1 WHERE id=14` | 业务字段 + 2 个公共字段 | **2** |
| `UPDATE employee SET status=0, update_time='...', update_user=1 WHERE id=7` | 业务字段 + 2 个公共字段 | **2** |
| `UPDATE orders SET status=3 WHERE id=4` | 只有业务字段 | **0** |

**同一个 `updateById`，三张表填的字段数不同** —— 完全由实体上的注解决定。

**而且注意：`UPDATE` 里没有 `create_time` 和 `create_user`。** 因为 `updateFill` 只填两个，且 `createTime` 标的是 `INSERT`（`strictUpdateFill` 会跳过）。

## ⑤ 权衡

### MetaObjectHandler vs AOP（课程原版方案）

苍穹外卖课程里用的是另一套：自定义 `@AutoFill` 注解 + AOP 切面 + 反射。

| | **MetaObjectHandler（当前）** | AOP + 自定义注解 |
|---|---|---|
| 怎么判断"新增还是修改" | **框架在 SQL 组装前精确回调**，天生知道 | 切 Service 方法，靠方法名/注解猜 |
| 怎么找要填的字段 | 用 MP 已缓存的 `TableInfo` 元数据，**按属性名直接取** | **反射遍历实体的所有字段** |
| 额外依赖 | 无 | aspectj + 自定义注解 + 切面类 |
| 需要改的地方 | 实体上标注解 | 每个 Service 方法上加 `@AutoFill` 注解 |
| 对 XML 手写 SQL | 不生效（同） | 不生效（同） |
| 性能 | 无反射遍历 | 每次反射遍历所有字段 |

**最关键的优势：MetaObjectHandler 天然知道"这是 insert 还是 update"。**

因为它是 MyBatis-Plus 在 `insert`/`update` 方法的**内部**调用的：

```java
// MyBatis-Plus 的 insert 逻辑（简化）
public int insert(T entity) {
    ...
    if (metaObjectHandler != null) {
        metaObjectHandler.insertFill(metaObject);    // ← 明确知道是 insert
    }
    ...
}
```

而 AOP 是在 Service 方法外面切，它只能靠"方法叫 `save` 还是 `update`"或者"注解参数"来猜。

**这是"在正确的层次解决问题"的典型案例。**

**AOP 的唯一优势**：可以给"非 MP 的写操作"也加填充（比如 XML 手写 insert）。但那个场景很少。

### 为什么不用数据库的 `DEFAULT CURRENT_TIMESTAMP`

MySQL 支持：

```sql
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

**这样连 Java 代码都不用写，插入时自动填。**

**为什么项目没用？** 两个原因：

1. **`create_user` 填不了。** 数据库不知道"当前操作人是谁"（除非用 `SET @current_user = ?` 会话变量，很别扭）。
2. **项目用的是 `LocalDateTime`（Java 侧时间），不是 `TIMESTAMP`。** `DATETIME` 的 `DEFAULT CURRENT_TIMESTAMP` 用的是**数据库服务器时间**，`LocalDateTime.now()` 用的是**应用服务器时间**。两台机器时区/时钟不一致时，会出现"创建时间和业务时间差几小时"。

**这个项目用 Java 侧时间，是为了和应用日志、接口返回时间用同一个时钟源。**

**`ON UPDATE CURRENT_TIMESTAMP` 也填不了 `update_user`**，所以还是得靠 Java。

**结论：时间字段可以交给数据库，操作人字段必须交给应用。既然都要写 handler，不如两个都自己管，保持一致。**

### `strict` vs 非 strict，为什么不干脆用非 strict？

非 strict 的 `fillStrategy` 不检查注解，直接设值。看起来"更省事"（不用在实体上标注解），实际上：

**（1）字段不存在就报错。** `dish_flavor`、`setmeal_dish`、`order_detail` 这些子表实体没有 `createUser` 属性，非 strict 会抛 `ReflectionException`。

**（2）无法区分 `INSERT` 和 `INSERT_UPDATE`。** 非 strict 的 `insertFill` 和 `updateFill` 是分开的方法，你在 `insertFill` 里写什么就填什么，没有"这个字段更新时不填"的表达能力。

**（3）没法"有的表填、有的表不填"。** 声明式的好处就是"每个实体自己决定"。

**所以 strict 是必须的，不是可选的优化。**

## ⑥ 踩坑实录

### 坑 1：只写 handler 不标注解，字段全是 null

最初以为"写了 `MyMetaObjectHandler` 就自动生效"，结果新增菜品时 `create_time` 是 null。

**原因：`strictInsertFill` 发现实体上没标 `@TableField(fill=...)`，跳过了。**

**必须两层配合，缺一不可：**

```
实体标注解  ← "声明这个字段要填"
     +
handler 填 ← "真正执行填充"
```

**只有声明没有执行，字段是 null；只有执行没有声明，strict 直接跳过。** 两者是"声明 + 实现"的关系。

### 坑 2：XML 里手写的 insert 不触发填充

`MetaObjectHandler` 只在 **MyBatis-Plus 的 `BaseMapper.insert/update`** 时被调用。

如果你在 XML 里写：

```xml
<insert id="insertCustom">
    INSERT INTO dish (name, price) VALUES (#{name}, #{price})
</insert>
```

**handler 完全不会触发**，`create_time` 还是 null。

**判断方法**：看这个写操作是走 `mapper.insert(entity)` 还是走 XML 里的自定义方法。

**这个项目里所有的 XML 都是 `select`**（`DishMapper.xml`、`SetmealMapper.xml`、`ReportMapper.xml`），所以没踩这个坑。

**但如果将来加了"批量插入"用 XML 写 `<foreach>`，就要手动填公共字段。**

### 坑 3：`orders` 表的公共字段永远填不上

前面详细说了：`orders` 表没有这四列，`Orders` 实体也没标注解。

**我一开始以为是 handler 坏了**，因为"其他表都填了，就订单表没有"。

查了 `information_schema` 才确认：**表里就没这列，不是什么 bug。**

**但换个角度，这是设计缺失** —— 订单表比任何表都需要"谁在什么时候接的单"。

### 坑 4：`create_time` 和 `update_time` 差了几微秒

最早的写法是每次调用都 `LocalDateTime.now()`：

```java
strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
strictInsertFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
```

结果：

```
create_time = 2026-10-27 22:40:55.133745
update_time = 2026-10-27 22:40:55.134012    ← 差 267 微秒
```

**改成"先取一次 now，两处复用"后就一致了。**

**这个坑很小，但很典型：同一个逻辑时刻的多个字段，应该用同一个时间戳。**

### 坑 5：`@TableField(fill = ...)` 和 `@TableField(value = "...")` 冲突

如果想同时指定列名和填充策略，不能写两个注解：

```java
// ✗ 错：重复注解，编译不过
@TableField(value = "create_time")
@TableField(fill = FieldFill.INSERT)
private LocalDateTime createTime;

// ✓ 对：一个注解里写两个属性
@TableField(value = "create_time", fill = FieldFill.INSERT)
private LocalDateTime createTime;
```

**这个项目没踩到**，因为开了 `map-underscore-to-camel-case: true`，`createTime` 自动映射到 `create_time`，不需要显式写 `value`。

**但如果某张表的列名不符合下划线规则（比如 `ctime`），就需要显式指定 `value`，这时候容易犯上面的错。**

## ⑦ 缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **`orders` 表没有公共字段** | **高** | 订单没有 `create_time`/`update_time`/`update_user`，算不出"接单时长"、查不到"谁接的单" | 加列 + 实体标注解；或加 `order_status_log` 表 |
| **`Orders.java` 有未使用的 import** | 低 | `import FieldFill` 但没用，IDE 会警告 | 删掉 |
| **没有逻辑删除字段的自动填充** | 低 | 如果加 `@TableLogic` 的 `deleted` 字段，删除时要填 `delete_time`/`delete_user`，现在没有 | 加 `deleteFill` 逻辑 |
| **批量插入不触发** | 中 | 如果用 XML 批量 INSERT，handler 不生效 | 手动填，或用 MP 的 `saveBatch` |
| **`0L` 兜底可能违反外键** | 低 | 如果 `create_user` 建了外键指向 `employee.id`，`0` 会报错 | 用 NULL 或单独建"系统用户" |
| **时区隐式依赖** | 低 | `LocalDateTime.now()` 用 JVM 默认时区，服务器时区变了数据就乱 | 显式指定 `ZoneId`，或统一用 UTC 存储 |
| **前端能覆盖公共字段** | 中 | 如果 DTO 里有 `updateTime` 字段且被 `copyProperties` 拷贝，handler 会因为"非 null"而跳过，**存进去的是前端传的时间** | DTO 里不要放公共字段（现在是对的） |

### 「前端能覆盖公共字段」这个风险值得展开

假设有人图省事，直接拿实体接收请求：

```java
@PostMapping
public Result<Void> save(@RequestBody Dish dish) {    // ← 直接收实体
    dishService.save(dish);
}
```

前端就可以传：

```json
{"name":"水煮鱼","price":68,"createTime":"2020-01-01T00:00:00","createUser":999}
```

**`strictInsertFill` 的第 ③ 个条件（当前值非 null 就跳过）会让 handler 不填**，于是数据库里存的是 `2020-01-01` 和 `createUser=999`。

**这是"自动填充"和"参数防篡改"的交叉风险。**

**这个项目为什么没事？** 因为所有新增接口都收 DTO（`EmployeeDTO`、`DishDTO`、`SetmealDTO`），DTO 里没有公共字段，`copyProperties` 拷不过来。

**所以"用 DTO 而不是实体接收请求"不只是规范问题，它直接堵住了一个安全漏洞。**

**面试如果被问"为什么要有 DTO"，这是一个很硬的答案。**

## ⑧ 面试 30 秒版

> 公共字段自动填充用 MyBatis-Plus 的 `MetaObjectHandler`，不用课程那套 AOP。原因是 MP 的 handler 是框架在 SQL 组装前**精确回调**的，天生知道当前是 insert 还是 update；而 AOP 切在 Service 外层，只能靠方法名猜。而且 handler 用的是 MP 已经缓存的 `TableInfo` 元数据按名字取字段，没有反射遍历，零额外依赖。
>
> 它必须两层配合：实体上标 `@TableField(fill = INSERT / INSERT_UPDATE)` 做声明，handler 里用 `strictInsertFill` 执行。strict 是关键——它会先检查这个字段有没有标 fill，没标就跳过。所以我一个 handler 能服务所有表：`dish` 标了 4 个字段就填 4 个，`dish_flavor` 一个没标就一个不填，`shopping_cart` 只标了 createTime 就只填时间。如果换成非 strict，往没有 `createUser` 属性的子表实体上设值会直接抛 `ReflectionException`。
>
> 操作人 id 从 `BaseContext`（ThreadLocal）取，取不到时用 0 兜底——因为数据初始化、定时任务、异步线程都没有登录上下文，直接塞 null 会因为 `NOT NULL` 约束报错。
>
> 两个已知短板：一是 `orders` 表根本没有这四列，所以自动填充对订单表完全失效，导致查不到"谁接的单"；二是如果接口直接用实体接参，前端传了 `createTime` 会因为"非 null 就跳过"而不被覆盖，所以必须用 DTO 收参。
