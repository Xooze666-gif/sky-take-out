# 精讲 07 · 套餐多对多：快照补全与起售校验

> 源码位置：`SetmealServiceImpl`（`saveWithDish` / `insertSetmealDishes` / `startOrStop` / `deleteBatch`）
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版

---

## ① 场景

「套餐」是外卖里的组合商品。比如"测试双人餐" = 麻婆豆腐 ×2 + 水煮鱼 ×1。

后端发出：

```
POST /admin/setmeal
{
  "name": "测试双人餐",
  "categoryId": 6,
  "price": 80.00,
  "status": 0,
  "setmealDishes": [
    {"dishId": 5, "copies": 2},
    {"dishId": 6, "copies": 1}
  ]
}
```

**注意前端只传了 `dishId` 和 `copies`** —— 没传菜名、没传菜价。这不是前端偷懒，是**设计要求**：菜名和菜价必须由后端从 `dish` 表查。

---

## ② 数据：执行前 → 执行后

**执行前**：`dish` 表里 `id=5` 是「麻婆豆腐 18.00」，`id=6` 是「水煮鱼 68.00」。

**执行后**：

`setmeal` 表新增一行：

| id | name | category_id | price | status | create_user |
|---|---|---|---|---|---|
| **6** | 测试双人餐 | 6 | 80.00 | 0 | 1 |

`setmeal_dish` 表（中间表）新增两行：

| id | setmeal_id | dish_id | name | price | copies |
|---|---|---|---|---|---|
| 18 | 6 | 5 | **麻婆豆腐** | **18.00** | 2 |
| 19 | 6 | 6 | **水煮鱼** | **68.00** | 1 |

### 这里有个必须注意的实验

我在请求里**故意传了错的菜名和菜价**：

```json
{"dishId": 5, "name": "前端伪造的菜名", "price": 0.01, "copies": 2}
```

结果入库的是 `麻婆豆腐 / 18.00`。

**前端传的假值被后端完全丢弃了。** 这是本篇最核心的证据 —— 下面第 ③ 层会讲它是怎么做到的。

## ③ 逐行拆

### `saveWithDish`：主表 + 中间表

```java
@Transactional
public void saveWithDish(SetmealDTO setmealDTO) {
    Setmeal setmeal = new Setmeal();
    BeanUtils.copyProperties(setmealDTO, setmeal);
    if (setmeal.getStatus() == null) {
        setmeal.setStatus(StatusConstant.ENABLE);       // ① 默认起售（但允许前端指定）
    }
    setmealMapper.insert(setmeal);                       // ② 主表插入，主键回填

    insertSetmealDishes(setmeal.getId(), setmealDTO.getSetmealDishes());  // ③ 中间表
}
```

**第 ① 行和菜品不一样**：菜品是**强制** `setStatus(ENABLE)`，套餐是 **`null` 才给默认值**。

为什么？因为套餐有"先建好、配齐菜品再上架"的流程，前端会显式传 `status: 0`（停售）。菜品没这个需求（建了就能卖）。

**这是一个不一致。** 严格说，同一个项目里两个相似实体的默认值策略应该统一。但业务上确实存在差异，所以不算 bug——面试被问"你注意到代码里有不一致吗"，这是一个可以主动提的点。

### `insertSetmealDishes`：这段是全项目最值得讲的方法之一

```java
private void insertSetmealDishes(Long setmealId, List<SetmealDish> setmealDishes) {
    if (CollectionUtils.isEmpty(setmealDishes)) {
        return;
    }

    // ---- 第 1 步：收集所有 dishId ----
    List<Long> dishIds = setmealDishes.stream()
            .map(SetmealDish::getDishId)
            .filter(id -> id != null)          // ① 过滤 null
            .collect(Collectors.toList());

    // ---- 第 2 步：一次性查出所有菜品，转成 Map ----
    Map<Long, Dish> dishMap = dishIds.isEmpty()
            ? Collections.emptyMap()
            : dishMapper.selectBatchIds(dishIds).stream()
                    .collect(Collectors.toMap(Dish::getId, Function.identity()));   // ②

    // ---- 第 3 步：逐条用数据库的真实值覆盖前端传来的值 ----
    for (SetmealDish sd : setmealDishes) {
        Dish dish = dishMap.get(sd.getDishId());
        if (dish == null) {
            throw new BaseException("套餐内包含不存在的菜品");     // ③ 校验存在性
        }
        sd.setId(null);                  // ④ 防篡改
        sd.setSetmealId(setmealId);      // ⑤ 绑定父 id
        sd.setName(dish.getName());      // ⑥ 用数据库的值覆盖前端
        sd.setPrice(dish.getPrice());    // ⑦ 同上
        setmealDishMapper.insert(sd);
    }
}
```

**第 ① 步 `.filter(id -> id != null)` 为什么必要？**

`selectBatchIds` 内部是把 id 拼成 `WHERE id IN (5, 6, null)`。如果集合里有 `null`：

- 单条 `IN` 带 null 不会报错，但 `null` 永远匹配不上任何行
- 更麻烦的是 `Collectors.toMap(Dish::getId, ...)` —— 如果查回来的结果里有 null key（不会），或者 `dishIds` 里有重复（**会**），`toMap` 会抛 `IllegalStateException: Duplicate key`

**重复 dishId 是真实可能发生的**：前端如果传 `[{dishId:5},{dishId:5}]`（用户误点两次），`dishIds` 就是 `[5,5]`。`selectBatchIds([5,5])` 返回的 list 里只有一条 Dish，`toMap` 不会报错（因为只有一个元素）。所以这里**实际不会炸**，但 `IN (5,5)` 是多余的。

**真正会炸的是另一种情况**：`selectBatchIds` 返回的结果如果因为某些原因有两条 id 相同的记录（比如主键有重复——不可能），才会炸。所以这个 `toMap` 是安全的。

**严格说这里应该加 `.distinct()`**，减少无意义的 SQL 参数。这是个小优化点。

**第 ② 步 `selectBatchIds` 是「避免 N+1」的关键。**

对比两种写法：

```java
// ✗ N+1 写法：套餐里有几个菜就查几次
for (SetmealDish sd : setmealDishes) {
    Dish dish = dishMapper.selectById(sd.getDishId());   // 2 个菜 = 2 条 SELECT
    ...
}

// ✓ 批量写法：不管几个菜，一条 SELECT
List<Dish> dishes = dishMapper.selectBatchIds(dishIds);   // WHERE id IN (5,6)
```

套餐里有 10 个菜，N+1 写法就是 11 条 SQL（1 主表 + 10 查菜品）；批量写法固定 2 条（1 主表 + 1 批量查）。**这是最经典、最高频的性能优化点。**

**第 ③ 步「不存在就抛异常」是在校验什么？**

如果前端传了 `dishId: 999`（不存在的菜品），`dishMap.get(999)` 返回 `null`，这里直接抛。如果不抛，`dish.getName()` 就是 NPE。

**注意这个异常会让整个事务回滚** —— 前面已经 `INSERT setmeal` 了，但因为 `@Transactional`，主表那条也会被撤销。这就是事务的价值：不会留下"套餐建好了但没有任何菜"的脏数据。

**第 ④ 步 `sd.setId(null)`**：和菜品口味一样的防篡改。

**第 ⑥⑦ 步是全场最重要的两行。**

这两行就是"前端传 0.01 却被存成 18.00"的原因：

```java
sd.setName(dish.getName());    // sd 是前端传来的对象，它的 name 本来是"前端伪造的菜名"
sd.setPrice(dish.getPrice());  // 它的 price 本来是 0.01
```

`s d` 这个对象是从 `setmealDishes` 里遍历出来的，**它的字段值是 Jackson 从请求 JSON 反序列化出来的**，也就是前端给什么就是什么。这两行把它**原地覆盖**成数据库里的真实值。

**为什么不干脆"不读前端的 name/price 字段"？** 因为 `SetmealDish` 实体有这两个属性，Jackson 会自动填。做不到"忽略某些字段"（除非用 `@JsonIgnore`，但那样响应时也读不出来）。所以只能"先接收、再覆盖"。

**这是很实用的模式：接收 → 校验 → 用可信源覆盖。** 面试讲"防前端篡改"，这就是最好的例子。

### `startOrStop`：起售前的业务校验

```java
public void startOrStop(Integer status, Long id) {
    // 只有「起售」才校验；「停售」不校验（停售永远允许）
    if (StatusConstant.ENABLE.equals(status)) {
        // ① 查出这个套餐包含哪些菜品
        List<SetmealDish> dishes = setmealDishMapper.selectList(
                Wrappers.<SetmealDish>lambdaQuery().eq(SetmealDish::getSetmealId, id));

        if (!CollectionUtils.isEmpty(dishes)) {
            List<Long> dishIds = dishes.stream()
                    .map(SetmealDish::getDishId).collect(Collectors.toList());

            // ② 数一下有几个菜品不是「起售」状态
            Long stopped = dishMapper.selectCount(Wrappers.<Dish>lambdaQuery()
                    .in(Dish::getId, dishIds)
                    .ne(Dish::getStatus, StatusConstant.ENABLE));

            if (stopped != null && stopped > 0) {
                throw new BaseException(MessageConstant.SETMEAL_ENABLE_FAILED);
            }
        }
    }

    Setmeal setmeal = new Setmeal();
    setmeal.setId(id);
    setmeal.setStatus(status);
    setmealMapper.updateById(setmeal);
}
```

**业务规则：套餐要起售，它里面的每个菜都必须在售。**

为什么？因为用户点套餐时，看到的应该是"能立刻做出来"的组合。如果套餐里有个菜停售了（可能食材没了），用户下单后商家做不出来。

**为什么"停售"不校验？** 停售是"从货架拿下来"，永远应该允许——哪怕套餐里有菜已经不存在了，你也得让人把它下架。

**注意 `ne(Dish::getStatus, ENABLE)` 而不是 `eq(Dish::getStatus, DISABLE)`。**

`ne`（不等于 1）能同时覆盖 `status = 0` 和 `status = NULL` 的情况（虽然 `NULL` 在 `!=` 比较里不成立，但这里 `status` 是 `NOT NULL`）。用 `eq(0)` 只挡了"明确停售"，如果将来加了 `status = 2`（比如"售罄"），`eq(0)` 就漏了。

**`ne` 更稳，因为它表达的是"只要不是起售就拦"。**

## ④ SQL 实况（真实抓取）

### 场景 A：新增套餐（前端传假名假价）

```sql
SET autocommit=0

INSERT INTO setmeal ( category_id, name, price, status, description, image,
                      create_time, update_time, create_user, update_user )
VALUES ( 6, '测试双人餐', 80.00, 0, '精讲用测试套餐', 'https://example.com/set.jpg',
         '2026-10-27 22:41:28.969963', '2026-10-27 22:41:28.969963', 1, 1 )

SELECT id,name,category_id,price,image,description,status,create_time,update_time,create_user,update_user
FROM dish WHERE id IN ( 5 , 6 )

INSERT INTO setmeal_dish ( setmeal_id, dish_id, name, price, copies ) VALUES ( 6, 5, '麻婆豆腐', 18.00, 2 )
INSERT INTO setmeal_dish ( setmeal_id, dish_id, name, price, copies ) VALUES ( 6, 6, '水煮鱼', 68.00, 1 )

commit
SET autocommit=1
```

**逐条解读：**

| SQL | 关键点 |
|---|---|
| `INSERT INTO setmeal ...` | 主表，**注意 `setmeal_dish` 的两条 INSERT 用的是 `setmeal_id = 6`**——回填的 |
| `SELECT ... FROM dish WHERE id IN ( 5 , 6 )` | **只有 1 条**，两个菜品一次查完 → 没有 N+1 |
| `INSERT INTO setmeal_dish ... VALUES (6, 5, '麻婆豆腐', 18.00, 2)` | **name/price 是数据库值**，不是前端传的"前端伪造的菜名/0.01" |
| `INSERT INTO setmeal_dish ... VALUES (6, 6, '水煮鱼', 68.00, 1)` | 同上 |

**验证入库结果：**

```
id  setmeal_id  dish_id  name      price   copies
18  6           5        麻婆豆腐   18.00   2
19  6           6        水煮鱼     68.00   1
```

前端传的 `0.01` 和 `"前端伪造的菜名"` **一个字都没进数据库**。

### 场景 B：起售被拦（套餐内有停售菜品）

先把菜品 6（水煮鱼）停售，再起售套餐：

```sql
SELECT id,setmeal_id,dish_id,name,price,copies FROM setmeal_dish WHERE (setmeal_id = 6)
SELECT COUNT( * ) AS total FROM dish WHERE (id IN (5,6) AND status <> 1)
```

响应：`{"code":0,"msg":"套餐内包含未起售的菜品，无法起售"}`

**注意：这里没有 `SET autocommit=0`，也没有 `rollback`。**

### 场景 C：起售成功

```sql
SELECT id,setmeal_id,dish_id,name,price,copies FROM setmeal_dish WHERE (setmeal_id = 6)
SELECT COUNT( * ) AS total FROM dish WHERE (id IN (5,6) AND status <> 1)
UPDATE setmeal SET status=1, update_time='2026-10-27 22:41:39.367365', update_user=1 WHERE id=6
```

**同样没有 `SET autocommit=0`。**

### 这三个场景放在一起，暴露了一个真实问题

| 场景 | 有事务？ | 证据 |
|---|---|---|
| 新增套餐 | **有** | `SET autocommit=0` ... `commit` |
| 起售套餐（被拦） | **没有** | 直接两条 SELECT |
| 起售套餐（成功） | **没有** | 两条 SELECT + 一条 UPDATE，无 commit |

因为 `startOrStop` 方法上**没有 `@Transactional`**：

```java
@Override
public void startOrStop(Integer status, Long id) {    // ← 没有 @Transactional
```

**这意味着"校验"和"更新"不在同一个事务里。** 详见第 ⑦ 层。

## ⑤ 权衡

### 为什么中间表要存 `name`/`price` 快照？（反范式）

按数据库范式，`setmeal_dish` 只需要 `setmeal_id` + `dish_id` + `copies`，菜名和价格应该 join `dish` 表拿。存一份是**冗余（反范式）**。

**为什么还是存了？** 三个理由：

1. **性能**：套餐详情页要展示"含麻婆豆腐 18.00 ×2"，join 一次就够了，不用每次去 dish 表查。
2. **历史一致性**：菜品改价后，**已建好的套餐里显示的价格不应该自动变**。如果 join，商家把麻婆豆腐从 18 改到 25，所有包含它的套餐明细都会跟着变——但套餐总价 `setmeal.price` 是固定的 80，就对不上了。
3. **菜品可能被删除**：join 会因为找不到菜品而显示空白，快照还能显示。

**这就是"快照"和"外键关联"的分界线：**

> 需要"跟着源数据变" → 用外键 join；需要"冻结在某个时刻" → 存快照。

**和精讲 03 的价格快照是同一个思想**，只是应用在不同层级：订单存快照冻结"下单那一刻"，中间表存快照冻结"套餐定价那一刻"。

**代价是什么？** 数据会不一致。如果商家改了麻婆豆腐的价格，`dish.price` 是 25，但 `setmeal_dish.price` 还是 18。这时候套餐里显示"麻婆豆腐 18"，但用户单点要 25。

**这是业务可接受的**——因为套餐是"打包价"，本来就不等于单点价之和。但如果业务要求"套餐必须实时反映菜品价格"，那就不能存快照，得改成 join + 套餐价格动态计算。

### 为什么不用 `setmeal.dish_ids` JSON 列存菜品列表？

| | 中间表（当前） | JSON 列 |
|---|---|---|
| 查"哪些套餐包含麻婆豆腐" | `WHERE dish_id = 5`，可走索引 | `JSON_CONTAINS(dish_ids, '5')`，全表扫 |
| 单个菜品份数独立修改 | `UPDATE ... WHERE setmeal_id=? AND dish_id=?` | 读整个 JSON → 改 → 写回 |
| 存 `name`/`price` 快照 | 每行独立存，结构清晰 | 嵌套在 JSON 里 |
| 统计"麻婆豆腐一共卖出多少份（含套餐）" | join 一下就行 | 几乎做不了 |

**多对多的标准解法就是中间表。** JSON 只适合"整体读写、不需要按元素查询"的场景。

### 为什么校验用 `selectCount` 而不是查出所有菜品再在 Java 里判断？

```java
// 当前：让数据库数
Long stopped = dishMapper.selectCount(... .ne(Dish::getStatus, ENABLE));

// 另一种：查全量再 Java 判断
List<Dish> dishes = dishMapper.selectBatchIds(dishIds);
long stopped = dishes.stream().filter(d -> !ENABLE.equals(d.getStatus())).count();
```

`selectCount` 只返回一个数字，网络传输量最小；查全量要传回所有字段（含 image、description 这些大字段）。

**"能在数据库算的，不要在应用层算"** —— 这是 SQL 优化的第一条原则。

## ⑥ 踩坑实录

### 坑 1：一开始想"只接收 dishId，别接收 name/price"

写第一版时我觉得"既然 name/price 要用数据库的，那 DTO 里就不要这两个字段"。

但 `SetmealDish` 是**实体类**，直接当 DTO 用了（`SetmealDTO.setmealDishes` 的类型就是 `List<SetmealDish>`）。实体上有 `name`/`price` 属性，Jackson 就会往里填。想"不接收"只能加 `@JsonIgnore`，但那样响应（查询套餐详情）时也读不出来了。

**最终方案就是"接收 → 覆盖"**。这个思路后来在别处也复用了：先信任度最低地接住数据，再用可信源覆盖关键字段。

### 坑 2：起售校验我以为有事务

一开始看代码，觉得"校验 + 更新"是完整业务，应该有事务。抓 SQL 才发现**根本没有 `SET autocommit=0`**。

翻代码确认：

```java
@Override                                    // ← 只有这一个注解
public void startOrStop(Integer status, Long id) {
```

`SetmealServiceImpl` 里 `saveWithDish`、`deleteBatch`、`updateWithDish` 都有 `@Transactional`，唯独 `startOrStop` 漏了。

**这是个真实的缺口**，不是设计选择 —— 因为如果是有意为之，应该在注释里说明。而 `DishServiceImpl.startOrStop` 也没加（那边只有一条 SQL，确实不需要）。`SetmealServiceImpl.startOrStop` 有三条 SQL，需要。

### 坑 3：`selectBatchIds` 传空集合会怎样

如果套餐里一个菜都没有（`setmealDishes` 是空数组），`dishIds` 为空。代码里做了判断：

```java
Map<Long, Dish> dishMap = dishIds.isEmpty()
        ? Collections.emptyMap()
        : dishMapper.selectBatchIds(dishIds).stream()...
```

**为什么要判空？** 因为 `selectBatchIds(空集合)` 在 MyBatis-Plus 里会生成 `WHERE id IN ()` —— **SQL 语法错误**。

不同版本的 MP 行为不同（有的会直接返回空 list，有的会抛异常），所以显式判空是最稳的。

**同类坑**：`deleteBatchIds(空集合)`、`in(列, 空集合)` 都有这个问题。MyBatis-Plus 的条件构造器里 `.in()` 传空集合会生成 `IN ()`，直接报错。**所以所有 `in` 操作前都要判空。**

## ⑦ 缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **`startOrStop` 没有事务** | **高** | 校验（2 条 SELECT）和更新（1 条 UPDATE）分开执行，中间有并发窗口 | 加 `@Transactional` |
| **起售校验有并发窗口** | 高 | 校验通过的那一瞬间，另一个请求把某个菜品停售 → 套餐起售成功，但里面有停售菜品 | 校验时 `SELECT ... FOR UPDATE` 锁住菜品行，或改用数据库约束 |
| **套餐价格没校验** | 中 | 套餐价 80，明细加起来是 104（18×2+68），差价 24 元。系统不校验合理性 | 加"套餐价不得高于明细之和"的软校验 |
| **删除套餐没校验订单引用** | 中 | 历史订单里有这个套餐，删了之后"再来一单"会断链 | 改逻辑删除 |
| **修改套餐没有防并发** | 低 | 两人同时改，后覆盖前 | 乐观锁 |
| **`toMap` 没处理重复 dishId** | 低 | 前端传重复 dishId 会插两条重复的中间记录 | 加 `.distinct()`，或在业务上合并 copies |

### 「起售校验的并发窗口」值得细说

这是一个**真实的、可以复现的**时序问题：

```
时刻 T1: 管理员 A 点「套餐起售」
         → SELECT setmeal_dish（查套餐含菜品 5、6）
         → SELECT COUNT dish WHERE id IN (5,6) AND status<>1  → 0，全部在售，校验通过
         
时刻 T2: 管理员 B 点「停售菜品 6」
         → UPDATE dish SET status=0 WHERE id=6

时刻 T3: 管理员 A 的代码继续执行
         → UPDATE setmeal SET status=1 WHERE id=6      ← 套餐起售成功

结果：套餐在售，但里面的水煮鱼是停售的。校验失效。
```

**这就是"检查后使用"（TOCTOU, Time-of-Check to Time-of-Use）竞态的经典形态。**

三种解法：

1. **加事务 + 行锁**：`SELECT ... FOR UPDATE` 把 `dish` 那两行锁住，B 的 UPDATE 会阻塞到 A 提交
2. **数据库约束**：技术上做不到（跨表约束 MySQL 不支持）
3. **接受不一致 + 查询时兜底**：用户下单时再校验一次（更实际，因为"停售"是低频操作）

**面试如果被问"你怎么保证套餐起售时菜品都在售"，能答出 TOCTOU 和 `FOR UPDATE`，就是高级回答了。**

而且这里还有个更基础的错误：**连事务都没加**。没事务的情况下，`FOR UPDATE` 也锁不住（因为 `SELECT` 结束锁就释放了）。所以修复顺序是：**先加 `@Transactional`，再加 `FOR UPDATE`。**

## ⑧ 面试 30 秒版

> 套餐和菜品是多对多，靠 `setmeal_dish` 中间表。新增时有个关键设计：**前端只传 dishId 和份数，菜名和菜价由后端查 dish 表补**。我用真实请求验证过——故意传 `price: 0.01` 和假菜名，入库的是 18.00 和"麻婆豆腐"，说明覆盖逻辑生效。
>
> 查菜品用 `selectBatchIds` 一次查完转成 Map，避免 N+1 —— 套餐里有 10 个菜，循环查就是 11 条 SQL，批量查固定 2 条。中间表存 `name`/`price` 是刻意的反范式快照，目的是"冻结套餐定价那一刻"，菜品改价不影响已建套餐的明细显示。
>
> 起售前要校验套餐内所有菜品都在售，用 `status <> 1` 而不是 `= 0`，这样将来加"售罄"状态也能拦住。
>
> 但我发现 `startOrStop` 漏了 `@Transactional`——我抓 SQL 能看到别的方法有 `SET autocommit=0`，这个方法没有。这导致校验和更新不在同一事务，存在 TOCTOU 竞态：校验通过后另一个请求把菜品停售，套餐照样能起售。正确做法是加事务 + `SELECT ... FOR UPDATE` 锁住菜品行。
