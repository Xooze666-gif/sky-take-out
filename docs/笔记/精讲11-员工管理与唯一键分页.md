# 精讲 11 · 员工管理：唯一键、启停与分页

> 源码位置：`EmployeeController` + `EmployeeServiceImpl` + `GlobalExceptionHandler`
> 八层拆解：① 场景 ② 数据 ③ 逐行 ④ SQL 实况 ⑤ 权衡 ⑥ 踩坑 ⑦ 缺口 ⑧ 面试 30 秒版

## ① 场景

员工管理是后台最基础的一块，五个动作：

| 动作 | 接口 | 说明 |
|---|---|---|
| 新增 | `POST /admin/employee` | 密码统一默认 `123456` |
| 分页 | `GET /admin/employee/page?page=1&pageSize=10&name=张` | 姓名模糊 + 创建时间倒序 |
| 启停 | `POST /admin/employee/status/{status}?id=x` | `1` 启用，`0` 禁用 |
| 回显 | `GET /admin/employee/{id}` | 编辑前查详情 |
| 修改 | `PUT /admin/employee` | 不允许改用户名 |

看起来是 CRUD，但里面有三个值得讲的点：**唯一键冲突怎么处理**、**启停为什么不用先查再改**、**分页怎么把密码带出来了**。

## ② 数据：执行前 → 执行后

**新增前**，`employee` 表里有 `admin`（id=1）。

**新增后**，多一行：

| id | name | username | password | status | create_user | update_user |
|---|---|---|---|---|---|---|
| **7** | 测试员 | test_precision | `e10adc3949ba59abbe56e057f20f883e` | 1 | **1** | **1** |

**注意 `password` 是 MD5，不是明文 `123456`。**

**禁用后**（同一个 id=7）：

| status | update_time | update_user |
|---|---|---|
| **0** | 2026-10-27 22:42:23 | 1 |

**只有三列变了**：`status`、`update_time`、`update_user`。其他 8 列一个没动。

## ③ 逐行拆

### `save`：密码在后端写死

```java
public void save(EmployeeDTO employeeDTO) {
    Employee employee = new Employee();
    BeanUtils.copyProperties(employeeDTO, employee);      // ① DTO → Entity

    employee.setStatus(StatusConstant.ENABLE);            // ② 默认启用
    employee.setPassword(DigestUtils.md5DigestAsHex(
            DEFAULT_PASSWORD.getBytes(StandardCharsets.UTF_8)));   // ③ 默认密码

    employeeMapper.insert(employee);                      // ④ 公共字段由 handler 填
}
```

**第 ① 步为什么用 `EmployeeDTO` 而不是 `Employee`？**

因为 `EmployeeDTO` 里**没有** `password`、`status`、`createTime` 这些字段：

```java
public class EmployeeDTO {
    private Long id;
    private String name;
    private String username;
    private String phone;
    private String sex;
    private String idNumber;
}
```

**如果接口直接收 `Employee`，前端就能传 `password` 和 `status`** —— 恶意用户可以：

- 传一个超长密码或者空密码
- 传 `status: 0` 让新建的员工直接是禁用状态
- 传 `id: 1` 尝试覆盖 admin

**用 DTO 做"收窄"，是最简单的参数防篡改手段。** 这比在 Service 里一个个 `setXxx(null)` 干净得多。

**第 ②③ 步**：新建员工默认启用、默认密码 `123456`（MD5 后存）。

**这里有个业务假设：管理员建完账号，要把初始密码口头告诉员工。** 生产系统一般是"生成随机密码 + 短信发送 + 首次登录强制改密"。

**第 ④ 步 `create_user` 从哪来？** 从 ThreadLocal（精讲 05 讲过那条链）。下面第 ④ 层有 SQL 证据。

### `startOrStop`：为什么"更新"比"先查再改"好

```java
public void startOrStop(Integer status, Long id) {
    // 用 update 而非先查再改：一次 SQL 完成，且能防止「查出来已不存在」的并发问题
    Employee employee = new Employee();
    employee.setId(id);
    employee.setStatus(status);
    int rows = employeeMapper.updateById(employee);

    if (rows == 0) {
        throw new BaseException("员工不存在");
    }
}
```

**对比"先查再改"的写法：**

```java
// ✗ 两条 SQL
Employee db = employeeMapper.selectById(id);
if (db == null) throw new BaseException("员工不存在");
db.setStatus(status);
employeeMapper.updateById(db);
```

| | 先查再改 | **直接 update（当前）** |
|---|---|---|
| SQL 数量 | 2 条 | **1 条** |
| 并发下 | 查到存在 → 另一个请求删了 → update 影响 0 行，但代码以为成功 | **rows=0 就是不存在，准确** |
| 能否拿到旧值 | 能 | 不能（这里不需要） |
| 网络往返 | 2 次 | **1 次** |

**关键差异在"判断存在性"的方式：**

- 先查再改：靠 `SELECT` 的结果判断
- 直接 update：靠 `UPDATE` 的**影响行数**判断

**`rows == 0` 有两种可能**：id 不存在，或者值没变（MySQL 默认返回"实际改变的行数"，如果 `status` 已经是目标值，返回 0）。

**这是个潜在的误判！**

```
员工 7 已经是 status=0（禁用）
管理员再次点"禁用"
  → UPDATE employee SET status=0 WHERE id=7
  → MySQL 返回 affected rows = 0（值没变）
  → 代码抛 "员工不存在"    ← 错误提示！
```

**为什么会这样？** 因为 MySQL 的 `UPDATE` 默认返回 **"实际改变的行数"（changed rows）**，不是"匹配的行数"（matched rows）。这个行为由 JDBC 连接参数 `useAffectedRows` 控制：

- `useAffectedRows=false`（MySQL 默认，JDBC 默认）→ 返回 matched rows（匹配行数）
- `useAffectedRows=true` → 返回 changed rows

**实际上 MySQL Connector/J 默认是 `useAffectedRows=false`，返回的是"匹配到的行数"，所以上面的误判不会发生。**

但这是个**很容易踩的坑**，因为很多数据库（PostgreSQL）默认是 changed rows。**如果哪天换了数据库，这段代码就会出问题。**

**更稳的写法**：显式加条件，用 `rows == 0` 判断"状态不对"而不是"不存在"：

```java
int rows = employeeMapper.update(null, Wrappers.<Employee>lambdaUpdate()
        .eq(Employee::getId, id)
        .ne(Employee::getStatus, status)     // 只有状态不同才更新
        .set(Employee::getStatus, status));
```

这样 `rows == 0` 明确表示"id 不存在或者状态已经是目标值"，两种都是幂等成功，不用抛异常。

**但这样就丢失了"员工不存在"的提示。** 折中：只在 `id` 存在性上做判断（先 `selectById` 判存在），再做无条件 update。

**面试如果被问"update 返回 0 行代表什么"，答"可能是记录不存在，也可能是值没变化，取决于驱动的 useAffectedRows 配置"** —— 这个回答会让人觉得你真的写过。

### `pageQuery`：MP 分页插件的两件事

```java
public PageResult pageQuery(EmployeePageQueryDTO dto) {
    Page<Employee> page = new Page<>(dto.getPage(), dto.getPageSize());

    LambdaQueryWrapper<Employee> wrapper = Wrappers.<Employee>lambdaQuery()
            .like(StringUtils.hasText(dto.getName()), Employee::getName, dto.getName())
            .orderByDesc(Employee::getCreateTime);

    employeeMapper.selectPage(page, wrapper);       // ← 这里发了两条 SQL

    return new PageResult(page.getTotal(), page.getRecords());
}
```

**`selectPage` 内部自动发两条 SQL：**

```sql
SELECT COUNT(*) AS total FROM employee WHERE (name LIKE '%测试%')
SELECT id,name,... FROM employee WHERE (name LIKE '%测试%') ORDER BY create_time DESC LIMIT 2
```

第一条算总数（前端要显示"共 N 条"），第二条取当前页。

**这个"自动两条"是 `PaginationInnerInterceptor` 做的**（在 `MybatisPlusConfiguration` 里注册）。

**`like` 的第一个参数 `StringUtils.hasText(dto.getName())` 是动态条件开关**：

```java
.like(条件为true, 列, 值)
```

- `name` 有值 → 拼 `WHERE name LIKE '%测试%'`
- `name` 为 null/空 → 这个条件整条不拼

**这就是"一个方法支持四种查询组合"的写法**（无条件 / 只按姓名 / 只按状态 / 两者都要）。

**`orderByDesc(Employee::getCreateTime)` 为什么必要？**

不加的话，MySQL 返回顺序是**不确定的**（取决于存储引擎、索引、执行计划）。分页查询如果没有 `ORDER BY`，**翻页时会出现"同一条记录出现两次"或者"漏掉一条"**。

**这是分页查询的硬性要求：没有 ORDER BY 的分页是错的。**

**注意：`create_time` 相同的记录，排序依然不确定。** 严格做法是加个 tie-breaker：`ORDER BY create_time DESC, id DESC`。

### `getById`：回显前抹掉密码

```java
public Employee getById(Long id) {
    Employee employee = employeeMapper.selectById(id);
    if (employee == null) {
        throw new AccountNotFoundException();
    }
    employee.setPassword(null);      // 密码敏感，回显前抹掉
    return employee;
}
```

**这里有个"双保险"的设计：**

第一层：`Employee` 实体的 `password` 字段上有 `@JsonIgnore`，序列化时自动跳过。
第二层：这里手动 `setPassword(null)`。

**为什么要两层？** 因为 `@JsonIgnore` 是"反序列化也不接收"，如果将来有人把这个实体直接当请求体用，密码就传不进来了。而手动置 null 是"业务层保证不返回敏感数据"。

**从安全角度，两层都留着更好**（防御纵深）。但要注意：**`setPassword(null)` 之后，这个对象如果被拿去 `updateById`，会因为 `NOT_NULL` 策略跳过 password —— 不会误清空密码。** 这是运气好，不是设计好。

### `update`：三个 `setXxx(null)` 的意思

```java
public void update(EmployeeDTO employeeDTO) {
    Employee employee = new Employee();
    BeanUtils.copyProperties(employeeDTO, employee);

    employee.setUsername(null);      // ① 不允许改用户名
    employee.setPassword(null);      // ② 防止误清空密码
    employee.setStatus(null);        // ③ 状态走专门的启停接口

    int rows = employeeMapper.updateById(employee);
    if (rows == 0) {
        throw new BaseException("员工不存在");
    }
}
```

**这三行的机制都是同一个：`NOT_NULL` 策略下，值为 null 的字段不会被拼进 `SET`。**

所以生成的 SQL 只有 `name`、`phone`、`sex`、`id_number`，加上自动填充的 `update_time`、`update_user`。

**第 ① 行为什么不让改用户名？**

因为 `username` 是唯一键，是登录凭证。改了之后：

- 用户不知道新用户名，登不进来
- 历史日志里记的旧用户名对不上人

**真实系统里"改用户名"要么不支持，要么走独立流程（需要验证 + 通知）。**

**第 ② 行为什么要显式置 null？**

`EmployeeDTO` 里没有 `password` 字段，`copyProperties` 不会拷它，所以 `employee.getPassword()` 本来就是 null。**这行是"防御性冗余"** —— 防止将来有人给 DTO 加了 password 字段，忘了这里的约束。

**第 ③ 行**同理：`EmployeeDTO` 也没有 `status`，但显式置 null 说明"状态不能通过编辑接口改"。

**这三行代码的写法值得学：用 `setXxx(null)` 表达"这个字段不参与本次更新"，比写注释清楚。** 因为代码会执行，注释可能过期。

## ④ SQL 实况（真实抓取）

### 场景 A：新增员工 —— `create_user = 1` 从哪来

```sql
INSERT INTO employee ( name, username, password, phone, sex, id_number, status,
                       create_time, update_time, create_user, update_user )
VALUES ( '测试员', 'test_precision', 'e10adc3949ba59abbe56e057f20f883e',
         '13900000001', '1', '110101199001011234', 1,
         '2026-10-27 22:42:21.177684', '2026-10-27 22:42:21.177684', 1, 1 )
```

**注意最后那两个 `1`。**

`EmployeeServiceImpl.save` 里**没有 `setCreateUser`**，这两个 1 是 `MyMetaObjectHandler` 从 ThreadLocal 里取的（详见精讲 12）。

**这是"拦截器 → ThreadLocal → 自动填充 → SQL"整条链的终点。** 面试时能把这条链讲完，比单说"用了 ThreadLocal"强得多。

### 场景 B：重复用户名 —— 只有一条 INSERT，没有预查

```sql
INSERT INTO employee ( name, username, ... ) VALUES ( '测试员2', 'test_precision', ... )
```

响应：

```json
{"code":0,"msg":"test_precision 已存在","data":null}
```

**关键：抓到的 SQL 里只有 INSERT，没有 `SELECT ... WHERE username = 'test_precision'`。**

说明代码**没有"先查重再插入"**，而是**直接插，靠数据库唯一索引兜底**。

**这是有意的设计，不是漏了。** 详见第 ⑤ 层。

### 场景 C：启停 —— 精准更新三列

```sql
UPDATE employee SET status=0, update_time='2026-10-27 22:42:23.457502', update_user=1 WHERE id=7
```

**只有三个字段**：`status`（业务字段）+ `update_time` / `update_user`（自动填充）。

**这印证了 `new Employee()` 只 set 两个字段 + `NOT_NULL` 策略的效果。**

### 场景 D：分页 —— 两条 SQL，且把 password 查出来了

```sql
-- 第 1 条：算总数
SELECT COUNT(*) AS total FROM employee WHERE (name LIKE '%测试%')

-- 第 2 条：取当前页
SELECT id,name,username,password,phone,sex,id_number,status,create_time,update_time,create_user,update_user
FROM employee
WHERE (name LIKE '%测试%')
ORDER BY create_time DESC LIMIT 2
```

**注意第 2 条里的 `password`。**

**这就是 `selectPage(page, wrapper)` 的默认行为：查实体的全部字段。**

前端拿不到密码（因为 `@JsonIgnore`），但**密码哈希确实被查出来了、在网络里传了一遍、在内存里存在了一会儿**。

**更严格的做法：**

```java
LambdaQueryWrapper<Employee> wrapper = Wrappers.<Employee>lambdaQuery()
        .select(Employee::getId, Employee::getName, Employee::getUsername,
                Employee::getPhone, Employee::getSex, Employee::getIdNumber,
                Employee::getStatus, Employee::getCreateTime)
        .like(...)
        .orderByDesc(Employee::getCreateTime);
```

**`.select(...)` 指定只查哪些列。** 列表页根本不需要 `password`、`id_number`（身份证号也是敏感信息）。

**这是"最小权限"原则在数据层的体现：不需要的字段就别查。**

**同类问题在用户端也存在**：`user` 表如果有 `openid` 之类的字段，分页查出来也会带上。

### 场景 E：禁用后登录

```json
{"code":0,"msg":"账号被锁定"}
```

对应的 SQL 只有一条 `SELECT ... WHERE username = 'test_precision'`（和正常登录一样），然后 Java 里判 `status == 0` 抛 `AccountLockedException`。

**注意：禁用后登录的报错是"账号被锁定"，和"密码错误"不同。** 这泄露了"账号存在"这个信息（精讲 04 提过）。

## ⑤ 权衡

### 为什么靠唯一索引兜底，而不是先查重？

**两种写法对比：**

```java
// 方案 A：先查后插
Employee exist = employeeMapper.selectOne(...eq(username, dto.getUsername()));
if (exist != null) throw new BaseException("用户名已存在");
employeeMapper.insert(employee);

// 方案 B：直接插，靠唯一索引（当前）
employeeMapper.insert(employee);   // 冲突时抛 DuplicateKeyException
```

| | 先查后插 | **直接插（当前）** |
|---|---|---|
| SQL 数量 | 2 条 | **1 条** |
| 并发安全 | ❌ 两个请求同时"查不到"，然后都插成功（如果没唯一索引） | ✅ 数据库层保证 |
| 错误信息 | 可以很精确 | 要解析异常消息 |
| 依赖 | 无 | **必须有唯一索引** |

**核心：先查后插在并发下是无效的。**

```
时刻 T1: 请求 A 查 "zhangsan" → 不存在
时刻 T2: 请求 B 查 "zhangsan" → 不存在
时刻 T3: 请求 A INSERT 成功
时刻 T4: 请求 B INSERT ... 如果没有唯一索引，就插进去了两个 zhangsan
```

**只要数据库有唯一索引，方案 B 就永远是对的** —— 因为"检查唯一性"这个动作由数据库在插入的同一瞬间原子完成。

**代价：异常处理要费点劲。**

### 为什么 `GlobalExceptionHandler` catch 的是 `DuplicateKeyException`

```java
@ExceptionHandler(DuplicateKeyException.class)
public Result<String> handleDuplicateKey(DuplicateKeyException ex) {
    String message = ex.getMessage();
    if (message != null && message.contains("Duplicate entry")) {
        // 形如：Duplicate entry 'wangwu' for key 'employee.idx_username'
        int start = message.indexOf("Duplicate entry '");
        // ... 截取 'wangwu'
        return Result.error(value + " 已存在");
    }
    return Result.error(MessageConstant.UNKNOWN_ERROR);
}
```

**为什么不是 `SQLIntegrityConstraintViolationException`？**

因为 MyBatis（Spring）会把 JDBC 的 `SQLException` 用 `SQLErrorCodeSQLExceptionTranslator` **翻译**成 Spring 的 `DataAccessException` 体系。

```
MySQL 抛出 SQLIntegrityConstraintViolationException (errorCode 1062, SQLState 23000)
  → Spring 的 SQLErrorCodeSQLExceptionTranslator 识别出 1062 = 唯一约束
  → 翻译成 DuplicateKeyException
  → 抛给调用方
```

**所以你永远 catch 不到原生的 `SQLIntegrityConstraintViolationException`**（除非绕过 Spring 直接用 JDBC）。

**这个坑我第一次就踩了**：写的 `@ExceptionHandler(SQLIntegrityConstraintViolationException.class)` 完全不生效，异常一路滑到兜底的 `Exception` handler，前端看到"未知错误"。

**判断方法**：看日志里的异常类名。如果是 `org.springframework.dao.DuplicateKeyException`，就 catch 它。

**顺带说：`ex.getMessage()` 的格式是 MySQL 定的**：

```
Duplicate entry 'wangwu' for key 'employee.idx_username'
```

所以代码要 `contains("Duplicate entry")` 再截取。**这是典型的"解析外部系统文本"，很脆弱** —— MySQL 换个版本、换个语言，格式可能就变。

**更稳的做法**：捕获后统一返回"该用户名已存在"（不解析具体值），或者在插入前用 DTO 校验一次用户名格式。

**现在这个实现的好处是错误信息友好**（"test_precision 已存在"），代价是耦合了 MySQL 的错误消息格式。**这是可接受的折中，但面试时应该主动说"这是解析数据库错误消息，比较脆弱"。**

### 易错点：`SQLIntegrityConstraintViolationException` 抛不出来的原因

补充一个更底层的点：**即使你绕过 Spring，直接用 MyBatis 的 `SqlSession`，拿到的也是 `PersistenceException` 而不是原生的 `SQLIntegrityConstraintViolationException`。**

因为 MyBatis 会把所有 `SQLException` 包装成 `PersistenceException`，Spring 再在外面包一层翻译。

**层层包装的结果**：你要 catch 的是**最外层**的类型，不是最内层的。

```
SQLException (JDBC)
  → PersistenceException (MyBatis)
    → DataAccessException 子类（Spring 翻译）
      → DuplicateKeyException (你该 catch 的)
```

## ⑥ 踩坑实录

### 坑 1：`@ExceptionHandler(SQLIntegrityConstraintViolationException.class)` 不生效

前面详细讲了。这里补充**当时的表现**：

- 重复用户名时，前端显示 `{"code":0,"msg":"未知错误"}`
- 日志里有完整堆栈，最外层是 `DuplicateKeyException`，`Caused by` 里才是 `SQLIntegrityConstraintViolationException`
- 我一开始只看了 `Caused by` 那一行，以为 catch 内层就行

**教训：Spring 的异常处理要 catch 最外层的"翻译后"类型。**

### 坑 2：`EmployeeLoginVO` 的字段叫 `userName`，实体叫 `username`

```java
// Employee 实体
private String username;      // 全小写

// EmployeeLoginVO
private String userName;      // 驼峰大写 N
```

登录响应的 JSON 是：

```json
{"id":1,"userName":"admin","name":"管理员","token":"..."}
```

**注意是 `userName` 不是 `username`。**

做前端时我写 `data.username` 取了半天 `undefined`，后来发现是 `data.userName`。

**为什么会有这种不一致？** 因为 `EmployeeLoginVO` 是照着课程/接口文档写的，文档里就叫 `userName`。而实体是照着数据库列名 `username` 生成的。

**这类"同一个概念两个拼法"的坑，在前端联调时最耗时** —— 因为接口有返回、状态码 200、只是某个字段取不到。

**预防方法**：接口文档要和 VO 严格一致；前端拿到响应先 `console.log` 看一眼真实字段名。

### 坑 3：分页查询传中文 400

```bash
curl "http://localhost:8080/admin/employee/page?name=测试" -H "token: $AT"
```

返回的是 **Tomcat 的 400 错误页**，不是 JSON：

```html
<!doctype html><html lang="en"><head><title>HTTP Status 400 – Bad Request</title>
```

**原因**：URL 里的中文没有编码，Tomcat 的高版本（Boot 3 内嵌 Tomcat 10）严格执行 RFC 7230，不允许 URL 里出现非 ASCII 字符。

**修法**：

```bash
curl -G "http://localhost:8080/admin/employee/page" --data-urlencode "name=测试" -d "page=1" -d "pageSize=2" -H "token: $AT"
```

**注意这是"测试姿势"的问题，不是代码问题** —— 真实前端 `fetch`/`axios` 会自动编码。

**但这类 400 很有价值**：它返回 HTML 而不是 JSON，说明请求在 **Tomcat 层就被拒了，根本没进 Spring**。所以 `GlobalExceptionHandler` 也没机会处理。

**判断"请求有没有进应用"的技巧**：看响应是 JSON（进了应用）还是 HTML 错误页（容器层就拒了）。

## ⑦ 缺口

| 缺口 | 严重度 | 说明 | 怎么改 |
|---|---|---|---|
| **分页查出了 `password` 和 `id_number`** | 中 | `selectPage` 默认查全字段，敏感数据在网络上跑了一遍 | `.select(...)` 指定列 |
| **`rows == 0` 语义模糊** | 低 | "不存在"和"值没变"都返回 0，取决于驱动配置 | 显式加 `ne(旧值)` 或先判存在 |
| **禁用员工不踢下线** | 中 | 禁用后他手上的 token 还能用满 2 小时（见精讲 04） | 短 TTL + 黑名单/版本号 |
| **没有角色权限** | 中 | 所有管理员权限相同，"新增员工"和"接单"是同一个人能干 | RBAC 表 + 注解式鉴权 |
| **初始密码固定 `123456`** | 中 | 所有新员工密码一样，且永不过期 | 随机密码 + 短信 + 首次登录强制改 |
| **没有操作审计** | 中 | 谁禁用/启用了谁，查不到（只有 `update_user` 字段） | 操作日志表 |
| **`update` 没校验手机号/身份证格式** | 低 | 传 `phone: "abc"` 也能存进去 | `@Valid` + `@Pattern` |
| **物理删除（如果有删除功能）** | — | 当前没有删除员工的接口，只有禁用，这个设计是对的 | — |

### 「分页查出 password」的严重性容易被低估

看起来"前端拿不到，没事"。但：

1. **日志**：`application.yml` 里开着 `log-impl: StdOutImpl`，所有 SQL 都打到控制台。如果这台机器被入侵，日志里全是密码哈希。
2. **中间件**：如果将来加了 SQL 审计、APM 探针、慢查询日志，密码哈希会进入这些系统。
3. **内部人员**：任何能看日志的人（运维、开发）都能拿到所有员工的密码哈希。虽然 MD5 不可逆，但 `123456` 的 MD5 一查就知道。

**"不返回给前端"和"不查询"是两件事。** 安全要求的是后者。

**这也是我建议加 `.select(...)` 的原因：成本很低（一行代码），收益很明确。**

### 「没有角色权限」是本项目最大的架构缺失

现在的情况：**任何能通过 admin 鉴权的人，可以调所有 `/admin/**` 接口。**

- 前台服务员也能看营业额报表
- 也能导出全部订单
- 也能新增/禁用员工（包括禁用老板）

真实业务必须区分角色：

```sql
CREATE TABLE role (id, code, name);
CREATE TABLE employee_role (employee_id, role_id);
CREATE TABLE permission (id, code, name, resource);
CREATE TABLE role_permission (role_id, permission_id);
```

然后用注解式鉴权：

```java
@PreAuthorize("hasRole('MANAGER')")     // Spring Security
@PostMapping("/employee")
public Result<Void> save(...) { ... }
```

**这是本项目已知的最大短板。** 面试如果被问"你的权限设计是怎样的"，诚实答"只做了认证没做授权，所有管理员权限相同；生产需要 RBAC"，比硬编一个不存在的功能强。

## ⑧ 面试 30 秒版

> 员工管理里有三个点值得说。
>
> 第一，**新增员工靠唯一索引兜底，不做"先查后插"**。因为先查后插在并发下无效——两个请求同时"查不到"然后都插入。直接插让数据库唯一索引在插入的瞬间原子保证唯一性，冲突时抛 `DuplicateKeyException`。这里有个坑：Spring 会把 JDBC 的 `SQLIntegrityConstraintViolationException` 翻译成 `DuplicateKeyException`，所以 `@ExceptionHandler` 要 catch 后者，我第一次 catch 内层类型完全没生效，异常滑到兜底 handler，前端只看到"未知错误"。
>
> 第二，**启停用 `updateById` 而不是"先查再改"**，一条 SQL 完成，靠影响行数判断存在性。但要注意 `rows == 0` 的语义取决于驱动的 `useAffectedRows` 配置——可能是"记录不存在"，也可能是"值没变"。
>
> 第三，**修改接口用 `setUsername(null)` / `setPassword(null)` / `setStatus(null)` 来排除字段**。因为 MyBatis-Plus 默认 `NOT_NULL` 策略，null 字段不会进 `SET`，所以这几行等于"这次更新不碰这些列"。用户名是唯一键、是登录凭证，不允许通过编辑接口改。
>
> 我还发现自己抓 SQL 时暴露了一个缺口：**分页查询把 `password` 也查出来了**。前端拿不到是因为 `@JsonIgnore`，但 SQL 层面确实传输了敏感数据，应该用 `.select(...)` 指定只查需要的列。
